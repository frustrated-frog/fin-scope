# Research 页面走查报告

> 走查日期：2026-07-11<br>
> 范围：Research 页面前端、研究运行 API、来源规划、异步执行、运行记录及当前本地数据。<br>
> 边界：本文是审查结论和讨论材料，不是实施方案，也不代表已经修复。

## 一、结论摘要

Research 页面目前更接近“后台任务调试台”，还不是用户可以依赖的研究工作台。

它能够发起一次按主题抓取来源的异步任务，并展示运行状态、计划步骤、来源快照和 Agent trace。但研究运行的产物归属不清、步骤语义与真实执行不一致、任务无法恢复，且页面没有把“本次研究得到什么结论”作为主内容。

当前最需要优先解决的不是继续增加页面字段，而是建立一条可追溯的主链：

```text
研究目标
  → 来源覆盖与选择理由
  → 可恢复的执行任务
  → 本次产出的文章、事件、证据、结论
  → 用户确认、收藏、追问或继续研究
```

## 二、当前页面与后端实际做了什么

### 2.1 用户可操作内容

`frontend/src/features/research/ResearchView.tsx` 提供：

- 日期；
- 三个固定主题：中国宏观、AI 创业、公司 / IPO；
- 每主题来源数；
- 是否包含停用来源；
- 启动一次研究任务；
- 查看运行表格和技术 trace；
- 任务完成后打开当天简报。

页面没有研究问题、研究对象、假设、时间窗口、排除条件、证据标准或交付物类型等输入。

### 2.2 后端实际工作流

`ResearchService#createRun` 创建运行记录、计划来源和六个计划步骤，然后通过应用内 `Executor` 异步执行：

1. 规划来源；
2. 抓取来源；
3. 标记“归并事件”完成；
4. 标记“抽取证据”完成；
5. 生成简报；
6. 汇总运行。

但文章抓取时，`FetchService` 已经调用 `ArticleIngestCoordinator`；后者在文章入库期间直接触发文章解读、事件归并、证据抽取、学习任务和选题生成。因此“归并事件”和“抽取证据”并不是 ResearchService 在抓取后独立执行的阶段。

## 三、关键问题

### P0-1：运行产物没有可靠归属，统计可能串任务

**证据**

- `ResearchService#execute` 通过全库 `countAll()` 的前后差值计算本次运行的文章、事件、证据、学习任务和选题数量。
- `ResearchRun` 只保存总数，没有保存本次产物的 ID 集合，也没有对应的 run-output 关联表。
- `ResearchRunDetailResponse` 只返回运行本身、来源快照、步骤和 Agent trace，不返回本次产出的事件、证据、学习任务或选题。

**后果**

如果两个抓取或研究任务并发执行，其他任务写入的事件和证据会被计入当前运行。即使单任务运行成功，用户也无法从 Research 页面打开“本次生成的 12 条证据”来验证统计。

**判断**

这是该页面不能成为可信研究工作台的首要问题。研究结果的可追溯性必须先于仪表盘和视觉优化。

### P0-2：计划步骤的语义不真实

**证据**

- `ResearchRunPlanService` 定义了“抓取来源 → 归并事件 → 抽取证据”的串行计划。
- `ArticleIngestCoordinator#ingestInternal` 在抓取来源的过程中已经调用 `eventClusterService.attachArticle(saved)`。
- `EventClusterService#attachArticle` 会调用 `evidenceService.capture(event, article)`，并生成学习任务、内容选题。
- `ResearchService#execute` 的“归并事件”和“抽取证据”阶段只有计数和状态更新，没有对应的执行调用。

**后果**

运行详情展示的是一份流程说明，而不是实际执行轨迹。页面上“正在归并事件”或“抽取证据已完成”的含义不可靠，排障和用户信任都会受损。

### P0-3：运行任务不能恢复，也没有重试闭环

**证据**

- 任务运行在应用内 `researchTaskExecutor` 上，进程退出后任务不会续跑。
- `ResearchStartupRecoveryService` 会把所有遗留的 `RUNNING` 任务和开放步骤收敛为失败。
- 当前本地 `/api/research/runs` 数据中，运行记录 4 到 12 多次因进程关闭而失败，错误为 `Run was interrupted by process shutdown before completion.`。
- 页面没有“重试失败来源”“从中断处继续”“复制配置重跑”或“取消任务”入口。

**后果**

本地重启、开发调试或单个慢来源都会使一次长研究直接失效。用户只能重新发起整个任务，既浪费时间，也无法保持运行历史的可比性。

## 四、功能层面的问题

### P1-1：用户不能定义研究任务

当前页面的核心动作是“生成今日研究”，输入只有固定主题与来源数量。它实际完成的是“抓取一批主题来源并生成日报”，不是“开展一次研究”。

缺失的研究任务要素包括：

- 研究问题或假设；
- 关注对象，例如公司、行业、政策、人物或事件；
- 研究时间范围与信息截止点；
- 必须覆盖的来源或排除来源；
- 证据门槛、反证要求和预期交付物；
- 用户希望得到的是日报、事件图谱、公司研究、观点对比还是行动清单。

### P1-2：“每主题来源数”与实际来源覆盖不一致

`SourcePlanner` 会在主题间全局去重来源，因此“每主题 3 个来源”不代表每个主题最终都有 3 个来源。

同时，来源即使没有对应主题标签，只要来源层级属于某主题的偏好层级，也会被选中。`MEDIA` 被多个主题偏好，泛财经来源可以进入不相关主题。

当前页面只显示总来源数和来源列表，不显示：

- 每个主题实际分配到的来源；
- 每个来源被选中的理由；
- 哪个主题覆盖不足；
- 来源之间是否高度重复；
- 因停用、无标签或质量不足而被排除的来源。

### P1-3：完成后没有“研究结果页”

当前页面完成后仍然以运行表和 trace 为中心。用户最多点击“打开简报”，但不能从本次运行直接查看：

- 本次新增的文章；
- 本次形成的事件；
- 每个事件的证据链与可信度；
- 新增学习任务和选题；
- 哪些关键问题没有找到证据；
- 简报中的结论由哪些证据支撑。

这使得页面缺少用户可消费的成果层。

## 五、技术实现问题

### P1-4：详情接口返回完整 Agent 原始输入输出

`ResearchController#detail` 直接返回 `agentRunService.findByResearchRunId(id)` 的全部记录，未做分页、摘要、裁剪或权限分层。前端再直接渲染 `run.output`。

当前本地运行记录中已经可以看到完整模型提示词、文章正文片段和模型长输出。风险包括：

- 详情接口体积随运行历史快速膨胀；
- 前端详情面板会被长文本撑坏；
- 调试信息和普通研究结果混在一起；
- 后续若输入中带有敏感配置或用户私有上下文，存在不必要暴露面。

建议把“研究摘要”和“调试 trace”拆成两个接口或两个权限层级。默认只返回节点摘要、状态、耗时、错误类别和可点击的结果链接；原始输入输出应按需展开并分页。

### P1-5：前端轮询成本高且边界不清

Research 运行详情每 750ms 轮询一次。每轮同时请求运行详情和完整运行列表。

问题包括：

- 首次轮询依赖定时器，没有立即执行；
- 前一轮请求未结束时，下一轮仍可能发起；
- 选中过运行后，即使用户切换到其他页面，状态仍保留时可能继续轮询；
- 每次进度刷新都拉取完整运行列表，而不是仅刷新当前运行的轻量摘要；
- 使用轮询但没有退避策略。

### P2-1：输入校验与资源保护不足

界面限制每主题来源数为 1 到 8，但 API 侧没有等价上限校验。直接调用接口可以传入极大值，导致来源规划和抓取任务膨胀。

同时没有幂等键、同配置去重、并发上限提示或取消机制。同日期、同主题可以被重复启动多次，结果又无法归属，因此很难比较或合并。

### P2-2：运行状态对用户不友好

页面直接展示 `RUNNING`、`PARTIAL_SUCCESS`、`SourcePlanner`、`FetchService`、`Δ` 等系统术语。它对开发排障有帮助，但对研究用户不回答三个关键问题：

1. 这次研究正在回答什么问题？
2. 目前发现了什么？
3. 下一步用户应该做什么？

## 六、当前测试覆盖的不足

现有测试覆盖了研究任务能被创建、来源抓取被调用、无来源时失败、以及 App 能展示一条 trace。

尚未看到对以下关键约束的覆盖：

- 并发运行时，运行产物不会串统计；
- 一次运行可以精确列出自己的事件、证据和任务；
- 计划步骤与真实执行调用一一对应；
- 中断后可安全重试或续跑；
- 来源规划满足每个主题的最低覆盖；
- Agent 原始输出不会无限制进入主详情接口；
- ResearchView 在运行中、部分失败、无结果、可重试等状态下的交互。

## 七、建议的讨论顺序

在进入实施前，建议先共同确定以下产品决策：

1. Research 页面究竟是“每日自动研究运行台”，还是“用户发起专题研究的工作台”？
2. 一次研究的最小交付物是什么：日报、事件与证据包、专题报告，还是可继续追问的研究会话？
3. 用户是否需要研究问题输入，还是仅需要系统自动生成每日研究？
4. 事件、证据、学习任务和选题是否都必须能追溯到某一次运行？
5. 失败时优先支持重试、续跑、取消还是人工确认？

在以上决策明确前，不建议直接扩展当前运行表或继续增加更多“计划步骤”。

## 八、推荐的重构优先级

### 第一阶段：可信运行

- 建立运行与产物的显式关联；
- 消除全库计数差值；
- 让每个计划步骤对应真实执行单元；
- 提供失败来源重试和中断续跑；
- 定义并发、幂等和取消策略。

### 第二阶段：研究成果优先

- 定义研究问题、范围和交付物；
- 展示来源覆盖预览与缺口；
- 为运行详情增加“本次结果”页签；
- 从本次运行直达事件、证据链、简报和待办。

### 第三阶段：调试与体验收口

- 将 trace 与普通研究结果分层；
- 对原始 Agent 输入输出分页、裁剪和按需加载；
- 优化轮询为轻量进度接口或 SSE；
- 用中文业务语言解释状态、降级与下一步动作。
