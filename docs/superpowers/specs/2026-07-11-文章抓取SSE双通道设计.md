# 文章抓取 SSE 双通道设计

## 目标

将文章 URL 抓取从“800ms 高频轮询驱动进度”升级为：

- SSE 作为实时进度主通道；
- `async_task` 持久化状态作为唯一事实来源；
- 低频轮询负责页面刷新、断线和丢事件恢复；
- SSE 故障不能中断抓取任务；完成事件必须在结果落库后发送。

## 架构

后端新增通用文章任务进度契约 `TaskProgressEvent` 与发布接口 `TaskProgressPublisher`。Web 层实现 `TaskSseRegistry`，维护每个 taskId 的订阅者和有限事件缓冲。`UrlIngestTaskService` 的每次状态迁移顺序固定为：

1. 更新 `async_task`；
2. 从持久化状态构造事件；
3. 尝试发布 SSE；
4. SSE 发布失败只记录日志，不改变任务状态。

终态顺序为：文章与卡片落库 → `async_task` 更新为终态 → 发布 `DONE/ERROR` → 关闭 SSE。

前端提交任务后立即建立 `/api/tasks/{taskId}/stream`。SSE 更新界面阶段；同时每 5 秒读取 `/api/tasks/{taskId}`。SSE 异常后轮询提高到 800 毫秒，SSE 正常时保持低频。无论 SSE 收到什么，终态都必须再读取任务接口确认。

## 事件模型

`TaskProgressEvent` 包含：

- `eventId`：任务内单调事件标识，用于去重；
- `taskId`；
- `type`：`SNAPSHOT | PHASE | DONE | ERROR | HEARTBEAT`；
- `status`、`phase`、`message`、`errorMessage`、`articleId`；
- `occurredAt`。

新订阅建立时，后端先补发有界内存缓冲，再发送数据库 `SNAPSHOT` 收敛到最新事实。即使服务重启导致缓冲丢失，数据库快照仍能恢复当前状态。

## 并发与生命周期

- 注册表支持同一任务多个订阅者，避免刷新或多标签页互相挤掉连接。
- 缓冲采用有界队列，只保留最近 32 条事件，并在任务终态或超时后清理。
- 订阅前任务已经完成时，发送终态快照后立即关闭。
- 前端使用 generation token 防止旧任务回调覆盖新任务。
- 组件卸载、重试和新任务提交时必须关闭旧 EventSource、定时器和失效请求结果。

## 接口

- 保留 `POST /api/articles/ingest-url`。
- 保留 `GET /api/tasks/{taskId}`，作为事实查询与轮询恢复接口。
- 新增 `GET /api/tasks/{taskId}/stream`，响应 `text/event-stream`。

## 错误处理

- SSE 建连失败：继续低频/快速轮询，不向用户报告抓取失败。
- 任务查询暂时失败：指数式容忍有限次数，SSE 仍可继续更新。
- SSE 收到 DONE：立即查询任务详情；只有数据库状态为 `COMPLETED` 才刷新文章列表。
- SSE 收到 ERROR：立即查询任务详情，并优先展示数据库中的 `errorMessage`。
- 超时但文章已存在：保留现有按 URL 恢复成功逻辑。
