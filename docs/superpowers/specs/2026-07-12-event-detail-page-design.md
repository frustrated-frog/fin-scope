# 事件独立详情页设计

## 目标

将事件研究台拆分为轻量的事件队列页与应用内独立事件档案页。队列负责发现、筛选和切换；档案页负责阅读事件演变、归并依据、当前证据状态以及人工治理，避免在双栏工作台中压缩高密度研究信息。

## 用户流程

```text
事件队列
  -> 点击事件卡
  -> 应用内事件档案页
  -> 返回事件队列
  -> 恢复此前筛选条件、分页与已选事件
```

不使用新浏览器标签页、弹窗或 URL 路由库。沿用 App 当前基于 `View` 的应用内状态导航；新增 `eventDetail` view 和 `focusedEventId`。

## 页面职责

### 事件队列页

- 保留标题、主题/状态/新意筛选、分布摘要、事件卡和分页。
- 移除右侧详情面板和详情数据请求。
- 点击事件卡时调用 `onOpenEvent(eventId)`，进入档案页。
- 卡片继续显示标题、摘要、主题、新意、文章/证据数、重要性和最近更新。

### 事件档案页

顶部为返回事件队列按钮、主题/状态/新意标签和治理操作入口；其余内容按研究阅读顺序排列：

1. 标题、摘要、重要性、文章数、证据数、最后更新。
2. **事件如何发展**：按文章时间顺序呈现，保留新意类型与原文链接。
3. **为什么归并**：逐篇显示 relationType、matchScore、noveltyType 和 noveltyReason。
4. **当前证据状态**：只展示最高质量的两条代表证据和到证据工作台的入口；完整判断关系不重复渲染。
5. 学习任务和内容选题。
6. 人工治理：状态调整、事件合并、文章迁移；保持现有确认机制和刷新行为。

桌面端使用主内容 2/3 与上下文侧栏 1/3 的比例；900px 以下折为单列。视觉上复用深色工作台 token，不新引入独立色板。详情页的记忆点是“档案脊柱”：时间线左侧的日期/新意标记连续贯穿事件演变，不用装饰性大卡片分割阅读。

## 组件与数据边界

- `EventsView` 仅保留队列、筛选和分页；不再持有详情查询或治理状态。
- 新增 `EventDetailView`，唯一负责所选事件的文章/证据请求、学习/选题过滤和治理操作。
- `App` 持有 `focusedEventId`，在队列打开、证据页跳转和返回时统一维护。
- 复用既有接口：`GET /api/events/{id}/articles`、`GET /api/events/{id}/evidence` 和既有治理 handler；不改变后端 API。

## 错误与空状态

- 详情事件不存在时，显示明确说明及“返回事件队列”动作。
- 文章、证据、学习任务、内容选题为空时保留当前说明文案。
- 详情请求失败时不展示过期事件数据；显示重试按钮。

## 验收标准

1. 点击队列事件卡会打开独立详情页，返回后保持原筛选与分页。
2. 详情页保留原工作台中的时间线、归并依据、代表证据、学习任务、选题和治理能力。
3. 事件列表不再与详情并排，1280px 宽度下卡片无需为详情面板让位。
4. 详情在 900px 以下单列可读，键盘可访问返回与治理控件。
5. 前端单测覆盖打开、返回、详情数据加载和治理 handler；构建通过。
