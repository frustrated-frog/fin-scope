# 命题研究报告生成与简报解耦技术方案

## 1. 现状与根因

当前 `ResearchService.execute` 在抓取和证据抽取后直接调用 `BriefService.generate(runDate)`。`BriefService` 与 `BriefResearchContextService` 又按日期查询全部文章和事件，因此研究产物跨运行、跨命题混合，并覆盖 `vault/daily-briefs/{date}.md`。

报告质量问题由四个技术原因共同造成：

1. **产物类型错误**：研究报告复用了每日简报领域对象和文件路径。
2. **作用域错误**：上下文按日期构建，而不是按 `research_run_output` 的 `runId` 构建。
3. **生成输入错误**：完整机械 Markdown 被截断到前 9,000 字后交给模型，模型看不到整体证据结构。
4. **降级错误**：模型异常被吞掉，系统把无长度上限的机械模板当作正式报告写入。

修复必须建立独立的研究报告边界，不能继续在 `BriefGenerator` 上增加条件分支。

## 2. 总体架构

```text
ResearchThesis
  -> ResearchPlanBuilder
  -> ThesisQueryExpansionService
  -> configured sources + dynamic Google News RSS
  -> RunScopedResearchContextService
  -> ResearchEvidenceSelector
  -> EvidenceSufficiencyEvaluator
       -> insufficient: expand query and fetch, max 3 rounds
       -> sufficient / budget exhausted
  -> ResearchReportGenerator
  -> ResearchReportRepository + ResearchReportVaultWriter
  -> /api/research/runs/{runId}/report
```

每日简报仍由 `BriefService` 独立维护，研究编排器不再依赖它。

## 3. 数据模型

### 3.1 research_report

```sql
CREATE TABLE research_report (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  research_run_id INTEGER NOT NULL UNIQUE,
  thesis_id INTEGER,
  report_type TEXT NOT NULL,
  status TEXT NOT NULL,
  title TEXT NOT NULL,
  conclusion TEXT NOT NULL,
  conclusion_direction TEXT NOT NULL,
  confidence TEXT NOT NULL,
  executive_summary TEXT NOT NULL,
  content_markdown TEXT NOT NULL,
  markdown_path TEXT NOT NULL,
  generation_mode TEXT NOT NULL,
  warning_message TEXT,
  evidence_count INTEGER NOT NULL DEFAULT 0,
  source_count INTEGER NOT NULL DEFAULT 0,
  character_count INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

约束：

- `research_run_id` 唯一，保证一次运行只有一个正式报告。
- `report_type` 为 `THESIS` 或 `EXPLORATION`。
- `generation_mode` 为 `AGENT` 或 `DETERMINISTIC_FALLBACK`。
- `conclusion_direction` 为 `SUPPORT`、`PARTIAL_SUPPORT`、`COUNTER` 或 `LOW_CONFIDENCE_LEAN`。
- `character_count <= 12000` 由服务层强校验。

### 3.2 research_plan_snapshot

为避免增加过多表，研究计划以 JSON 快照保存在报告生成过程和 Agent trace 中，不单独建立可编辑领域模型。`ResearchPlanSnapshot` 包含：

- 原始命题、研究对象。
- 子问题列表。
- 中文关键词、英文关键词、主体和指标。
- 正向查询和反向查询。
- 最大检索轮数。

### 3.3 thesis_finding

增加可空 `research_run_id` 列和索引，使阶段性发现可追溯到运行。现有记录保持兼容。

### 3.4 research_run_output

新增输出类型 `REPORT`。新运行不再记录 `BRIEF`。报告实体 ID 通过既有输出表关联到运行和命题详情。

## 4. 核心组件

### 4.1 ResearchPlanBuilder

输入：`ResearchThesis`、运行主题和日期。

输出：`ResearchPlanSnapshot`。

策略：

1. 先生成确定性基础计划，保证模型不可用时仍可执行。
2. 模型可用时只允许补充或改写 3–6 个子问题和检索词。
3. 校验计划必须包含反向查询和至少一个可观测指标。
4. 模型输出无效时记录 fallback 原因并使用基础计划。

### 4.2 ThesisQueryExpansionService

根据研究对象和未覆盖子问题构建免费动态 Google News RSS URL：

```text
https://news.google.com/rss/search?q={encodedQuery}&hl=zh-CN&gl=CN&ceid=CN:zh-Hans
```

每轮最多两个查询：一个主查询、一个反证或缺口查询。最多三轮。动态查询使用临时 `Source` 对象，通过 `FetchService.fetch(Source)` 复用 RSS、筛选和入库流程，不写入用户来源配置表。

### 4.3 RunScopedResearchContextService

只能通过 `ResearchRunOutputService.list(runId)` 获得本次运行的文章、事件和证据 ID，再批量查询实体。禁止调用 `findByDate`。

输出：

- 本次运行文章。
- 本次运行事件。
- 本次运行证据。
- 来源快照。
- 研究计划。

### 4.4 ResearchEvidenceSelector

先执行确定性预筛选，再执行一次可选的批量模型判断。

确定性相关性分数由以下信号组成：

- 研究对象命中：35 分。
- 子问题关键词命中：25 分。
- 核心指标命中：15 分。
- 来源可信度：最多 15 分。
- 新鲜度：最多 10 分。

低于 35 分直接丢弃；35–59 分只进入附录候选；60 分以上进入证据矩阵候选。模型只能在候选集合内调整相关性、子问题和立场，不能把零命中的无关材料抬进正文。

正文证据选择规则：

- 最多 15 条。
- 同一 URL 或标题指纹只保留一条。
- 同一来源最多 5 条。
- 至少保留一条反证或明确记录已经执行反证检索但未发现有效反证。
- 英文标题和摘要生成简洁中文事实摘要，原始标题只放附录。

### 4.5 EvidenceSufficiencyEvaluator

计算：

- 核心子问题覆盖率。
- 全部子问题覆盖率。
- 高相关事实数量。
- 独立来源数量。
- 反证检索完成情况。

充分条件：核心覆盖 100%、整体覆盖不低于 70%、至少 3 条高相关事实、至少 2 个独立来源且完成反证检索。

不足时返回明确缺口，用于生成下一轮查询。第三轮后仍不足时返回 `LOW_CONFIDENCE_LEAN`，要求报告给出方向性判断和缺失项，禁止用空洞的“无法判断”结束。

### 4.6 ResearchReportGenerator

输入只包含：

- 研究计划。
- 充分性结果。
- 最多 15 条压缩证据卡片。
- 每条卡片最多 500 字符。

报告生成分两层：

1. 确定性生成器先构造包含所有必需章节的合规 Markdown。
2. 模型基于同一证据矩阵进行语言和推理综合。

模型输出必须通过 `ResearchReportPolicy`：

- 含全部 9 个章节。
- 执行摘要 800–1,200 字符。
- 正文 4,000–8,000 字符。
- 总长度不超过 12,000 字符。
- 包含结论方向、置信度、支持证据、反证和下一验证。
- 不包含未出现在证据矩阵中的 URL 或数字。

不合规时使用规则化报告，并把 `generation_mode` 设置为 `DETERMINISTIC_FALLBACK`，同时记录具体警告。

### 4.7 ResearchReportService

负责：

- 验证运行和命题。
- 保存或幂等更新报告。
- 写入 `vault/research-reports/thesis-{id}/run-{id}.md`；探索运行写入 `vault/research-reports/exploration/run-{id}.md`。
- 记录 `REPORT` 输出。
- 提供按运行查询接口。

### 4.8 ResearchService 改造

删除对 `BriefService` 的依赖。运行末尾调用研究报告流水线，并将原 `compose_brief` 步骤替换为：

- `plan_research`
- `screen_relevance`
- `build_evidence_matrix`
- `check_sufficiency`
- `compose_report`

运行成功后不设置 `briefDate`。报告失败时运行进入 `FAILED`；规则化 fallback 成功时运行仍可 `COMPLETED`，但报告带 warning。

## 5. API 与前端契约

### 5.1 API

```http
GET /api/research/runs/{runId}/report
```

返回 `ResearchReport`。不存在时返回 404。

```http
POST /api/research/runs/{runId}/report/regenerate
```

只基于已有 run-scoped 产物重新生成，不重新抓取；用于迁移运行 14 和报告策略升级后的重算。

### 5.2 研究页

- 运行详情按钮从“打开简报”改为“打开研究报告”。
- 展示结论方向、置信度、生成模式和警告。
- 报告正文继续复用现有 Markdown 阅读能力，但数据来源改为研究报告 API。
- 每日简报页面和接口保持不变。

## 6. 模型与时间预算

- 研究计划：最多 1 次模型调用。
- 证据判断：最多 1 次批量模型调用。
- 报告综合：最多 1 次模型调用。
- 单次运行模型调用上限：3。
- 动态检索轮数上限：3。
- 候选文章上限：30。
- 证据上下文上限：8,000 字符。
- 报告总字符上限：12,000。
- 任一模型超时均进入明确 fallback，不重复无限重试。

## 7. 迁移方案

### 7.1 运行 14

1. 使用 `research_run_output` 中运行 14 的 ARTICLE、EVENT、EVIDENCE 构建 run-scoped 上下文。
2. 生成并保存独立报告。
3. 删除运行 14 的 `BRIEF` 输出关联。
4. 将 `research_run.brief_date` 置空。

### 7.2 错误简报

1. 将 `../data/vault/daily-briefs/2026-07-13.md` 移动到 `../data/recovery/invalid-research-brief-2026-07-13-run-14.md`。
2. 删除 `brief_date=2026-07-13` 且由运行 14 生成的错误数据库记录。
3. 操作前验证文件路径和运行 14 的 BRIEF 输出关联，避免误处理用户手工简报。

## 8. 测试策略

### 8.1 单元测试

- 计划包含 3–6 个子问题、反向查询和指标。
- 相关性评分排除 CISA 和无关文学论文。
- 证据选择满足去重、来源上限和 15 条上限。
- 充分性不足时产生下一轮缺口查询。
- 第三轮后产生低置信度方向判断。
- 报告策略拒绝缺章节和超 12,000 字符的输出。
- fallback 报告仍包含九个章节和证据引用。

### 8.2 服务测试

- `RunScopedResearchContextService` 只查询指定运行输出。
- `ResearchService` 不再调用 `BriefService`。
- 研究运行不设置 `briefDate`，而是记录 `REPORT`。
- 模型调用总数不超过 3。

### 8.3 集成测试

- 在测试前创建一份每日简报，执行研究运行后断言其内容字节级不变。
- 同一天创建两个研究运行，断言报告数据互不污染。
- 运行报告 API 返回 200，简报 API 返回原内容。
- 迁移运行 14 后报告可读，错误简报不再出现在简报列表。

## 9. 风险与控制

- **免费 RSS 波动**：单来源失败不阻止其他来源和动态查询；终态记录部分成功。
- **命题过宽**：研究计划限制为 3–6 个子问题，并在报告中声明范围。
- **模型幻觉**：只允许使用证据矩阵，输出通过数字和 URL 白名单校验。
- **报告过长**：服务层硬拒绝，不依赖提示词自觉。
- **旧数据污染**：所有正式报告查询必须从 `runId` 输出关系起步。
- **迁移误删**：先备份文件，验证 BRIEF 输出归属后再删除索引。
