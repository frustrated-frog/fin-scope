# 研究运行可靠性与报告阅读体验设计

## 1. 背景与现场证据

本次问题由三个不同层面的缺陷叠加形成：

1. 运行 15 创建于 2026-07-13 18:41，仍使用旧流程的 `compose_brief`，数据库只有 `BRIEF` 输出，没有 `research_report`。新前端仅根据运行状态不是 `RUNNING/FAILED` 就展示“打开研究报告”，导致稳定返回 404。
2. 运行 16 创建于 23:29，抓取、归并和证据抽取约耗时 10 秒，但 `compose_report` 从 23:29:45 持续到 23:31:13，单步耗时 88.5 秒。最终报告仍为 `DETERMINISTIC`，说明长时间模型请求没有产生可采用结果。
3. 运行 16 的报告 API 返回 200，`contentMarkdown` 有 3,975 个字符，Vault 文件约 9.2KB。前端把报告追加在很长的运行详情和 Agent Trace 之后，既不切换阅读状态，也不滚动定位，因此用户感知为空白。
4. 前端每 750ms 轮询一次运行详情，但当前阶段埋在长列表中；Agent Trace 又直接展示英文节点名和巨大 JSON，技术数据没有转化为用户能理解的进度。

## 2. 目标

- 运行列表和详情只在报告真实存在时显示“打开研究报告”。
- 绑定命题的运行结束时，报告落库、REPORT 输出和终态保持一致。
- 历史运行没有报告时，提供明确的“补建研究报告”动作，不再抛出不可恢复的 404。
- 正常命题研究在免费数据可用时尽量控制在 30 秒内；模型慢或不可用时快速使用确定性报告。
- 运行期间持续显示当前阶段、完成度、实时数量和阶段耗时。
- 报告在独立阅读面展示，打开动作立即可见，支持返回运行详情。
- Agent Trace 保留诊断价值，但默认只展示中文摘要，原始 JSON 按需展开。

## 3. 方案选择

### 方案 A：显式报告能力 + 轮询进度投影 + 独立阅读面（采用）

后端在运行详情中返回报告能力状态和当前进度投影；前端继续复用现有轮询，不引入新的长连接基础设施。报告模型使用独立短超时，证据不足时跳过模型。报告打开后进入独立阅读状态。

优点是同时解决数据一致性、等待时间、进度表达和报告不可见问题，且对当前架构侵入适中。

### 方案 B：只修前端按钮和自动滚动（不采用）

实现快，但 run 15 仍没有报告，88 秒模型等待仍存在，运行进度仍不可理解。

### 方案 C：新增 SSE 流式事件总线（暂不采用）

实时性最好，但当前数据库中的计划步骤已经足够支撑 750ms 轮询。此时引入 SSE 会扩大服务端连接、断线恢复和测试范围，不符合本轮聚焦修复目标。

## 4. 后端设计

### 4.1 运行详情中的报告能力

`ResearchRunDetailResponse` 增加：

- `reportAvailable`：该运行是否存在 `research_report`。
- `reportStatus`：报告状态，例如 `COMPLETED` 或 `COMPLETED_WITH_GAPS`。
- `reportGenerationMode`：`LLM_VALIDATED` 或 `DETERMINISTIC`。
- `canRegenerateReport`：运行绑定命题、已结束且不是 `RUNNING` 时为 true。

按钮和空态都基于这组显式能力字段，不再从运行状态猜测报告是否存在。

### 4.2 终态一致性

对新运行保持以下顺序：

1. 生成并持久化报告文件。
2. upsert `research_report`。
3. 记录唯一 `REPORT` 输出。
4. 完成 `compose_report` 计划步骤。
5. 最后把研究运行更新为 `COMPLETED` 或 `PARTIAL_SUCCESS`。

任一报告步骤失败，运行进入 `FAILED`，不能出现“运行成功但没有报告”。

### 4.3 报告生成时间预算

- `EvidenceSufficiency` 不充分时直接采用确定性报告，不调用报告模型。
- 证据充分时允许一次报告模型调用，独立连接/读取超时为 20 秒。
- `LlmChatClient` 增加带单次超时参数的重载；实际 HTTP 客户端使用“单次预算与全局预算中的较小值”。
- 模型超时、异常或输出不合规时立刻采用确定性报告，并将生成模式保留为 `DETERMINISTIC`。
- 不进行模型自动重试，避免一次报告反复消耗时间和成本。

### 4.4 遗留运行恢复

运行 15 使用现有 `POST /api/research/runs/{id}/report/regenerate` 补建报告。补建成功后：

- 删除该运行的 `BRIEF` 输出关联。
- 清空 `research_run.brief_date`。
- 若 2026-07-13 简报确认为该遗留研究生成的超长简报，则先备份数据库和文件，再移出简报索引。
- 不修改其他运行或用户简报。

## 5. 进度投影

不新增持久化表。前端根据 `research_run_plan` 与运行计数构建用户进度：

- `plan_sources`：正在规划资料范围。
- `fetch_sources`：正在获取资料，展示 `fetchedSourceCount/sourceCount`、文章和证据数量。
- `classify_events`：正在整理事件。
- `extract_evidence`：正在筛选证据。
- `compose_report`：正在组织研究报告，并展示阶段耗时。
- `summarize_run`：正在保存结果。

进度百分比按六个计划步骤完成数计算；当前步骤为 `RUNNING` 时显示脉冲轨道，但尊重 `prefers-reduced-motion`。阶段耗时由 `startedAt` 在浏览器端计算，每秒更新，不需要额外请求。

## 6. 前端交互设计

### 6.1 运行详情

运行详情顶部增加“研究进度轨道”：

```text
┌ 当前阶段：生成研究报告 ───────────── 4 / 6 ┐
│ ● 规划  ● 获取资料  ● 整理事件  ● 筛选证据  ◉ 生成报告  ○ 保存 │
│ 已获取 8/9 来源 · 56 篇资料 · 56 条候选证据 · 本阶段 18s       │
└─────────────────────────────────────────────┘
```

这是页面唯一的高强调元素，沿用当前墨蓝底色和青绿色状态色；失败使用克制的红色，证据缺口使用琥珀色。

### 6.2 报告按钮状态

- `reportAvailable=true`：显示“阅读研究报告”。
- `reportAvailable=false && canRegenerateReport=true`：显示“补建研究报告”。
- 运行中：显示禁用文案“报告生成中”。
- 探索运行或无法补建：不显示报告动作，并解释原因。

补建操作有进行中状态，完成后刷新运行详情并自动进入阅读面。

### 6.3 独立报告阅读面

打开报告后，研究执行表单、运行列表和 Trace 暂时退出主视觉，只展示：

- 返回运行详情。
- 报告标题、命题、结论、置信度、生成模式、证据和来源数量。
- 证据不足警告。
- Markdown 正文。

阅读面使用现有排版语言，不新增装饰性视觉；正文宽度限制在适合长文阅读的范围。打开时标题获得焦点并滚动到页面顶部，键盘用户可以立即继续浏览。

### 6.4 Agent Trace

- 节点名映射为中文：`article-interpret` → “理解文章”，`evidence-extract` → “提取证据”等。
- 默认只展示状态、耗时和最多 160 字的摘要。
- 原始输入、输出 JSON 和 fallback 技术信息放入 `<details>`，明确标记“诊断信息”。
- 长文本必须换行和裁剪，不能横向撑破页面。

## 7. 错误与空态

- 404 不再直接暴露 `Research report not found`。若可补建，显示：“这次历史运行尚未生成独立报告，可以用已有证据补建。”
- 报告正文为空或少于最低有效长度时不进入阅读面，显示可执行错误。
- 补建失败保留运行详情和错误提示，不清空原有页面。
- 轮询失败只更新进度错误提示，不丢失最后一次成功状态。

## 8. 测试与验收

### 后端

- 运行详情准确返回报告能力字段。
- 证据不足时报告模型调用次数为 0。
- 证据充分时使用单次 20 秒预算；超时后返回确定性报告。
- 新运行终态存在且只存在一个 `research_report` 和一个 REPORT 输出。
- run 15 补建后报告可查询，BRIEF 关联为 0。

### 前端

- 没有报告的历史运行显示“补建研究报告”，不显示“阅读研究报告”。
- 运行中展示当前步骤、完成度、数量和耗时。
- 点击报告后切换到独立阅读面，正文立即在可视区域出现。
- 返回按钮恢复同一运行详情。
- Agent Trace 默认不直接展示巨大 JSON。

### 真实验收

- run 15 可补建并打开。
- run 16 可直接进入阅读面并看到完整正文。
- 新建一次研究，观察抓取、证据、生成报告、完成全过程；证据不足路径不再等待报告模型。
- 桌面宽屏与窄屏均无横向溢出，键盘焦点和减少动画偏好有效。

## 9. 非目标

- 本轮不引入 SSE/WebSocket。
- 不重写整个研究中心或全局导航。
- 不把所有 Agent Trace 删除；只降低其默认展示权重。
- 不承诺外部 RSS 永远成功；单一来源失败继续以 `PARTIAL_SUCCESS` 结束，但必须有报告。
