# 财报解读 Agent 深度与性能升级设计

> 日期：2026-07-17；状态：已确认；范围：A 股非金融企业财报解读第三阶段

## 1. 目标

在不降低证据约束的前提下，同时提升解读深度和生成速度。

- 内容从“每个维度一句结论”升级为“结论、关键事实、趋势、驱动、反证和观察项”。
- 单次模型输入由当前约 60 KB、247 条证据压缩到不超过 24 KB、72 条高价值证据。
- 真实模型成功输出保持单次调用，目标 P50 小于 18 秒，P95 小于 35 秒。
- 输出中的每条事实、推断和观察项继续使用稳定证据引用，并通过服务端门禁。
- 历史 v1/v2 结果继续可读，不修改已有记录。

本期不接入公告 PDF 原文，不实现自由问答，不更换用户现有模型服务 URL。

## 2. 方案选择

采用“确定性证据摘要 + 单次结构化生成”的方案。

未采用直接扩写现有提示词，因为当前证据包包含 207 条原始科目和 32 条趋势，模型需要先在大量低价值字段中寻找重点，输入越长，速度和稳定性越差。

未采用六个维度并行调用，因为它会把一次模型请求放大为六次，增加成本、限流风险和跨维度结论冲突，也不利于统一门禁。

推荐方案先在服务端筛选、分组和排序证据，再让模型一次生成完整 JSON。输入更短，输出可以更长，总耗时仍可下降。

## 3. 用户结果结构

保留现有经营状态、置信度、执行摘要、六维分析、积极信号、风险、拐点、观察项、限制和免责声明。

新增两个一级章节：

1. `periodChanges`：本期最重要的同比、环比或连续趋势变化，2 至 3 条。
2. `crossStatementInsights`：利润表、资产负债表和现金流量表之间的勾稽观察，1 至 3 条。

六维分析从单一 `summary` 扩展为：

- `summary`：一句话判断。
- `details`：1 至 2 条结构化 Claim，分别描述最关键的事实、趋势、驱动或反证。
- `refs`：维度总引用，兼容现有展示和历史数据。

每条 Claim 仍包含 `claim`、`claimType` 和 `refs`。不引入模型自由计算字段。

页面展示顺序：

1. 经营状态和执行摘要。
2. 核心变化。
3. 三表联动。
4. 六维深度分析。
5. 积极信号、风险与反证、拐点、后续观察。
6. 数据限制和免责声明。

## 4. 证据压缩

新增 `FinancialEvidenceSelector`，输入完整证据，输出模型使用的精简证据。完整证据仍保存在快照中并供证据抽屉查询。

选择规则：

- 全量保留 `METRIC`、`FINDING` 和 `DATA_GAP`。
- `TREND` 只保留至少两个有效时点且属于核心概念的序列，最多 24 条。
- `LINE_ITEM` 采用核心概念白名单，覆盖收入、成本、利润、费用、现金流、应收、存货、合同负债、货币资金、有息负债、流动资产负债、总资产负债和权益。
- 同一概念存在 `CURRENT_QUARTER` 与 `CURRENT_YTD` 时，Q1 去重；半年报、三季报和年报按分析口径保留必要值。
- 排除技术平衡字段、重复零值和没有业务标签的低价值字段。
- 总证据数硬上限 72，总序列化大小目标上限 24 KB；核心科目为利润表、资产负债表和现金流量表分别预留容量，再稳定裁剪。

快照保存两部分：

- `evidence`：完整、可审计证据。
- `modelEvidence`：实际发送给模型的精简证据。

输入指纹包含选择器版本，任何筛选规则变化都会产生新解读版本。

## 5. 生成协议与门禁

提示词版本升级为 `financial-interpret-v4`，算法版本升级为 `financial-analysis-v4`，证据选择器版本为 `financial-evidence-selector-v2`。

数量约束：

- 执行摘要 3 条。
- 核心变化 2 至 3 条，证据不足时允许空数组。
- 三表联动 1 至 3 条，证据不足时允许空数组。
- 每个维度 1 至 2 条详情。
- 积极信号和风险各不超过 3 条；拐点和观察项各不超过 2 条。
- 单条 Claim 不超过 80 个中文字符，维度摘要不超过 60 个中文字符。
- 页面通过证据引用展示精确数值；正文优先解释方向、关系和经营含义，禁止模型自算比率、倍数、天数与预测值。

门禁新增：

- 校验新增数组和维度详情的引用、数字和禁止表达。
- 使用趋势词时必须至少引用一个 `TREND`，或引用明确的同比/变化指标。
- 使用跨表结论时必须引用至少两种不同证据类型或两个不同报表域。
- `FACT` 只能描述证据直接包含的事实；原因和影响必须标为 `INFERENCE`。
- 限制输出总长度，避免模型用冗余文字拖慢生成。

首次输出失败时仍只修复一次。修复请求只携带精简证据和错误摘要，不重复发送完整快照。

## 6. 速度策略

实际耗时优化顺序：

1. 将输入从约 60 KB 压缩到 24 KB 以内。
2. 单次请求同时生成所有章节，不拆成多 Agent。
3. 精简 system prompt，使用固定字段协议和明确数量上限。
4. 普通请求继续按输入指纹复用成功结果；只有“重新生成”创建新版本。
5. 记录输入字节数、证据数、输出字节数、主请求耗时和修复耗时，支持后续基准比较。

不采用原始 JSON 流式展示。未经门禁的半成品不能进入页面，且流式 JSON 无法安全渲染。页面继续展示排队、生成和校验阶段。

## 7. 兼容与失败处理

- Java 与 TypeScript 新字段使用空数组默认值，旧记录反序列化后正常展示。
- 确定性降级结果补齐新增字段，但不伪造深度内容。
- 证据筛选异常时拒绝模型调用并进入可读降级，不回退到发送全量证据。
- 新生成失败时继续展示上一份成功结果。
- 不修改现有模型 URL、密钥、模型名和全局超时配置。

## 8. 测试与验收

单元测试：

- 证据选择优先级、去重、大小上限和稳定排序。
- v2 历史 JSON 向后兼容。
- 新增章节、维度详情、数量上限和引用门禁。
- 趋势词和三表联动的证据要求。
- 修复和确定性降级。

前端测试：

- 新章节和维度详情展示。
- 空章节不产生空白大卡片。
- 历史 v2 结果仍可阅读。
- 证据标签继续打开原证据抽屉。

真实样本验收：

- 使用当前杭电股份报告做相同模型、相同网络环境的前后对照。
- 输入不超过 24 KB，模型证据不超过 72 条。
- 输出至少包含 3 条摘要、2 条核心变化、2 条三表联动和每维度至少 2 条详情，数据不足除外。
- 所有门禁错误为 0。
- 生成耗时以真实模型对照记录；若模型服务波动，则至少实现输入缩减 55%，并避免非必要的二次修复调用。
- 前端、Java 和 Python 既有全量测试全部通过。

## 9. 后续接口

下一阶段公告 PDF 解析产生的证据使用新类型 `MANAGEMENT_COMMENTARY`、`RISK_DISCLOSURE` 和 `AUDIT_OPINION`。`FinancialEvidenceSelector` 预留类型优先级，但本期不发送不存在的原文证据。

原文证据接入后，可在同一输出协议中增加“管理层解释与数字验证”，无需重新设计整个 Agent 页面。

## 10. 实测结果

2026-07-17 使用杭电股份 2026 年一季报、GLM-5 和相同模型服务进行主数据库副本压测：

- 完整快照 59,220 字节、257 条证据；实际模型输入 17,472 字节、72 条证据，输入缩减 70.5%。
- 精简证据覆盖 17 条指标、1 条规则发现、26 条趋势，以及利润表 9 条、资产负债表 10 条、现金流量表 9 条核心科目。
- 单次模型调用通过门禁，`generationMode=LLM`，耗时 40.611 秒；相比此前页面约 64 秒的修复结果缩短约 37%。
- 输出 4,898 字符，包含 3 条执行摘要、3 条核心变化、2 条三表联动、6 个固定维度和 12 条维度详情，以及积极信号、风险、拐点和观察项。
- 第一版深度协议因模型生成证据外数字触发二次调用并在 88.9 秒降级；v4 通过压缩输入、约束输出预算和禁止自算数字消除了该次二次调用。

本次真实模型耗时仍受上游模型服务波动影响，未达到设计中的 P50 目标；输入体积、单次调用成功率和页面可读深度均达到本期验收要求。后续性能优先通过模型服务能力或异步体验优化继续降低，不牺牲证据门禁。
