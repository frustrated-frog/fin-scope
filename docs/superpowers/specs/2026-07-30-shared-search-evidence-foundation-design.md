# 共享搜索证据底座设计

## 背景与目标

研究智能体和归因智能体都需要从公开互联网补充事实证据。当前两条链路直接调用 `WebSearchClient`，但分别实现 URL 去重、来源分层、相关性排序和证据映射；研究链路另外拥有正文抓取与分块能力，归因链路只能消费搜索摘要。与此同时，现有实现把公开搜索结果、运行轨迹和前端文案固定描述为 Tavily，无法在不复制业务编排的前提下增加第二个搜索来源。

本次改造建立一套供研究类任务复用的搜索证据底座：保留 Tavily 作为主要搜索来源，引入 AnySearch 作为补充来源，统一完成 Provider 选择、并发调用、故障隔离、结果融合、来源质量判断和正文获取。研究智能体与归因智能体继续负责各自的查询规划、预算、业务字段、证据持久化和报告合成。

## 非目标

- 不把归因智能体改造成研究智能体的子流程，也不统一两者的 Prompt、状态机和报告模型。
- 不用 AnySearch 替换 Tavily。
- 第一阶段不接入需要额外参数和语义验证的 `finance.*` 标签，只使用 AnySearch 的 `general.general` 搜索。
- 不在本次改造中建设通用爬虫、搜索结果缓存或面向所有外部数据源的统一 Provider 平台。
- 不把现有固定 API Key 改成环境变量，也不在文档、日志或前端输出凭据。

## 方案比较

### 方案一：组合版 WebSearchClient

在 RPC 层并发调用 Tavily 和 AnySearch，再把结果列表拼接后返回。该方案改动最少，但 RPC 层需要承担来源分层和融合策略，调用方仍会重复正文获取、URL 规范化和证据质量判断，也无法表达 Provider 部分失败等诊断信息。

### 方案二：共享搜索证据网关

RPC 层只负责供应商协议适配，Service 层提供统一搜索证据网关。网关依据搜索深度选择 Provider，并发调用后进行规范化、融合、分层、正文获取和诊断汇总。调用方只把标准证据映射到自身领域模型。该方案边界清晰，可同时服务研究与归因，并允许未来增加 Provider 而不修改业务 Agent。

### 方案三：统一到研究智能体运行时

让归因任务直接复用研究智能体的任务图和证据表。它能最大化代码表面复用，但会把归因特有的事件、赛道、立场、直接性和置信度门控强行塞入研究运行时，造成数据库和状态机耦合。

采用方案二。

## 分层与组件

### RPC：搜索供应商适配

新增 `WebSearchProvider` 合同，提供 Provider 编码、配置状态和结构化搜索方法。请求使用统一的 `WebSearchRequest`，至少包含查询词、单 Provider 最大结果数、区域和语言；结果使用 `SearchResult`，保留标题、URL、摘要或正文、来源域名、发布时间和供应商原始相关性，并增加 Provider 编码与 Provider 内排名。

现有 Tavily 实现迁移为 `WebSearchProvider`。新增 `AnySearchWebSearchProvider`，调用 `POST https://api.anysearch.com/v1/search`，第一阶段固定使用 `general.general`、`format=json`，并按照请求传入中英文语言和区域提示。AnySearch 没有相关性分数或统一发布时间时保持字段为空，不伪造分数。

所有外部调用继续位于 `finscope-rpc`。供应商客户端负责协议解析、连接与读取超时、响应大小限制和错误分类，不负责跨供应商融合或业务证据持久化。

### Service：多源搜索证据网关

新增 `SearchEvidenceGateway`，输入 `SearchEvidenceRequest`，输出 `SearchEvidenceBatch`：

- 请求包含查询词、搜索深度、每个 Provider 的结果上限、最终证据上限、正文抓取预算和截止时间。
- 批次包含标准化证据列表和 Provider 诊断列表。
- 标准证据包含规范 URL、标题、摘要、可用正文、域名、来源层级、发布时间、Provider 集合、融合分数和正文获取状态。
- Provider 诊断包含 Provider 编码、耗时、原始命中数、保留数和不含敏感响应正文的失败类型。

搜索深度策略为：

- `QUICK`：只调用 Tavily，保持低延迟和低调用成本。
- `DEEP`：并发调用 Tavily 与 AnySearch，任一 Provider 成功即可继续。
- 归因公开资料补充属于研究型任务，使用 `DEEP`，但仍受归因计划已有的查询数和总截止时间约束。

网关使用应用级有界线程池，不为每次请求创建线程池。Provider 超时不得超过批次剩余截止时间；取消或超时只影响对应 Provider。逻辑工具调用预算与供应商调用次数分别统计，避免新增 Provider 后错误消耗 Agent 的逻辑步骤预算。

### 结果融合

融合流程固定为：

1. 校验 HTTP(S) URL，并去除片段、默认端口和常见追踪参数，生成规范 URL。
2. 以规范 URL 精确去重；同一 URL 的 Provider、摘要和发布时间合并。
3. 使用 Provider 内排名做倒数排名融合，不依赖不同供应商不可比的原始分数。
4. 结合现有来源注册表生成来源层级；官方站点和一级资料优先，但不把来源层级混入供应商协议层。
5. 对单域名设置结果上限，避免同一站点占满最终证据集合。
6. 按融合分数、来源层级、发布时间和稳定顺序排序，截取最终证据上限。

Tavily 原始分数只作为同 Provider 的辅助信息。AnySearch 缺少分数不会被过滤；现有“分数为空即丢弃”的逻辑必须删除。

### 正文与分块

将现有 `research.evidence` 下只依赖搜索结果和 `ResearchSourceReader` 的正文获取、分块和排序组件迁移到通用 `search.evidence` 包，并使用与研究领域无关的命名。网关在结果融合后、最终证据截取前后按预算执行正文获取：优先为高层级和高融合分数候选获取正文，失败时保留搜索摘要，不因单篇正文失败丢弃整个搜索结果。

研究资料工具继续复用这些通用正文组件，但结构化公告、互动问答和研报 Provider 不经过公开搜索融合。

## 双智能体接入

### 研究智能体

`PublicNewsSearchTool` 改为调用 `SearchEvidenceGateway`：

- `QUICK` 研究模式只使用 Tavily。
- `DEEP` 研究模式使用 Tavily 与 AnySearch。
- 将标准证据映射并写入 `ResearchSearchEvidence`，Provider 字段记录实际贡献来源；同一证据由多个 Provider 命中时记录稳定的组合值。
- 工具摘要和轨迹使用“多源公开资料搜索”等中性文案，并展示各 Provider 命中或失败摘要。

研究任务图、分支查询生成、运行级证据去重和报告合成保持不变。

### 归因智能体

`AttributionAgent` 的公开互联网查询改为调用 `SearchEvidenceGateway`，使用标准证据的正文或摘要生成 `AttributionEvidence`。归因保留本地召回、赛道、事件、立场、直接性、相关性和置信度门控；删除其内部重复的公开搜索 URL 规范化、去重和基础来源排序逻辑。

归因计划中的逻辑查询上限保持不变。多 Provider 调用属于同一次逻辑查询，诊断信息写入 Agent 运行轨迹，但不改变现有归因报告接口。

## 配置

在现有 `finscope.search` 配置下增加独立 Provider 配置：

- Tavily：启用状态、API Key、超时和单次结果上限。
- AnySearch：启用状态、API Key、基础地址、固定标签、区域、语言、超时和单次结果上限。
- 融合：倒数排名常数、单域名上限、Provider 并发数和默认最终结果上限。

配置继续直接写入 `application.yml`。若 AnySearch 未配置或调用失败，DEEP 自动退化为 Tavily；若 Tavily 未配置但 AnySearch 可用，DEEP 仍可运行，QUICK 明确返回无可用 Provider。任何日志和异常都不得包含 Authorization 头、API Key 或供应商完整错误响应正文。

## 错误处理与安全

- 400、401、402、403 视为当前调用的终止错误，不自动重试。
- 429 可依据 `Retry-After` 在批次截止时间内有限重试；5xx 和网络瞬时错误最多有限重试一次。
- Provider 返回格式异常、超大响应、非 HTTP(S) URL 或缺失 URL 时丢弃对应结果并记录计数。
- Provider 部分失败以诊断形式返回，不终止其他 Provider；仅所有目标 Provider 均失败且没有证据时返回可解释的搜索失败。
- URL 读取继续遵循现有域名和网络安全校验，不扩大对内网地址的访问权限。

## 前端与可观测性

- 将固定的“Tavily 公开资料搜索”改成“多源公开资料搜索”。
- 证据卡片或运行轨迹显示 `TAVILY`、`ANYSEARCH` Provider 标识；两者共同命中时都显示。
- 运行轨迹展示逻辑查询数、供应商调用数、各 Provider 耗时、命中数、去重数和降级信息。
- 不向前端暴露 API Key、请求头或供应商原始错误正文。

## 兼容与迁移

数据库现有研究搜索证据已包含 Provider 字段，本次不新增数据库迁移。对外 REST 请求和报告结构保持兼容；新增诊断字段时采用可选字段。旧的单一 `WebSearchClient` 注入点在所有消费者迁移后删除，避免新旧链路长期并存。

## 实施顺序

1. 用契约测试引入统一请求、Provider 合同和 AnySearch 适配器，并迁移 Tavily。
2. 用单元测试实现 URL 规范化、倒数排名融合、域名上限和部分失败隔离。
3. 通用化正文获取组件，构建 `SearchEvidenceGateway` 和配置装配。
4. 接入研究智能体，更新证据持久化、轨迹与前端文案。
5. 接入归因智能体，删除重复搜索证据处理逻辑。
6. 完成全仓回归和真实查询对比评测。

## 验收标准

- QUICK 只发起 Tavily 调用，DEEP 和归因可同时调用 Tavily 与 AnySearch。
- 任一 Provider 超时、鉴权失败或返回异常时，另一 Provider 的有效证据仍可进入报告。
- AnySearch 分数为空的有效结果不会被过滤。
- 相同规范 URL 只生成一条证据，并保留所有贡献 Provider。
- 融合结果受单域名上限约束，官方来源和高质量来源在同等排名下优先。
- 研究与归因均可使用正文获取结果，并在正文失败时回退到摘要。
- 运行轨迹和前端不再把通用搜索能力固定命名为 Tavily，并能显示 Provider 诊断。
- API Key 和供应商错误正文不出现在日志、测试快照、数据库诊断或前端响应中。
- RPC 契约测试、Service 单元与集成测试、后端全仓测试、前端测试和生产构建全部通过。
- 使用至少二十个财经查询做真实对比，记录独立 URL、独立域名、一级来源占比、重复率、失败率和延迟；多源结果相较 Tavily 单源应带来可量化的证据增量，若质量下降则通过来源层级与域名上限调优而不是直接替换主来源。
