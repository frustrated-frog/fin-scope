# 个人研究雷达第一版设计

## 1. 结论

第一版只建设一个面向个人投资初学者的“研究雷达”，将现有实时资讯、动态分类、自选股和事件能力串成一条容易理解的路径：

```text
现在发生了什么
  -> 哪几条资讯其实在说同一件事
  -> 哪些事件最值得我先看
  -> 哪些与我的自选股有关
  -> 系统为什么这样判断
  -> 下一步应该观察什么
```

本期不建设策略配置后台、Prompt 编辑器、工具编排、模型选择、推理模式、Skill 生成或运营投放能力。分析流程由系统内置，用户不需要理解 Agent、Prompt 或数据源接口。

第一版也不引入 Embedding、向量数据库或新的 Agent 框架。先用现有标题相似度、事件特征、资讯分类和来源信息形成可解释基线；基线通过人工样本评测后，再决定是否引入向量召回和 LLM 灰区判定。

## 2. 用户与成功标准

目标用户是只维护少量自选标的、没有专业信息终端使用经验的个人投资学习者。

进入页面后，用户应能在一分钟内回答四个问题：

1. 今天最值得关注的三到五个事件是什么；
2. 每个事件由哪些独立来源共同确认；
3. 哪些事件与自己的自选标的直接相关；
4. 当前判断有哪些不确定性，后续应观察什么。

第一版成功不以资讯数量衡量，而以下列行为和质量衡量：

- 同一事件的跨来源资讯不会占据多个主要卡片；
- 事件卡能明确说明排序原因，而不是只给出一个神秘分数；
- 与自选标的无关时如实显示“未发现直接关联”，不强行生成关系；
- 任一资讯源或 LLM 不可用时，页面仍能展示已有信号和确定性判断；
- 用户无需进入设置页面即可使用完整主流程。

## 3. 本期边界

### 3.1 本期包含

- 在研究雷达刷新时保存 News Wire 最近一段时间的轻量资讯信号；
- 对资讯信号做确定性跨来源事件聚合；
- 计算系统内置、可解释的研究优先级；
- 识别事件与自选标的的直接关系；
- 在 News Wire 中增加“值得关注”和“实时发生”两个阅读层级；
- 展示事件来源、归并依据、评分原因、不确定性和观察项；
- 保留来源失败、分类失败和降级状态；
- 为后续聚类评测保存人工纠错入口所需的数据关系。

### 3.2 本期不包含

- 策略管理、Prompt 管理和模型管理；
- 用户可调权重；
- 自动买卖建议、目标价和仓位建议；
- 自动向外部平台发布内容；
- 通用定时任务配置；
- 向量数据库、在线学习或复杂推荐算法；
- 将所有实时快讯自动提升为长期文章、证据或知识笔记；
- 展示模型隐式思维链或完整内部 Prompt；
- 重做独立的通用 Agent Runs 控制台。

## 4. 为什么增加雷达层，而不直接复用 EventCluster

当前 `EventCluster` 是长期研究资产，关联正式文章、证据、学习任务和内容选题。News Wire 中大量实时快讯时效短、正文薄、可能尚未确认，如果全部直接写入现有文章和事件流程，会污染长期知识库并制造大量低质量事件。

第一版增加独立的轻量雷达层：

```text
ResearchMaterial / NewsFeedItem
  -> RadarSignal（短期信号）
  -> RadarEvent（短期聚合事件）
  -> Research Radar UI

用户主动发起研究或保存
  -> 复用现有正式摄入、EventCluster、Evidence、ResearchRun
```

雷达层负责“发现和排序”，现有事件档案负责“长期研究和沉淀”。两者不能使用同一张事件表，但雷达事件需要保留可追溯的来源信号 ID，方便后续显式提升。

## 5. 数据模型

### 5.1 radar_signal

保存从 News Wire 观察到的短期信号：

| 字段 | 含义 |
| --- | --- |
| `id` | SQLite 主键 |
| `item_id` | News Feed 稳定 ID，唯一 |
| `provider_code` | Provider 编码 |
| `source_name` | 用户可读来源 |
| `source_tier` | 来源质量层级 |
| `category_code` | 已完成的动态分类，可空 |
| `title` | 标题 |
| `content` | 截断后的正文或摘要 |
| `url` | 原文 URL，可空 |
| `published_at` | 发布时间 |
| `first_seen_at` | 首次观察时间 |
| `last_seen_at` | 最近观察时间 |
| `content_hash` | 内容去重哈希 |
| `status` | `ACTIVE/EXPIRED` |

同一 `item_id` 重复出现时只更新最近观察时间、分类和可补全字段，不重复插入。默认只参与最近 48 小时的雷达计算；超过 14 天的信号可以标记过期并清理。

### 5.2 radar_event

保存当前雷达聚合结果：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `event_key` | 稳定事件键 |
| `canonical_title` | 代表标题 |
| `summary` | 确定性摘要，优先使用代表信号内容 |
| `category_code` | 主分类 |
| `status` | `ACTIVE/QUIET/EXPIRED` |
| `first_seen_at` | 首次出现 |
| `last_seen_at` | 最近出现 |
| `source_count` | 独立来源数 |
| `signal_count` | 信号数 |
| `priority_score` | 0–100 研究优先级 |
| `score_explanation` | 分项解释 JSON |
| `watchlist_relevance` | 0–100 自选相关性 |
| `watchlist_explanation` | 命中的标的及原因 JSON |
| `uncertainty` | 当前不确定性说明 |
| `next_observation` | 后续观察项 |
| `updated_at` | 最近计算时间 |

### 5.3 radar_event_signal

保存事件与信号的多对多关系，并记录归并依据：

| 字段 | 含义 |
| --- | --- |
| `event_id` | 雷达事件 ID |
| `signal_id` | 信号 ID |
| `relation_type` | `PRIMARY/SUPPORTING/RECAP` |
| `match_score` | 确定性匹配分数 |
| `match_reason` | 用户可读的归并原因 |

唯一键为 `(event_id, signal_id)`。第一版不建立榜单历史快照和升降排名，避免提前建设尚未验证的功能。

## 6. 信号采集与聚合

### 6.1 信号采集

`NewsFeedService` 继续负责从 `ResearchMaterialGateway` 获取、排序、URL 去重、分类附加和页面返回，不给现有 `/api/news` 增加新的持久化副作用。

`ResearchRadarService.refresh()` 调用 `NewsFeedService.load()` 取得当前快照，再通过 `RadarSignalService.capture(items)` 幂等保存信号并刷新雷达事件。这样旧资讯接口保持原契约，雷达的采集、聚合和降级由一个用例边界负责。

单次刷新最多读取最近 48 小时的 500 条活动信号；超过上限时优先保留最新信号。确定性聚合在请求内完成，使用进程内 `tryLock` 防止页面轮询并发触发重复计算。未拿到锁的请求直接返回最近一次成功结果，不排队等待。

保存雷达信号失败不能导致 News Wire 基础资讯丢失；错误写入日志并作为 warning 返回，页面继续展示本次已获取的实时资讯和最近一次成功的雷达事件。

### 6.2 第一版聚合算法

每次刷新只处理最近 48 小时的活动信号，按以下顺序执行：

1. URL 或稳定 item ID 相同：视为同一信号，不进入事件匹配；
2. 标题规范化结果完全相同：归入同一事件；
3. 分类不同且没有明确主体重合：直接视为不同事件；
4. 提取公司名、指数、行业、政策主体、动作和关键变量；
5. 主体冲突：拒绝归并；
6. 主体重合，并且标题/正文相似度超过高阈值：归并；
7. 相似度低于低阈值：新建事件；
8. 中间灰区第一版保守地新建事件，并记录 `AMBIGUOUS`，不调用 LLM 猜测。

事件键使用“分类 + 主体 + 动作 + 关键变量”的规范化组合。代表标题优先选择来源层级高、内容完整、发布时间早的信号，避免每次刷新时标题抖动。

一次聚合刷新在单个事务中写入事件和关系。仍在 48 小时窗口内但本轮没有新信号的事件标记为 `QUIET`；离开窗口后标记为 `EXPIRED`，不在刷新过程中物理删除，避免详情请求读到半成品或事件突然消失。

该算法需要复用现有 `FingerprintService` 和 `EventClassifier` 中的可解释信号提取思想，但不直接调用会写入长期事件表的 `EventClusterService`。

### 6.3 人工纠错数据

第一版详情中保留“不是同一事件”和“与另一事件合并”的轻量操作，但不要求首批 UI 同时实现。数据模型和服务契约必须允许后续加入：

- 拆分时记录被拒绝的信号对；
- 合并时记录被确认的事件对；
- 评测脚本使用这些样本计算 pairwise precision、recall 和误合并率；
- 只有确定性基线不足时，才在后续版本为灰区增加 Embedding 或 LLM 判断。

## 7. 研究优先级

第一版使用系统内置权重，不提供设置入口：

```text
priorityScore
  = 新意 25
  + 自选相关性 25
  + 独立来源 20
  + 来源质量 15
  + 时效 15
```

### 7.1 分项规则

- 新意：首次出现且不是历史回顾得分高；重复旧闻或无新变量得分低；
- 自选相关性：标题或正文明确命中自选标的名称、代码或已知别名；不做模糊产业链想象；
- 独立来源：不同 Provider Family 才算独立来源，同源转载不重复计分；
- 来源质量：依据已有 `sourceTier`，高质量来源提高分数，但不能单独制造高排名；
- 时效：按发布时间连续衰减，缺少发布时间时使用首次观察时间并标注不确定。

页面不只显示总分，还显示最多三个主要原因，例如：

```text
值得关注 82
· 与自选「宁德时代」直接相关
· 3 个独立来源共同报道
· 过去 35 分钟内首次出现
```

不能输出“强烈买入”“重大机会”等投资建议式标签。推荐标签限定为“优先了解、持续观察、一般关注、信息不足”。

## 8. 面向小白的解释

雷达卡片和详情围绕以下固定问题组织，不展示 Prompt、模型名或推理模式：

### 8.1 发生了什么

显示代表标题和一到两句事实摘要。摘要优先来自原始内容，不足时明确显示“当前只有标题级信息”。

### 8.2 为什么值得关注

展示研究优先级的主要分项，不让用户猜测排序规则。

### 8.3 与我有什么关系

列出明确命中的自选标的和匹配文本。没有直接命中时显示“未发现与当前自选标的的直接关系”。

### 8.4 判断依据

按来源列出被归并的信号、发布时间、来源层级和原文链接，并说明“标题相同”“主体与动作一致”等归并原因。

### 8.5 还不知道什么

使用确定性规则生成保守说明，例如：

- 目前只有一个独立来源；
- 尚未发现公司公告或一手来源；
- 只有标题，缺少可核验正文；
- 不同来源对关键数字描述不一致。

### 8.6 接下来观察什么

只给信息验证方向，例如“等待公司公告”“观察是否出现第二个独立来源”“核对后续成交与资金数据”，不生成买卖动作。

## 9. 页面设计

第一版不新增顶层导航入口，保留现有 `News Wire` 名称和实时资讯默认页。在页面内增加“实时资讯 / 研究雷达”二级切换，雷达只能增强现有资讯能力，不能替换 `/api/news`、实时快讯或要闻精华。

### 9.1 页面结构

```text
News Wire
├── 实时资讯（默认）
│   ├── 实时快讯
│   └── 要闻精华
└── 研究雷达（二级视图）
    ├── 概览：新事件数 / 与我相关 / 独立来源 / 降级状态
    ├── 分类：全部 / 与我相关 / 现有动态分类
    └── 值得关注事件 + 实时上下文
```

不单独复制 `jdt-data-hotspot` 的“各来源热榜”大卡。来源信息收敛为事件卡里的来源徽标和详情证据列表，减少初学者同时面对三套排名的认知负担。

900px 以下改为单列，先显示“值得关注”，再显示“实时发生”。

### 9.2 雷达事件卡

每张卡只展示：

- 推荐级别和更新时间；
- 代表标题与事实摘要；
- 最多三个排序原因；
- 自选关联；
- 独立来源数和信号数；
- “查看依据”动作；
- “围绕此事研究”动作。

“围绕此事研究”第一版只跳转到 Research 页面并预填研究问题，不自动发起外部搜索和模型调用，避免用户误触产生耗时任务。

### 9.3 研究依据详情

使用页面内抽屉或独立应用内详情层展示：

1. 发生了什么；
2. 为什么值得关注；
3. 与我有什么关系；
4. 来源与归并依据；
5. 不确定性；
6. 后续观察。

技术调试字段只放在折叠的“技术详情”中，包括事件键、匹配分数、内容哈希、Provider 编码和降级原因。默认不展示完整 Prompt 或模型隐式思维链。

## 10. 服务与 API

新增服务边界：

- `RadarSignalService`：幂等保存和过期短期信号；
- `RadarClusteringService`：确定性聚合并保存关系；
- `RadarPriorityService`：计算分项分数、自选关联和解释；
- `RadarRefreshCoordinator`：使用非阻塞刷新锁隔离并发轮询；
- `ResearchRadarService`：调用现有资讯服务、刷新雷达并组装页面只读模型。

推荐 API：

```http
GET /api/research-radar?category=ALL&watchlistOnly=false&limit=20
GET /api/research-radar/events/{id}
```

列表响应包括：

- `overview`：新事件数、与我相关数、来源数、warnings；
- `events`：排序后的事件卡；
- `liveItems`：现有快讯列表；
- `refreshedAt`：服务端刷新时间。

详情响应包含全部来源信号、用户可读解释和 `suggestedResearchQuestion`。前端使用现有 App 状态跳转到 Research 页面并预填该问题，不需要新增创建草稿接口。所有普通接口继续使用统一 `ApiResponse`；部分来源失败通过 `warnings` 返回，不能用空列表伪装完全成功。

News Wire 现有 `/api/news` 和分类接口暂时保留，避免一次性迁移导致回归；新页面稳定后再决定是否让 `/api/research-radar` 成为唯一组合接口。

## 11. 运行与降级

- 信号保存失败：保留当前 News Wire 响应，记录失败；
- 聚类失败：返回最近一次成功的雷达结果，并标注更新时间和降级状态；
- 自选为空：正常展示全市场事件，并引导用户添加自选，不生成虚假相关性；
- 分类尚未完成：信号仍进入“全部”，分类完成后下次重算；
- 某个来源失败：继续使用其他来源，展示来源降级提示；
- LLM 不可用：第一版主流程完全不依赖 LLM，因此不受影响；
- 数据不足：展示“信息不足”和缺失项，不生成完整故事。

## 12. 实施批次

每一批都必须独立测试、提交和推送。

### 批次一：雷达数据基础

1. 新增三张 SQLite 表、索引、Repository 和领域对象；
2. 由 `ResearchRadarService` 在雷达刷新时幂等保存 `radar_signal`；
3. 增加 48 小时活动窗口和 14 天过期策略；
4. 测试重复捕获、分类补全、过期和写入失败不阻断资讯。

### 批次二：确定性聚合与优先级

1. 提取可复用的标题规范化和事件信号逻辑；
2. 实现保守的事件聚合、稳定标题和关系保存；
3. 实现固定五因子评分；
4. 读取自选标的并生成严格的直接关联；
5. 测试同事件归并、主体冲突、灰区拆分、同源不重复计分和分数解释。

### 批次三：只读 API 与降级

1. 新增组合查询和事件详情接口；
2. 返回 overview、events、liveItems 和 warnings；
3. 增加非阻塞刷新锁和最近成功结果降级；
4. 测试并发刷新、未知分类、空自选、部分来源失败和空数据。

### 批次四：News Wire 页面升级

1. 增加雷达概览和“与我相关”筛选；
2. 增加“值得关注”事件卡；
3. 保留并压缩现有实时快讯时间线；
4. 增加研究依据详情；
5. 增加预填研究问题的跳转动作；
6. 测试轮询竞态、降级提示、响应式布局和键盘可访问性。

### 批次五：质量基线

1. 从真实资讯中整理一组应合并/不应合并样本；
2. 增加离线聚类评测；
3. 记录误合并、漏合并、重复事件率和解释完整率；
4. 基线不足时再单独设计 Embedding 与 LLM 灰区判定，不在本期顺手加入。

## 13. 测试与验收

### 13.1 后端

- 同一 URL 和 item ID 幂等；
- 同一事件的不同来源被合并；
- 同一来源转载不增加独立来源数；
- 相似标题但主体不同不会误合并；
- 灰区样本保守拆分；
- 代表标题在重复刷新后稳定；
- 优先级总分和解释分项一致；
- 自选关联只能由明确名称、代码或别名命中；
- 雷达写入或聚类失败不阻断基础资讯；
- 过期信号不参与当前排序。

### 13.2 前端

- 首屏优先展示值得关注事件；
- “与我相关”只展示有明确关联的事件；
- 卡片能看到来源数、排序原因和更新时间；
- 详情可以回溯全部来源和归并依据；
- 自动轮询不会用迟到响应覆盖当前分类；
- 部分失败保留已有内容并展示 warnings；
- 小屏幕先显示事件雷达，再显示实时快讯；
- “围绕此事研究”只预填，不自动启动任务。

### 13.3 产品验收

使用最近一个交易日的真实资讯手动验证：

1. 选取至少五组跨来源重复事件，确认主要卡片不重复；
2. 选取至少五组标题相似但主体不同的资讯，确认不会误合并；
3. 添加两个自选标的，确认直接相关事件可解释、无关事件不强行关联；
4. 关闭 LLM，确认研究雷达主流程仍可用；
5. 关闭一个资讯 Provider，确认页面明确降级而不是空白；
6. 让没有金融背景的使用者阅读前三张卡，能够复述“发生了什么、为什么重要、还缺什么”。

## 14. 后续版本的进入条件

只有满足以下条件，才进入第二版：

- 第一版真实使用中确实出现大量漏合并；
- 已建立人工确认的正负样本集；
- 可以用离线指标比较新旧算法；
- 增加复杂算法不会让主流程依赖 LLM；
- 用户仍然不需要配置策略、Prompt、模型或权重。

第二版可以评估 Embedding Top-K 候选召回和 LLM 灰区判定，但它们只能优化系统内部判断，不能变成面向用户的策略配置能力。

## 15. 生产式热点快照链路

雷达在保持现有本地 Provider、`ResearchMaterialGateway` 和 SQLite 约束的前提下，采用后台生产快照模式：

```text
现有 Provider/Gateway
  -> FETCH 批次
  -> NORMALIZE（去重、来源排名、来源权重）
  -> AGGREGATE（复用事件关系图与跨源聚合）
  -> RANK（热点分数 + 研究优先级）
  -> PERSIST（事件、信号、关系、批次步骤）
  -> 后台增强
```

页面请求不会在 HTTP 线程内抓取外部资讯。`refresh=true` 只提交一个单飞后台刷新请求，然后返回最近一次已完成快照；定时器也复用同一刷新入口。批次记录保存在 `radar_refresh_run`/`radar_refresh_step`，当前项目只有一个最新生产快照，不区分临时榜单和正式榜单。

页面“高优先级事件”仍按既有 `priority_score DESC` 展示，`hotspot_score` 作为生产热度的辅助排序键和解释字段，避免生产热度分数与用户看到的研究优先级分数产生错位。
