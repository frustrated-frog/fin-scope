# 实时资讯分类质量闭环设计

## 1. 目标

在现有 Agent 自动分类和 45 秒实时轮询基础上，增加一个轻量的分类质量闭环，使用户能够看到分类覆盖情况、理解 Agent 判断，并对低置信度结果进行人工确认或纠正。

本期完成：

- 分类标签显示当前资讯快照中的数量；
- 显示尚未完成分类的资讯数量；
- 新闻卡片展示有效分类、Agent 置信度和分类理由；
- Agent 置信度低于 `0.70` 的资讯进入“待确认”；
- 用户可以确认或修改分类，并可填写简短备注；
- 永久保留 Agent 原始分类结果，人工结果只作为有效分类覆盖层；
- 当前分类和“待确认”视图继续使用现有轮询和新资讯提示机制。

本期不实现分类目录管理后台、Agent 自主增删分类、自动 Prompt 学习、批量历史重分类和独立数据分析大盘。

## 2. 核心原则

### 2.1 原始判断不可覆盖

现有 `category_code`、`confidence`、`reason` 和 `model_name` 继续保存 Agent 原始结果。人工操作写入独立字段：

- `manual_category_code`：用户最终选择的分类；
- `manual_reason`：可选的人工备注；
- `review_status`：`AUTO_CONFIRMED`、`PENDING_REVIEW`、`CONFIRMED` 或 `CORRECTED`；
- `reviewed_at`：人工操作时间。

有效分类按以下优先级计算：

```text
manual_category_code > category_code
```

这样后续可以统计 Agent 与人工判断的差异，也能避免重新分类任务覆盖人工结论。

### 2.2 “待确认”是工作流，不是业务分类

`PENDING_REVIEW` 是前端和 API 支持的固定查询维度，不写入 `news_category`，也不提供给 Agent 选择。它只包含已成功分类且置信度低于阈值、尚未人工处理的资讯。

### 2.3 低置信度不阻断资讯

低置信度资讯仍出现在“全部”和其 Agent 业务分类中，同时也出现在“待确认”视图。分类失败或尚未完成的资讯只出现在“全部”，并计入“待分类”数量。

## 3. 数据模型与迁移

在 `news_item_classification` 增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `manual_category_code` | TEXT | 人工选择的有效分类，可空 |
| `manual_reason` | TEXT | 人工备注，可空 |
| `review_status` | TEXT | 分类复核状态 |
| `reviewed_at` | TEXT | 最近人工操作时间，可空 |

数据库初始化使用兼容现有 SQLite 文件的增量列检测。已有 `CLASSIFIED` 数据按置信度回填为 `AUTO_CONFIRMED` 或 `PENDING_REVIEW`，未完成分类的数据保持待分类状态。

Agent 完成分类时：

- 没有人工结果：根据 `0.70` 阈值更新复核状态；
- 已有人工结果：更新 Agent 原始判断，但保留人工分类和复核状态。

## 4. 后端服务与 API

### 4.1 资讯快照统计

`NewsFeedSnapshot` 增加：

- `categoryCounts`：当前去重资讯快照按有效分类统计，包含 `ALL` 和 `PENDING_REVIEW`；
- `unclassifiedCount`：当前快照中 `PENDING`、`FAILED` 或尚无分类记录的数量。

统计始终基于本次从 `ResearchMaterialGateway` 获取并完成去重后的资讯，不使用分类表全部历史记录。因此分类标签数量与用户当前能够看到的数据范围一致。

### 4.2 查询规则

`GET /api/news?category=PENDING_REVIEW&limit=100` 返回待确认资讯。

业务分类查询使用有效分类：人工纠正后，资讯从原分类移出并进入人工选择的分类。`ALL` 仍返回全部资讯。

### 4.3 人工复核

新增接口：

```http
POST /api/news/classifications/review
Content-Type: application/json

{
  "itemId": "CLS_NEWS_FLASH:12345",
  "categoryCode": "COMPANY",
  "reason": "主体是上市公司订单变化"
}
```

处理规则：

1. 校验资讯已有成功的 Agent 分类记录；
2. 校验目标分类存在且启用；
3. 始终写入 `manual_category_code`，防止后续 Agent 任务覆盖；
4. 与 Agent 原分类一致时记为 `CONFIRMED`，不一致时记为 `CORRECTED`；
5. 返回更新后的分类视图。

## 5. 前端交互

分类导航显示：

```text
全部 48  公司动态 12  行业产业 9  …  待确认 3     待分类 5
```

“待确认”使用与其他分类相同的页面结构、搜索、来源筛选、手动刷新和 45 秒轮询。

每条已分类资讯增加紧凑的分类说明栏：

- 有效分类名称；
- Agent 置信度百分比；
- Agent 分类理由；
- `待确认`、`已确认` 或 `已纠正`状态；
- “确认/修正”入口。

点击入口后展开原地复核控件，用户选择一个当前启用的业务分类、可填写备注并保存。保存成功后立即重新加载当前分类：若修改后的资讯不再属于当前视图，它会自然移出；失败时保留当前页面并显示错误 Toast。

未分类资讯显示“Agent 分类中”，不提供人工选择，避免在 Agent 尚未产生原始判断时破坏质量对照基线。

## 6. 并发与错误处理

- 人工结果优先于正在执行或后续重试的 Agent 结果；
- 自动轮询继续使用请求序号隔离迟到响应；
- 人工保存期间禁用该条资讯的保存按钮，防止重复提交；
- 分类复核失败不影响资讯浏览，也不清空当前快照；
- 分类目录加载失败时仍保留“全部”，但隐藏人工复核控件；
- Agent 失败继续沿用原有确定性降级：资讯仍可在“全部”浏览。

## 7. 测试与验收

后端覆盖：

- SQLite 旧表增量迁移和复核字段读写；
- 低置信度复核状态；
- 人工确认与纠正不覆盖 Agent 原始结果；
- 有效分类过滤、待确认过滤、分类数量和待分类数量；
- 无效资讯、未分类资讯及停用分类的请求校验；
- Controller 请求体传递和响应。

前端覆盖：

- 分类数量及待分类数量展示；
- 分类理由和置信度展示；
- 待确认标签切换后请求正确参数；
- 人工确认/修正请求和成功后的刷新；
- 保存失败时保留当前内容并提示；
- 原有分类轮询与新资讯确认行为不回归。

验收标准：

1. 用户可以看出当前资讯的分类覆盖率和各分类数量；
2. 低于 `0.70` 的结果可从“待确认”集中处理；
3. 人工操作后有效分类立即变化，Agent 原始结果仍可追溯；
4. Agent 后续执行不会覆盖人工结果；
5. 所有分类与待确认视图保持实时轮询；
6. 分类质量能力不影响研究雷达和原有实时资讯降级逻辑。
