# 雷达事件解读与页面增强设计

## 1. 目标

将研究雷达从“聚合后的新闻列表”增强为同时回答“刚发生了什么”和“最值得研究什么”的事件工作台，并为单个雷达事件提供可缓存、可审计的深度解读。

本次改动不得增加雷达首屏和自动刷新链路对 LLM、搜索或其他慢服务的同步依赖。

## 2. 明确边界

- 不修改现有资讯分类、分类 Agent、分类代码和分类复核流程。
- 不修改 `RadarEventMatchAgent`、灰区事件匹配、聚类规则或缓存语义。
- 不修改 `RadarCanonicalTitleAgent` 的职责。
- 不修改现有优先级评分公式和排序分数。
- 新增事件解读是聚类完成后的只读下游能力，不得反向改变事件分类、聚类结果、规范标题或优先级分数。
- 不生成买卖、仓位、目标价等投资建议，不展示 Prompt 或隐式思维链。

## 3. 页面结构

### 3.1 雷达主页

雷达主页移除右侧“实时发生”区域。实时新闻流继续由同级“实时资讯”页面承担，雷达页不再重复渲染 `liveItems`。

主体改为单列全宽的两个区域：

1. **最新变化**：展示最近新增或发生更新的 3–5 个事件，按 `lastSeenAt` 倒序。每项显示变化类型、时间、分类、标题和变化摘要。
2. **高优先级事件**：继续使用现有优先级分数倒序，时间只作为同分事件的次级排序条件。

自动轮询取得新快照后直接应用最新雷达数据，不再把新快照长期留在 `pendingSnapshot` 等待用户确认。为避免无提示的内容变化，页面使用轻量更新时间提示，不通过动画重排吸引注意力。

### 3.2 事件卡

事件卡保留评分、标题、摘要、自选关联、评分原因和研究入口，并补充：

- 新事件、后续进展或多源确认等变化类型；
- 证据数量和解读状态；
- 待确认事项和下一步观察；
- “查看解读”入口。

### 3.3 事件详情

桌面端使用右侧详情抽屉，窄屏使用全屏详情。详情分为：

- **事件解读**：发生了什么、新增变化、重要性、影响链、待确认项、下一步观察；
- **证据来源**：原始新闻和补充证据，展示来源、发布时间及摘要；
- **运行状态**：只展示节点、状态、耗时和降级原因。

详情打开后立即展示已有基础信息。没有深度解读时显示后台生成状态，不阻塞抽屉打开。

## 4. 异步解读架构

新增独立的 `RadarEventInterpretationService`，负责读取缓存、提交任务和查询任务状态；新增 `RadarEventInterpretationAgent`，只消费已经落库的事件、原始信号和补充证据。

数据流为：

1. 雷达列表接口按现有流程返回，不调用解读 Agent；
2. 用户打开事件详情，详情接口立即返回事件、来源、证据和现有解读状态；
3. 若当前事件版本没有可用解读，前端调用单独的生成接口；
4. 生成接口只提交后台任务并立即返回；
5. 前端仅轮询当前打开事件的详情，完成后展示解读；
6. 同一事件版本只允许一个进行中的任务；
7. 解读成功后按事件版本指纹持久化并复用。

事件版本指纹覆盖规范标题、摘要、关联信号内容指纹和补充证据指纹。事件出现新信号或新证据后，旧解读仍可读取但标记为 `STALE`，新版在后台生成完成后替换展示。

## 5. 解读输出

Agent 输出经过严格 JSON 解析和字段校验，包含：

- `factSummary`：仅陈述输入能够支持的事实；
- `newDevelopment`：相较已有事件信息新增的变化；
- `whyItMatters`：研究价值解释；
- `impactChain`：可能影响的公司、行业或宏观变量及传导关系；
- `uncertainties`：证据冲突、信息缺口和尚待确认事项；
- `nextObservations`：后续可验证的观察项；
- `evidenceRefs`：引用的原始信号或补充证据标识。

字段内容必须可追溯到输入，不允许补写输入未支持的确定性结论。

## 6. 持久化与接口

新增 `radar_event_interpretation` 表，保存：事件 ID、事件版本指纹、状态、结构化解读 JSON、错误类型、降级原因、创建时间和更新时间。事件 ID 与版本指纹构成唯一约束。

接口调整：

- 雷达列表响应增加最近变化列表，事件卡增加变化类型和解读状态；
- 事件详情响应增加当前解读及状态；
- 新增事件解读生成接口，只负责幂等提交异步任务。

现有 `/api/research-radar` 与事件详情的已有字段保持兼容。

## 7. 性能与并发护栏

- 雷达列表和刷新不得等待 LLM 或搜索。
- 事件详情初次响应不得等待解读 Agent。
- 解读使用独立、低并发执行器，不占用雷达刷新执行器。
- 同一事件版本使用进程内 `inFlight` 集合和数据库唯一约束双重去重。
- 前端只轮询当前打开且状态为 `PENDING` 或 `RUNNING` 的事件。
- Agent 使用明确超时和输出长度限制；失败只更新解读状态，不影响事件和页面刷新。
- 不因自动轮询批量创建解读任务。

## 8. 错误与降级

- 模型未配置：状态为 `UNAVAILABLE`，继续展示基础事件信息。
- 输出非法、超时或模型异常：状态为 `FAILED`，保留可重试入口。
- 事件版本在任务执行期间变化：旧版本结果可以保存，但详情优先展示与当前版本一致的记录。
- 缓存读取失败：详情仍返回原始来源与证据。
- 前端轮询失败：停止自动轮询并展示手动重试，不影响雷达列表。

## 9. 测试与验收

- 自动轮询后新事件直接进入“最新变化”，不再停留在待应用快照；
- 雷达页不再渲染右侧实时资讯；
- “最新变化”按时间倒序，“高优先级事件”仍按原评分规则排序；
- 雷达列表与事件详情初次响应均不等待 LLM；
- 同一事件版本重复提交只执行一次 Agent；
- 解读成功后可持久化、查询和复用；
- 事件版本变化后旧解读标记为过期，新版可重新生成；
- 模型异常和非法 JSON 不阻断雷达列表、事件详情或刷新；
- 资讯分类、分类 Agent、灰区匹配、聚类和评分现有测试保持通过；
- 前端生产构建和后端完整测试通过。
