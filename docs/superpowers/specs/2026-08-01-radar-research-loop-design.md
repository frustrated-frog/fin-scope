# 雷达研究闭环增强设计

## 1. 目标

将研究雷达从事件展示页增强为个人研究跟踪台，使用户能够回答四个连续问题：

1. 自上次查看后发生了什么变化；
2. 哪些事件值得持续关注，下一步要验证什么；
3. 当前判断由哪些独立证据支持，是否存在冲突；
4. 事件是否已经进入研究流程，最终形成了什么结论。

本次增强不得改变资讯分类、分类 Agent、事件匹配、聚类、规范标题和优先级评分，也不得在雷达首屏增加 LLM、搜索或其他外部调用。

## 2. 方案选择

采用“确定性研究状态层 + 现有异步解读层”的方案：

- 事件状态、阅读状态、关注关系、观察项、时间线、研究关联和提醒全部落 SQLite，并由确定性服务维护；
- 证据可信度基于已落库来源元数据和引用关系即时计算，不新增首屏 Agent；
- 现有事件解读 Agent 保持按需异步，只作为详情增强，不反向写入分类、聚类或评分；
- 前端首屏通过批量查询获得轻量摘要，复杂明细只在打开事件抽屉时读取。

不采用“为每条雷达事件自动运行新 Agent”的方案，因为它会放大延迟、失败率和成本；也不采用纯前端 `localStorage` 状态，因为研究状态需要可查询、可关联并随数据库长期保存。

## 3. 分阶段范围

### 3.1 阶段一：持续跟踪

- 事件卡支持未读、已读、关注、忽略和稍后处理；
- 打开事件详情自动标记已读；
- 雷达顶部增加“自上次查看以来”过滤，不改变原分类筛选；
- 关注事件拥有观察清单，默认从现有 `nextObservation` 生成第一项；
- 用户可新增、完成、恢复和删除观察项；
- 事件详情展示确定性时间线，包括首次进入、信号新增、多源确认、证据更新、解读完成和用户操作；
- 事件卡只展示未读、关注、观察项完成度等轻量状态。

### 3.2 阶段二：研究衔接

- “围绕此事研究”继续预填研究问题，同时创建雷达事件与后续研究运行之间的待关联上下文；
- 研究运行创建成功后，将 `research_run_id` 回写到雷达事件关联表；
- 事件详情展示关联研究的状态、问题和报告结论摘要；
- 一个事件可以关联多个研究运行，最新完成的运行作为当前结论摘要；
- 研究失败不影响事件状态，事件删除或忽略不删除研究记录。

### 3.3 阶段三：可信度与提醒

- 可信度面板展示独立来源数、来源等级分布、原始来源去重数、解读引用覆盖率和冲突提示；
- 来源域名或来源名称归一化只用于统计，不改变雷达聚类与 `sourceCount`；
- 冲突检测仅处理同一事件内可确定比较的结构化数字和相反措辞，无法确定时明确显示“未检测到可比较冲突”，不推断真假；
- 关注事件在新增信号、证据或解读版本后产生站内提醒；
- 提醒只在雷达页展示，不接入邮件、短信或系统推送；
- 每日摘要使用数据库聚合生成，不调用 LLM，展示新增事件数、关注事件变化数和待处理观察项数。

## 4. 数据模型

### `radar_event_user_state`

每个事件一行：`event_id`、`read_at`、`followed`、`disposition`（`ACTIVE|LATER|IGNORED`）、`last_viewed_fingerprint`、`updated_at`。

### `radar_event_observation`

观察项：`id`、`event_id`、`content`、`status`（`OPEN|DONE`）、`source`（`SYSTEM|USER`）、`created_at`、`completed_at`、`updated_at`。同一事件的系统默认观察项按规范化内容去重。

### `radar_event_timeline`

时间线：`id`、`event_id`、`event_fingerprint`、`event_type`、`title`、`summary`、`reference_type`、`reference_id`、`occurred_at`、`created_at`。使用事件指纹、类型和引用构成幂等键。

### `radar_event_research_link`

研究关联：`id`、`event_id`、`research_run_id`、`question_snapshot`、`created_at`，事件和研究运行唯一关联。

### `radar_event_notification`

站内提醒：`id`、`event_id`、`notification_type`、`fingerprint`、`title`、`message`、`read_at`、`created_at`，以类型和指纹去重。

## 5. 服务边界与数据流

`RadarEventWorkspaceService` 只管理用户状态、观察项和提醒；`RadarEventTimelineService` 根据已经保存的事件、信号、证据和解读记录补齐幂等时间线；`RadarEvidenceTrustService` 只读现有数据计算可信度；`RadarResearchLinkService` 管理雷达事件与研究运行的关系。

雷达列表请求流程：

1. 继续执行现有雷达加载、聚类和排序；
2. 用事件 ID 批量读取用户状态、观察项计数、未读提醒数和研究关联摘要；
3. 组装事件卡，整个过程只访问 SQLite；
4. 不在列表请求中生成时间线、不运行解读、不执行可信度深度计算。

事件详情流程：

1. 立即读取事件、信号、证据、解读和用户状态；
2. 确定性补齐时间线并返回；
3. 计算证据可信度；
4. 返回观察清单、提醒和研究关联；
5. 缺少解读时继续沿用现有异步生成与轮询。

## 6. 页面设计

雷达顶部保留现有分类，增加紧凑状态筛选：全部、未读、关注、稍后、已忽略。默认不隐藏任何事件，“已忽略”仅在主动选择时显示。

事件卡增加状态条：未读圆点、关注按钮、观察项完成度和关联研究状态。卡片主体仍以评分和事件摘要为主，避免把操作按钮堆满首屏。

详情抽屉新增四个页签：概览、时间线、观察、研究。证据可信度位于概览内；来源与 Agent 运行状态保留在概览下方。移动端使用同样的信息顺序，不增加独立页面。

雷达顶部增加一个轻量通知入口，展开后展示关注事件的变化；每日摘要作为通知列表首项，不增加新的首页请求。

## 7. 可信度规则

可信度不输出单一“真假分数”，避免制造虚假精确性，改为五个可解释指标：

- 来源独立性：归一化后独立来源数量；
- 来源层级：各 `sourceTier` 数量；
- 引用覆盖：解读 `evidenceRefs` 覆盖了多少输入信号和补充证据；
- 转载集中度：同域名或同来源占比；
- 冲突提示：可比较数字或明确相反表述的数量与文本。

所有指标都标注“仅基于当前已收集证据”，不作为优先级评分输入。

## 8. 性能护栏

- 列表新增数据必须批量查询，禁止逐事件查询；
- 列表不返回完整时间线、观察项正文、研究报告正文或证据冲突明细；
- 时间线写入只发生在详情打开或相关异步任务完成时，并使用唯一键幂等；
- 提醒由事件版本变化触发确定性写入，不启动新线程；
- 所有新表建立事件 ID、状态和时间索引；
- 页面轮询仍只轮询当前打开且解读未完成的事件。

## 9. 错误与降级

- 用户状态或提醒读取失败时，雷达事件仍正常展示；
- 时间线补齐失败时，详情仍返回原始信号和证据；
- 可信度计算遇到未知来源时归入 `UNKNOWN`，不阻断详情；
- 研究关联不存在时继续使用当前预填问题行为；
- 观察项写入失败只回滚该操作并显示错误提示；
- 已忽略事件发生新版本变化时保持忽略，但生成提醒，用户可从“已忽略”筛选中恢复。

## 10. 验收标准

- 用户可以关注事件并维护观察清单；
- 打开事件后未读状态消失，能筛选“自上次查看以来”的变化；
- 时间线按发生时间展示事件、证据、解读和用户操作；
- 研究运行创建后能从事件详情返回查看，完成后显示结论摘要；
- 可信度指标可追溯到已有信号、证据和来源元数据；
- 关注事件变化会产生幂等站内提醒和确定性每日摘要；
- 雷达列表不调用 LLM、搜索或逐事件数据库查询；
- 现有分类、匹配、聚类、规范标题和优先级测试保持不变并通过；
- 后端完整测试、前端完整测试和生产构建通过。
