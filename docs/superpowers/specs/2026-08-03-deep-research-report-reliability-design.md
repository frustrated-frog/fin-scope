# 深度研究报告结构与生成可靠性设计

> 日期：2026-08-03  
> 状态：已批准  
> 基准样本：`data/vault/research-reports/thesis-1/run-26.md`

## 1. 目标

恢复 2026-07-29 跨午夜生成的《半导体设备深度研究报告》所具备的详细阅读骨架，并修复新版结构化模型流水线从未成功落库的问题。新报告必须同时满足：结构稳定、对象特定、证据可追溯、模型可替换、局部失败不使整篇作废。

本次不是简单回滚。旧报告的证据矩阵、研究口径、论证链、反方解释、情景推演和监测清单会恢复；旧报告中低相关证据、通用填充段落和依赖运行中旧代码的偶然行为不会恢复。

## 2. 已确认根因

数据库中 2026-07-30 之后有六篇 `EVIDENCE_STRUCTURED_FALLBACK` 报告，没有任何一篇 `MODEL_STRUCTURED`、`MODEL_REPAIRED` 或 `MODEL_CLAIM_REPAIRED` 报告。失败集中在四类：

1. 蓝图要求模型一次生成包含十余个顶层字段和多层数组、对象的严格 JSON；不同模型会把数组写成字符串、对象或空值。
2. 正文要求模型一次生成 8,000–16,000 个中文字符，同时保持多个数组与蓝图等长；长 JSON 容易截断、转义失败或发生字段形态漂移。
3. 修复调用重复发送同样复杂的完整契约，没有缩小失败面，因此经常重复失败。
4. 引用审计把带引用的推理句也按可验证事实审计，语义重合不足时会误判为无支持主张，并触发整篇回退。

报告变短的直接原因是提交 `c8f3866` 同时简化了规则生成器和结构化组装器，删除了执行摘要、研究范围、证据表、核心证据链、最终认识与证据附录等章节。那篇详细半导体报告由未重启的旧进程生成，因此保留了提交前结构。

## 3. 方案选择

### 3.1 不采用：只恢复旧模板

它能恢复表格和章节，但不会修复模型成功率，也不能保证 GLM、DeepSeek 和未来模型之间的一致性。

### 3.2 不采用：继续兼容巨型 JSON

增加 Jackson coercion、更多 prompt 约束或完整重试只能追逐供应商差异。输出越长、嵌套越深，新的模型仍可能以不同方式失败。

### 3.3 采用：确定性文档合同 + 证据蓝图基线 + 模型片段增强

Java 负责证据编号、引用归属、文档章节、表格、情景和监测项的结构合同。模型只增强受控文本片段，不再决定数组形态、证据编号和 Markdown 骨架。模型返回使用可容错的分段标记协议；缺少的片段由证据基线补齐，已成功的片段继续保留。

## 4. 目标架构

```text
ResearchEvidenceSelector
  -> ResearchEvidenceDossierBuilder
  -> DeterministicReportBlueprintBuilder
       -> 永远有效的证据引用、反方、场景和监测基线
  -> ResearchReportBlueprintAgent
       -> 可选模型增强；只改文本，不改引用和集合形态
  -> DeterministicReportNarrativeBuilder
       -> 永远完整的对象特定正文基线
  -> ResearchReportNarrativeAgent
       -> 分段文本增强；缺失片段局部补齐
  -> StructuredResearchReportAssembler
       -> 唯一 Markdown 文档合同
  -> ResearchClaimAuditor + ResearchReportQualityValidator
       -> 数字事实、引用、章节、表格、反方和监测校验
  -> ResearchReportService
```

旧的 `ResearchReportGenerator` 继续作为证据不足或模型完全不可用时的入口，但它也必须通过同一套基线构建器和组装器输出相同章节，不再维护第二套精简模板。

## 5. 固定报告合同

所有新报告按以下顺序生成：

1. 标题与研究元信息
2. 核心结论
3. 关键认识
4. 执行摘要
5. 研究范围与口径
6. 关键事实与数字表
7. 发生了什么
8. 命题拆解与逐题判断
9. 核心证据链
10. 反方解释与争议
11. 机制与情景推演
12. 最终认识与未知项
13. 跟踪清单与失效条件
14. 证据附录

关键事实表固定包含证据编号、立场、时间、可验证事实、来源层级和相关性。证据附录固定包含来源、时间、立场、相关性、事实摘录、文章 ID 和原文链接。模型生成模式只改变正文质量和生成元数据，不改变章节名称或顺序。

## 6. 蓝图生成

`DeterministicReportBlueprintBuilder` 先根据证据档案生成合法蓝图：

- 方向和置信度由证据充分性、立场、来源数量和来源等级共同限定。
- 关键认识从高相关证据提炼，保留稳定 `E` 编号。
- 子问题根据对象类型和研究问题中的交易、财务、行业、政策等信号选择适用框架。
- 论证链按“事实—传导—判断—替代解释”构造，并覆盖至少一半证据。
- 存在反向证据时，最强反方必须绑定其中至少一条；没有反向证据时明确记录反方证据缺口。
- 场景和跟踪项复用蓝图中的对象特定变量，不补造基线数字。

模型蓝图增强不再输出完整 JSON。输入包含已验证蓝图与每个可编辑槽位，输出使用 `<<<DIRECT_ANSWER>>>`、`<<<KEY_INSIGHT_1>>>`、`<<<SUBQUESTION_1>>>` 等稳定标记。Java 只接收已知槽位的文本，引用集合、数组长度、key 和枚举值仍由服务端控制。

## 7. 正文生成

`DeterministicReportNarrativeBuilder` 为每个正文槽位提供证据特定基线，避免模型不可用时出现空章节。`ResearchReportNarrativeAgent` 使用同类分段标记协议生成：

- 执行摘要
- 发生了什么
- 每个子问题分析
- 每条论证链分析
- 反方分析
- 每个情景分析
- 最终认识
- 监测计划

解析器按标记独立提取片段。第一次输出缺少关键片段时，只请求缺失片段，不重新生成全部正文。修复后仍缺失的槽位保留确定性基线。只要关键片段达到覆盖门槛且最终质量校验通过，报告即为模型增强成功；局部补齐记为 `MODEL_REPAIRED`，不再把整篇改成精简 fallback。

## 8. 引用与质量控制

事实表、论证链事实和证据附录只使用证据档案原文，由 Java 生成。模型被要求只解释这些事实，不新增数字、日期、链接或证据编号。

声明审计区分事实与推理：

- 所有带数字或日期的句子继续强制审计。
- `**事实：**`、事实表和核心结论中的对象事实继续审计。
- 不含数字的解释性推理不再仅因带有引用而被误判为事实。

质量校验恢复详细报告章节，要求证据表、至少三条关键认识、至少两条证据链、实质反方、三种情景、可执行监测项和有效证据附录。证据充分时目标字符数为 8,000–16,000；证据不足时允许较短，但必须完整展示缺口，不能用通用文字填充。

## 9. 生成模式与诊断

- `MODEL_STRUCTURED`：模型关键片段完整，引用审计和质量校验一次通过。
- `MODEL_REPAIRED`：模型部分片段经过格式归一化、缺失片段定向修复或确定性局部补齐，最终通过。
- `MODEL_CLAIM_REPAIRED`：只修复了被审计拒绝的事实句，复审通过。
- `EVIDENCE_STRUCTURED_FALLBACK`：模型完全不可用或模型内容没有达到最低增强覆盖，但仍输出同一详细结构。

警告信息只记录阶段、分类、片段覆盖率和脱敏异常，不保存模型完整响应、推理内容或凭据。

## 10. 证据质量改进

搜索供应商分数不能单独让与对象无关的结果进入报告。公司命题至少要求标题、摘要或正文出现公司名称、代码或受控别名；行业命题要求命中行业核心词。来源去重继续使用规范域名，优先一手和权威来源，并限制聚合站占比。

本次只增强报告入选门槛，不改变研究工具和搜索供应商的外部接口。

## 11. 测试与验收

测试必须覆盖：

- 详细报告十四个章节和证据矩阵表。
- 模型与规则路径使用相同章节合同。
- GLM 风格的字符串数组、DeepSeek 风格的对象数组、残缺标记和空正文不会让整篇失败。
- 模型蓝图失败后仍继续正文增强，而不是立即整篇 fallback。
- 正文局部缺失只补缺失槽位。
- 反向证据被最强反方使用。
- 数字事实全部可追溯，解释性推理不会被错误拒绝。
- 低相关搜索材料不能凭供应商分数进入公司报告。
- 后端模块测试、全量后端测试、前端测试和生产构建通过。
- 使用当前 `application.yml` 的实际模型对冻结证据包完成至少一次不写数据库的烟雾验证；不输出或复制 API Key。

验收结果必须至少生成一篇通过质量门槛的 `MODEL_STRUCTURED` 或 `MODEL_REPAIRED` 报告，并确认 Markdown 包含证据表、对象特定结论、反方解释、三种情景和跟踪清单。
