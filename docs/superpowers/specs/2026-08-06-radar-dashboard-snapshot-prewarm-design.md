# 雷达与首页热点快照预热设计

## 目标

资讯抓取、雷达聚合、评分和 Agent 增强继续在既有后台链路中执行。雷达生产批次成功完成后，主动将用户常用的热点视图写入 Redis；首页榜单和雷达页优先只读这些快照，避免由第一个页面请求承担 SQLite 查询与 DTO 组装成本。

## 范围

- 预热首页金融、科技、政治三类热点榜单。
- 预热雷达页默认视图：`category=ALL`、`watchlistOnly=false`、`limit=20`、`state=ALL`。
- 保持现有雷达筛选组合的按需缓存：Redis 未命中时才读取 SQLite 并回写。
- 保持 Redis 不可用、缓存损坏或预热失败时的 SQLite 主链路回退。

不在本次范围内：将每一种雷达筛选组合全部写入 Redis、改变热点计算/分类口径、改动抓取频率或 Agent 行为。

## 架构与数据流

1. 定时抓取触发既有资讯刷新、雷达生产及 Agent 增强链路。
2. 雷达生产持久化成功后，预热服务读取已落库的雷达默认视图和三个分类榜单，序列化并写入版本化 Redis 快照。
3. 预热成功后递增 `radar` 与 `dashboard` 的视图版本，并通过既有 SSE 通知在线页面刷新。
4. 首页调用独立的热点榜单接口；雷达页调用既有雷达读取接口。两者命中时直接返回 Redis JSON。
5. Redis 不可用或缺少非预热筛选组合时，读取服务从 SQLite 装载、尝试回写缓存，并正常返回结果。

版本递增必须发生在新快照完成写入之后，避免客户端收到刷新通知后读到空缓存。旧 revision 的键继续由 TTL 自动回收。

## 接口

- 新增 `GET /api/dashboard/hotspots`：返回三个首页热点榜单；不再依赖首页汇总接口中的 `hotspotRankings` 字段。
- `GET /api/dashboard` 继续返回首页其它概览数据，不负责热点榜单。
- `GET /api/research-radar` 保持当前参数与响应契约。默认参数命中预热快照；其它组合沿用按需缓存。

前端首页并行请求首页概览和热点榜单，以免排行榜的更新或回退影响其它首页信息的返回。

## 错误处理与一致性

- 预热中的单项失败不会中断已完成的生产批次；记录日志，并让下一次读请求通过 SQLite 回填该项。
- Redis 写入失败不影响 SQLite 中的雷达事件、排行榜或页面可用性。
- 雷达生产失败时不发布新版本，继续展示最近一次完成的快照。
- 写入与读取复用既有的 JSON 序列化和版本化 key，避免增加第二套缓存协议。

## 测试

- 快照预热服务会写入默认雷达视图和三个榜单，并在完成后发布版本更新。
- 首页热点接口优先读取已预热快照；缓存未命中时回退服务层读取。
- 雷达默认视图可由预热快照直接返回；非默认筛选组合仍可按需回填。
- Redis 仓储异常时，两个接口仍通过 SQLite 返回数据。
