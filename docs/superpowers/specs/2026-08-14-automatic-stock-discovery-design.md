# 自动股票发现设计

## 1. 背景与目标

FinScope 已具备前复权日线缓存、单股多模型预测、概率校准、样本外验证、模型健康门禁、预测历史与结果结算能力。本期不建设第二套量化基座，而是在量化策略平台新增“股票发现”入口，将外部热门板块缩小后的股票池自动送入现有研究能力。

第一版目标是：每个 A 股交易日收盘后，系统无需用户操作即可获取热门板块、展开全部成分股、执行交易准入和统一量化、深度复核优势候选，并在前端直接呈现最多 5 只证据充分的最终候选。

股票发现属于研究支持功能，不执行交易，也不承诺收益。系统宁可少于 5 只，也不得为凑数降低研究门禁。

## 2. 已确认的产品约束

1. 热门板块由同花顺或东方财富的外部榜单定义，FinScope 不自创板块热度模型。
2. 默认研究行业和概念的 5 日资金流榜单，各取外部榜单中靠前板块并合并去重。
3. 数据获取、清洗、因子计算、候选排序和预测尽量在 Python 中完成；Java 负责工程编排。
4. 每日任务全自动运行。页面不把“手动刷新”作为正常工作入口。
5. 用户可用本金默认上限为 6000 元，含义是至少买入一手及预计费用不超过预算；不要求候选价格接近预算上限。
6. 预算只用于准入，不能给低价股额外加分。
7. 必须先对全部合格候选进行统一量化，再从中产生初选；不得把热门板块领涨股直接当成最终候选。
8. 初选前 10 至 15 只运行现有完整预测和模型健康复核，最终输出证据最强的最多 5 只。
9. 未通过数据质量、样本外优势或模型健康门禁的股票不得进入最终优势列表。
10. 所有榜单、成分关系、过滤原因、量化结果和最终预测均需按当时状态留痕，避免未来信息泄漏。

## 3. 系统职责边界

### 3.1 Python 市场数据与量化服务

Python 负责：

- 获取同花顺热门行业/概念榜单，失败时切换东方财富。
- 获取入选板块的成分股，并保留股票与板块的多对多关系。
- 标准化股票代码、名称、行情日期和来源信息。
- 执行预算、ST、停牌、上市时间、流动性与数据完整性准入。
- 批量读取现有前复权日线缓存，仅对缺失或过期数据增量拉取。
- 对全部合格候选执行一致的轻量因子计算和横截面标准化。
- 形成前 10 至 15 名初选，并调用现有单股预测能力完成深度复核。
- 按锁定规则形成最多 5 只最终候选及可解释的排序证据。
- 返回完整、版本化的发现报告，不直接写 Java 主库。

### 3.2 Java 工程层

Java 负责：

- 交易日收盘调度、应用启动补跑和同日任务防重。
- 通过 Kafka 解耦调度触发和长耗时执行。
- 调用 Python 的稳定 HTTP 契约，设置总超时、记录错误并有限重试。
- 维护发现批次状态，原子保存榜单快照、候选过程与最终结果。
- 仅在整批完成后切换“最新成功批次”，避免前端读取半成品。
- 对外提供最新批次、历史批次和候选详情 REST 接口。
- 发布视图版本更新，供前端自动刷新。

### 3.3 React 前端

React 负责：

- 在量化策略平台内新增排在“单股预测”之前的“股票发现”Tab。
- 默认展示最近一次成功批次和任务状态，不要求用户触发计算。
- 清楚区分外部板块热度、量化优势、模型健康和交易准入。
- 展示最终候选、优势证据、风险边界及未入选原因。
- 支持从最终候选进入既有单股预测历史与完整详情。

## 4. 自动运行流程

默认调度时间为每个工作日 15:30（Asia/Shanghai）：

```text
Java 调度器创建当日批次（唯一键：交易日 + 方案版本）
→ Kafka 发布发现请求
→ Java Listener 领取批次并标记 RUNNING
→ Java RPC 调用 Python 股票发现接口
→ Python 获取热门板块与成分股
→ Python 执行全部候选准入和轻量量化
→ Python 深度预测初选候选
→ Python 形成最多 5 只最终候选
→ Java 在一个事务中保存报告并标记 SUCCEEDED
→ 更新最新成功批次与视图版本
→ 前端自动读取新结果
```

如果 Mac 在调度时间休眠或关机，应用启动以及定时巡检会检查最近一个应完成交易日。缺少成功批次时自动补跑。第一版以工作日近似交易日，Python 报告的行情日期作为最终 `asOfDate`；后续积累交易日历后可替换判定器，不改变任务契约。

同一业务键只能有一个有效批次。重复消息必须读取现有批次并安全返回，不能重复运行和重复保存。

## 5. 数据源与降级

### 5.1 外部热度

- 首选：同花顺行业/概念资金榜。
- 备用：东方财富行业/概念 5 日资金流榜。
- 兜底：最近一次成功热门板块快照。
- 人工板块名单保留为后续可配置来源，不进入第一版主流程。

两家来源不混合成 FinScope 自定义热度分。报告必须保留来源、统计周期、原始排名、原始指标、采集时间和载荷指纹。

### 5.2 成分股与行情

- 同一来源优先获取对应板块成分；不可用时允许使用东方财富成分关系，并显式标记来源变化。
- 日线必须是完整前复权数据，沿用现有 `QFQ` 契约。
- 在线来源全部失败时允许使用未超过有效期的本地快照；过期数据只能展示为降级，不得悄悄冒充当日结果。
- 单只股票失败不终止整批任务，但必须记录失败阶段与原因。

## 6. 候选准入与计算

### 6.1 硬准入

至少满足：

- 股票代码属于沪深 A 股第一版支持范围；北交所暂不进入候选。
- 股票名称不包含 ST、*ST 或退市标记。
- 最新有效价格大于 0，且 `价格 × 100 + 预计交易费用 ≤ 预算上限`。
- 最近交易日可获得完整前复权日线。
- 不处于停牌状态，近期成交额达到最小流动性门槛。
- 上市时间满足最小历史窗口，能够完成现有样本外验证。

每个拒绝项保存结构化原因；预算、价格和预计费用按当日快照冻结。

### 6.2 全候选轻量量化

所有通过硬准入的候选使用同一时点数据计算：

- 5/20/60 日动量。
- 相对沪深 300 与行业代理的动量。
- 波动率、下行波动、最大回撤和距阶段高低点。
- 量价与流动性指标。
- 趋势一致性、极端追涨惩罚和数据质量指标。

因子在当日候选横截面内做稳健标准化。轻量优势分只用于选择深度复核对象，不作为最终预测概率。热门板块排名和预算占用率不进入该分数。

### 6.3 深度复核与最终排序

轻量量化排名前 15 名进入现有完整预测。完整预测继续使用模型竞赛、扩展窗口验证、概率校准、锁定样本、参数稳定性和模型健康门禁。

最终优势排序使用版本化、可解释的证据规则：

- 校准后上涨概率与置信区间下界。
- 相对同股买入持有的样本外优势。
- Brier Skill Score、Log Loss 和成熟预测准确率。
- 风险调整后收益、最大回撤与稳定性。
- 数据质量、模型资格状态和健康状态。
- 交易成本后的预期优势。

只有通过资格与健康门禁、且结论不是“无明显优势”或“数据不足”的候选可以进入最终列表。最终数量为 0 至 5。

## 7. 持久化模型

第一版新增三类数据：

1. `stock_discovery_run`：批次业务键、状态、预算、来源、统计日期、数量汇总、报告版本、错误和时间戳。
2. `stock_discovery_sector`：批次内热门板块原始快照，包含类别、来源、周期、原始排名和指标。
3. `stock_discovery_candidate`：批次内每只股票的板块关系、准入结果、拒绝原因、轻量分、深度排名、最终排名、预测摘要与完整解释 JSON。

数据库对业务键建立唯一约束。写入报告使用本地事务：先写板块和候选，再将批次状态切换为 `SUCCEEDED`。失败批次保留错误信息，但不能成为最新成功批次。

完整重复的行情矩阵不写入 Java 主库，继续由 Python 行情缓存维护。

## 8. API 契约

### 8.1 Python

`POST /v1/quant/stock-discoveries`

输入包含业务日期、预算、板块数量、深度复核数量、最终数量和方案版本。输出包含来源、统计日期、板块快照、全部候选的阶段结果、最终候选、警告与性能统计。

接口必须是确定性的：相同输入和相同数据指纹产生相同排序。报告中包含 `schema_version`、`policy_version` 和数据指纹。

### 8.2 Java Web

- `GET /api/quant/stock-discoveries/latest`：最新成功批次；没有成功批次时返回明确空状态。
- `GET /api/quant/stock-discoveries/runs?limit=...`：历史批次。
- `GET /api/quant/stock-discoveries/runs/{id}`：完整批次详情。
- `GET /api/quant/stock-discoveries/status`：当前运行状态和下一计划时间。

第一版不提供普通用户“开始选股”接口；重跑只作为后台恢复能力。

## 9. 页面设计

量化导航调整为：

```text
股票发现｜单股预测｜策略实验室｜策略素材库｜因子观测站｜实验档案
```

股票发现页面遵循现有深色研究终端风格，但采用更明确的信息层级：

- 顶部使用一张“每日研究摘要”主卡，展示统计日期、最终候选数、覆盖板块数、全候选数、来源和自动完成时间。
- 主卡内用自然语言给出结论，例如“2 只具备条件优势，3 只未通过最终门禁”。
- 热门板块采用横向紧凑卡片，展示原始排名、来源、周期、资金流和领涨信息。
- 最终候选采用大尺寸排行卡。突出最终名次、概率区间、模型健康、优势结论、一手成本和预算余量。
- 每张候选卡展开后展示优势证据、主要风险、样本外指标和入选路径。
- 页面下部提供“筛选漏斗”，显示板块成分总数、预算准入数、轻量量化数、深度复核数和最终数量。
- “观察池”表格列出未进入最终列表的深度复核候选及明确原因。
- 运行中或失败时，继续展示最近成功结果，并在顶部显示当前批次状态，避免半成品覆盖报告。

响应式布局在窄屏下改为单列。动效只用于数字更新、状态切换和卡片展开，并遵循 `prefers-reduced-motion`。

## 10. 性能与中间件

- Redis：任务锁、短期最新报告缓存和视图版本；丢失后可由 SQLite 重建。
- Kafka：解耦调度与长耗时执行，消费端必须幂等。
- SQLite：唯一事实源，保持短事务，不在事务中执行远程调用。
- Python 网络并发上限 6，单供应商有界限速。
- 深度预测并发上限 2，防止 NumPy/数学线程争抢 M5 CPU。
- 市场指数和共享上下文每批只加载一次。
- 行情按股票和交易日增量缓存，不重复保存。
- 全候选因子采用批量计算；第一版不引入 Spark、Flink、Ray、Celery、Qlib 在线主链路、DuckDB 或 LightGBM。

只有性能基准证明 DataFrame 处理成为瓶颈后才引入 Polars；历史数据规模明显增长后再评估 Parquet + DuckDB。

## 11. 失败恢复与可观测性

- 每个批次记录阶段：`CREATED`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`。
- 日志包含批次业务键、运行 ID、数据源、阶段、候选数和耗时，不记录密钥或完整外部载荷。
- 外部源超时、空数据和 Schema 漂移使用不同错误类型。
- Kafka 重复投递必须幂等；失败消息允许有限重试，最终失败保留批次记录。
- 单股失败以候选级错误返回；只有无法形成任何可审计股票池时才失败整批。
- 应用启动补跑最近应完成工作日，且不覆盖已有成功批次。

## 12. 测试与验收

Python：

- 固定供应商响应测试榜单和成分解析。
- 预算、ST、停牌、流动性和历史窗口准入测试。
- 横截面排序不受输入顺序影响的确定性测试。
- 热门排名和价格不进入优势分的契约测试。
- 深度门禁不足时最终候选少于 5 的测试。
- 数据源切换和候选级失败隔离测试。

Java：

- Schema 与 Repository 原子写入测试。
- 同日业务键防重和重复 Kafka 消费测试。
- 调度、启动补跑和失败状态测试。
- Python RPC 契约、超时和错误映射测试。
- Controller 最新结果、历史结果和空状态测试。
- 强制检查字段注入、完整大括号与模块依赖方向。

前端：

- 新 Tab 默认加载最新成功结果。
- 最终候选、筛选漏斗、数据来源和降级警告展示测试。
- 运行中仍保留最近成功报告的测试。
- 无最终候选与无历史批次的空状态测试。
- 生产构建和响应式视觉检查。

验收标准：用户启动现有本地服务后，无需手动刷新，系统能够在收盘调度或启动补跑后形成可审计批次；页面直接展示经过全候选量化和深度复核的最多 5 只最终候选，并且能够解释每只股票为何入选、风险是什么、数据与模型是否可信。
