# 股票发现与热点雷达故障隔离设计

## 背景与问题

股票发现和热点雷达共享同一个 Kafka 集群，但业务成功必须彼此独立。现场核对确认两者已经使用不同 topic 和消费组，且均无 Kafka 积压；本次同时无结果是两条独立故障：股票发现的热门板块数据源全部不可用，热点雷达则因同一生产批次出现重复事件身份而失败。

本次不能只更换 topic 名，也不能通过吞掉异常制造“成功”。目标是修复两个业务根因，并把共享 Kafka 上的消费、重试、死信和运行状态边界显式隔离。

## 目标

- 股票发现失败时，热点雷达刷新与热点解读继续运行。
- 热点雷达失败时，股票发现调度与量化计算继续运行。
- 两条链路分别拥有 topic、消费组、监听容器、重试策略和死信 topic。
- 热点雷达遇到同一事件身份时合并证据，不因单个重复键放弃整批结果。
- 股票发现对热门板块数据源进行有界重试，并在在线源不可用时使用有效期内快照；错误必须保留分源原因。
- 页面区分消息基础设施健康、业务批次状态、数据源状态和下一次重试时间。

## 非目标

- 不拆成两个 Kafka 集群或两个 Spring Boot 应用；本地 Mac 使用该方案成本过高。
- 不伪造热点板块，不使用过期快照冒充新数据。
- 不把业务失败转换成 Kafka 健康失败，也不让 Kafka 健康掩盖业务失败。

## 架构设计

### 消息隔离

保留现有业务 topic：

- 股票发现：`finscope.quant.stock-discovery.requested`
- 热点解读：`finscope.radar.interpretation.requested`

新增各自死信 topic：

- `finscope.quant.stock-discovery.requested.dlt`
- `finscope.radar.interpretation.requested.dlt`

Web 模块提供两个命名的 `ConcurrentKafkaListenerContainerFactory`。它们复用底层 `ConsumerFactory` 和 `KafkaTemplate`，但分别配置 `DefaultErrorHandler`、退避次数和 `DeadLetterPublishingRecoverer`。Listener 显式选择自己的 container factory，禁止落回全局默认错误处理器。

股票发现消费失败会先将批次更新为 `FAILED`，随后抛出异常触发本链路重试；重试耗尽只进入股票发现 DLT。热点解读消费失败只影响本批消息并进入热点 DLT。两者不共享消费组、重试分区或死信 topic。

### 热点雷达重复身份修复

同一批次内多个聚类可能解析成同一个稳定事件键。当前持久化前检测到重复键会抛异常，导致整批失败。新行为是在排名完成后、持久化之前按事件键归并：

- 第一个聚类保留排名事件对象。
- 后续同键聚类的 `RadarEventSignal` 关系合并并按信号 ID 去重。
- 信号数、来源数和解释基于合并后的证据重新保持一致。
- 真正无法合并的结构冲突才使热点批次失败。

这样重复身份是正常去重路径，不再是系统异常。

### 股票发现数据恢复

热门板块 provider 按优先级逐个调用，每个 provider 最多进行有界重试。每次失败记录来源、尝试次数和安全错误摘要。在线源全部失败后，只读取四天有效期内的本地快照；没有快照时返回包含全部来源原因的业务错误。

失败批次允许调度器在固定恢复周期内重新发布，不需要修改业务日期或手工刷新。数据库唯一运行键继续保证同一业务日只有一个批次；attempt token 保证迟到执行者不能覆盖新尝试。

### 状态与可观测性

股票发现状态响应增加：业务错误、是否等待重试、下一次恢复时间和数据源诊断。Kafka 健康单独来自 Actuator/Kafka 指标，不从股票批次状态推导。热点雷达仍读取自己的 `radar_refresh_run`，不读取股票发现表。

## 测试设计

- Python：主源第一次失败第二次成功、主备源全部失败后使用有效快照、无快照时错误包含各来源。
- Java Service：失败批次能够再次调度；业务失败持久化且继续向监听器抛出。
- Kafka Web：两个 Listener 绑定不同 container factory；两个 factory 的 DLT topic 不同。
- 热点雷达：两个聚类产生相同事件键时只持久化一个事件且关系完整。
- 故障隔离：股票消费抛异常不调用或停止热点 listener；热点消费异常不改变股票批次。

## 验收标准

1. Kafka 三个业务 topic 消费组独立，股票与热点 DLT 独立。
2. 注入股票 provider 失败后，热点雷达刷新测试仍成功。
3. 注入热点重复身份后，股票发现测试仍成功，热点批次也不再因重复键失败。
4. Python、相关 Maven 模块和前端测试通过。
5. 页面能够明确显示“Kafka 正常但业务计算失败”，不得只显示空白。
