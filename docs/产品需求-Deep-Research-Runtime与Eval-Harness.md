# Deep Research Runtime + Eval Harness 产品需求

## 1. 背景

FinScope 已具备研究命题、来源规划、抓取、事件归并、证据抽取、报告生成和 Agent trace，但当前研究运行仍是一次性的固定流水线：进程中断后不能从精确节点恢复，运行预算与终止原因不够清晰，研究质量也只能依靠人工阅读判断。

本次建设把“能运行的研究流程”升级为“可恢复、可约束、可评测的研究智能体系统”。它既服务个人投资研究，也要形成秋招项目中可被深入追问的 Agent 工程能力。

## 2. 产品目标

- 每次研究运行都有持久化的 runtime checkpoint，进程重启或节点失败后可以安全恢复。
- 研究循环受最大轮次、最大动作数、重复动作和无进展阈值约束，不会无限搜索或盲目重试。
- 每个节点都产生顺序稳定的 runtime event，能够解释“执行了什么、为什么停止、状态是否前进”。
- 用户可以对真实研究运行发起离线评测，获得可重复的总分、分项指标、质量门禁结果和改进建议。
- 评测不依赖在线模型和外部网络，避免模型波动与数据源波动污染回归结果。

## 3. 用户故事

### 3.1 可恢复研究

作为研究者，我希望研究任务失败或应用重启后可以从最近 checkpoint 继续，而不是重复抓取和重新生成全部结果。

验收标准：

- 运行详情能看到当前阶段、节点、checkpoint 版本、已消耗动作数和终止原因。
- 对可恢复状态调用 resume 后，只执行尚未完成的节点。
- 重复 resume 请求不能创建并行执行，也不能重复消费已完成节点。

### 3.2 受约束的深度研究循环

作为研究者，我希望系统在证据不足时自动扩展查询，但在没有进展、动作重复或达到预算时可靠停止。

验收标准：

- 证据不足时最多执行三轮查询扩展。
- 相同动作指纹达到阈值时停止重复调用。
- 连续两轮没有新增证据或独立来源时触发 `NO_PROGRESS` 终止。
- 达到动作预算时触发 `BUDGET_EXHAUSTED`，并保留已有部分结果。

### 3.3 研究运行评测

作为项目维护者，我希望对任意一次真实研究运行执行同一套规则评测，以比较版本变化是否真正提升质量。

验收标准：

- 评测返回 0–100 总分与 `PASS` / `BLOCK` 质量门禁。
- 至少包含完成度、证据充分性、来源多样性、trace 完整性、预算安全、恢复能力六个指标。
- 指标包含分值、权重、判定依据和可操作建议。
- 同一份运行数据和同一评测器版本必须得到相同结果。
- 历次评测结果持久化，可从研究运行详情回看。

## 4. 非目标

- 不引入 Python、LangGraph、消息队列或新的数据库。
- 不实现开放域通用 ReAct Agent；本期聚焦投资研究这一有明确状态与质量约束的领域。
- 不用 LLM-as-a-Judge 作为唯一评测依据；本期以确定性规则评测为主。
- 不实现多人协作审批或复杂权限体系。

## 5. 核心指标与门禁

| 指标 | 权重 | 满分条件 |
|---|---:|---|
| 运行完成度 | 20 | 运行进入可接受终态且报告可用 |
| 证据充分性 | 25 | 有效证据达到 3 条，且报告引用与运行证据一致 |
| 来源多样性 | 15 | 至少 2 个独立来源 |
| Trace 完整性 | 20 | 必经节点有有序事件，状态转换合法，无悬空 RUNNING 节点 |
| 预算安全 | 10 | 动作、轮次均未越界，终止原因与预算状态一致 |
| 恢复能力 | 10 | 无需恢复时得基础分；发生恢复时版本递增且最终收敛 |

总分不低于 80 且不存在严重问题时通过质量门禁。严重问题包括越过预算继续执行、事件序号冲突、报告不存在却标记完成、checkpoint 状态与研究运行状态矛盾。

## 6. 交互要求

- Research 运行详情增加 Runtime 区域，展示当前阶段、checkpoint、动作预算和最近事件。
- 终态运行提供“运行评测”按钮；执行后直接显示总分、门禁、六项指标和问题建议。
- 可恢复的失败/中断运行提供“从断点继续”按钮。
- 运行和评测接口失败时保留现有详情，不清空用户已经看到的结果。

## 7. 面试价值

该功能应能清晰回答以下问题：

- 为什么选择确定性状态机与受约束动态循环的混合架构？
- 如何设计 checkpoint、幂等恢复与乐观并发控制？
- 如何识别 Agent 的重复动作和无进展循环？
- 如何建立不依赖模型随机性的离线 Eval Harness？
- 为什么 Agent trace 不是日志堆积，而是可执行的质量证据？
