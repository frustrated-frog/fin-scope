# 研究智能体决策内核 PRD

> 产品：FinScope
> 版本：V1.0
> 日期：2026-07-27
> 状态：进入开发

## 一、背景

FinScope 已具备研究命题、动态任务图、证据缺口、运行时断点恢复、研究报告和轨迹评测。当前流程的主要不足不是可靠性，而是 Agent 决策能力：规划 Agent 只在运行开始时生成一次任务图，Java 编排器随后按固定顺序执行基线扫描、公开搜索、证据评估和报告生成。后续动作没有真正消费上一轮工具返回的 Observation，也不能根据新证据局部调整研究计划。

本期在现有 Deep Research Runtime 之上增加研究智能体决策内核，使研究过程从“LLM 生成计划 + 固定工作流执行”升级为“计划引导 + 观察驱动决策 + 局部重规划”。

## 二、产品目标

### 2.1 核心目标

1. 每个研究动作都由最新研究状态、证据缺口和历史 Observation 共同驱动。
2. Agent 能在受控工具集合中动态选择下一步动作，并生成经过 Schema 和策略校验的参数。
3. 工具返回结果被标准化为 Observation，写入持久化状态，并进入下一轮模型上下文。
4. 当动作失败、连续无进展、证据方向失衡或完成条件被拒绝时，Agent 能局部修改后续计划，而不是重建整张任务图。
5. 长任务可从数据库恢复工作记忆、动作预算和未完成子目标。
6. 用户能在研究页理解 Agent 当前目标、为什么选择某个工具、得到了什么新信息、是否发生重规划。
7. 评测从最终报告质量扩展到决策轨迹质量。

### 2.2 非目标

- 本期不实现多 Agent 协作、角色聊天或 Agent 间消息协议。
- 不开放 Shell、SQL、任意 HTTP、任意文件读写等高风险工具。
- 不保存或展示模型的隐式思维链，只保存面向审计的简短决策摘要。
- 不引入 LangGraph、AutoGen 等新框架；继续使用 Java 原生领域模型和现有 Runtime。
- 不建设向量数据库。语义记忆先复用研究报告、证据和 Vault 的现有数据。
- 研究结果仍是辅助判断材料，不自动执行投资交易。

## 三、目标用户与核心场景

目标用户是需要持续跟踪投资命题的个人研究者，也包括用于秋招项目展示的技术面试场景。

典型场景：用户提出“AI 资本开支是否继续支撑光模块需求”。Agent 先读取已有来源和证据，发现支持证据较多但缺少反方材料，于是选择反方新闻搜索；搜索结果没有带来新来源后，Agent 不机械重复相同查询，而是局部重规划为寻找公司公告或产业数据；满足正反证据和独立来源门槛后，Agent 请求完成，Finish Verifier 决定是否允许进入报告生成。

## 四、核心体验

### 4.1 启动研究

用户仍从研究命题发起运行。系统创建 Mission、Runtime Checkpoint 和 Agent State，先执行配置来源基线扫描，再进入观察驱动决策循环。

### 4.2 决策循环

每一轮只允许一个明确决策：

- `TOOL_CALL`：调用一个白名单工具；
- `PLAN_PATCH`：增加、替换或跳过局部任务；
- `FINISH`：提交完成请求，由服务端验证；
- `ABORT`：在不可恢复错误或预算耗尽时终止。

每个决策包含当前子目标、工具和参数、目标证据缺口、预期 Observation、决策摘要和置信度。服务端校验通过后才执行。

### 4.3 Observation 与记忆

每次工具执行都生成结构化 Observation：状态、新增信息摘要、证据增量、来源增量、数据引用、错误类型及是否可重试。State Reducer 将它写入当前工作记忆，并生成下一轮所需的紧凑上下文。

上下文优先保留：当前目标、活动子目标、证据缺口、最近有效 Observation、失败动作、剩余预算和可用工具。较早轨迹压缩为摘要，避免上下文无限增长。

### 4.4 局部重规划

以下信号触发 Agent 考虑 `PLAN_PATCH`：

- 相同动作指纹已经执行；
- 连续两次动作没有新增证据或独立来源；
- 工具不可用或参数连续被拒绝；
- 最新证据使原有子目标失效；
- Finish Verifier 拒绝完成并返回明确缺口。

重规划只修改未开始或已失败的局部任务，已完成任务和历史 Observation 不被重写。

### 4.5 研究过程可视化

研究页在现有“研究作战图”与运行诊断之间增加“Agent 决策流”：

- 顶部显示当前子目标、循环轮次、剩余动作和工作记忆摘要；
- 时间线展示决策类型、工具、决策摘要、预期结果；
- Observation 紧随对应决策，展示实际结果和证据/来源增量；
- 计划变更显示版本号和修改范围；
- 模型降级、校验拒绝、无进展与 Finish 拒绝拥有明确状态；
- 刷新页面后从服务端状态恢复，不使用伪进度。

## 五、功能需求

### 5.1 决策生成与校验

1. 模型输出必须是严格 JSON，未知字段、重复字段和尾随内容均拒绝。
2. `decisionType`、工具编码、参数字段、字符串长度和置信度范围必须校验。
3. 工具参数使用每个工具独立 Schema；禁止模型传入 URL、类名、SQL、Shell 或文件路径。
4. 模型不可用或输出被拒绝时，确定性策略根据 Evidence Gap 和动作历史选择安全动作。
5. 每次拒绝和降级都形成可查询的决策记录。

### 5.2 动态工具

V1 提供以下能力：

- `public_news_search`：按自然语言查询抓取公开新闻并进入现有摄入管道；
- `evidence_assess`：重新计算证据数量、独立来源、支持/反方分布和缺口；
- `source_scan`：保留为基线扫描能力，由外层 Runtime 执行；
- `report_synthesis`：只在 Finish Verifier 通过后由外层 Runtime 执行。

其中 Agent 循环可自主选择 `public_news_search` 与 `evidence_assess`。基线扫描和最终报告由服务端生命周期控制，避免模型绕过执行契约。

### 5.3 工作记忆

工作记忆至少包含：

- 当前子目标；
- 紧凑计划摘要；
- 最近 Observation 摘要；
- 已尝试动作指纹；
- 连续无进展次数；
- 最近失败与 Finish 拒绝原因；
- 证据状态摘要；
- 决策次数、重规划次数和剩余预算。

### 5.4 恢复与终止

1. Agent State、Decision 和 Observation 必须持久化。
2. Runtime Checkpoint 继续拥有动作预算、重复动作、防空转和恢复控制权。
3. 恢复后不得重复已经完成的工具动作。
4. 硬预算、重复动作阈值、停滞阈值或不可恢复错误触发明确终止。
5. Finish Verifier 必须检查 Evidence Gate、报告前置条件和任务一致性。

### 5.5 轨迹评测

新增以下过程指标：

- 决策 Schema 有效率；
- Observation 被后续决策引用的比例；
- 重复动作率；
- 无进展动作率；
- 局部重规划有效率；
- Finish 首次通过率；
- 降级决策比例。

指标与现有报告质量指标同时展示，但不把模型置信度直接当作质量分数。

## 六、验收标准

1. 下一动作不能由 Java 固定循环预先确定，必须由 Decision Agent 或可解释的确定性降级策略产生。
2. 第二轮及之后的模型输入明确包含上一轮 Observation 和更新后的 Evidence Gap。
3. 至少两个可选决策动作在同一状态机内可被动态选择。
4. 非法工具、非法参数、重复动作和超预算动作不会执行。
5. 连续无进展时可以产生并持久化局部计划变更。
6. 进程重启或手动恢复后继续同一轮次和工作记忆，不重复完成动作。
7. 完成请求必须经过独立 Finish Verifier，证据不足时返回缺口并继续循环。
8. 运行详情 API 返回 Agent State、Decision、Observation 和轨迹指标，旧运行保持兼容。
9. 研究页能展示真实决策流、Observation、重规划和剩余预算。
10. 后端模块测试、前端测试和生产构建通过。

## 七、秋招展示价值

本期实现应能用真实代码回答：

- ReAct 与 Plan-and-Execute 如何组合，而不是二选一？
- Observation 如何进入下一轮上下文并改变工具选择？
- 如何做动态工具 Schema、策略校验和确定性降级？
- 如何检测重复动作、无进展与循环震荡？
- 如何在不暴露思维链的前提下保留可审计决策轨迹？
- 长任务如何保存工作记忆、恢复断点并保证幂等？
- 为什么局部 Replan 比每轮重建整张 DAG 更稳定？
- 如何对 Agent 过程而不只是最终答案做评测？
