# 产品需求：统一采集与网页抓取能力

## 1. Problem Statement

FinScope 的价值依赖持续、稳定地获取外部金融事实和研究材料。当前行情链路已经具备多 Provider、熔断、快照和质量状态，但普通网页、RSS、X 以及若干公开行情端点仍各自创建 HTTP 连接，各自处理超时、请求头、字符集和错误。结果是同一种网络故障会在不同 Adapter 中表现为不同异常，新站点接入成本高，失败后也缺少可重放的原始证据。

用户不要求秒级行情，但要求数据稳定、可靠、时间语义真实；同时希望系统能够处理公开静态网页、动态渲染网页、公开 JSON API、RSS/XML、分页列表和详情页面，并允许配置已有 Cookie。验证码破解、账号自动登录和主动绕过站点风控不属于产品能力。

## 2. Solution

建设一个统一采集运行时，使网页、RSS、公开 API、X 和行情 Provider 的底层请求自动获得统一的截止时间、有限重试、响应大小限制、字符集识别、重定向、Cookie、域名级节流、错误分类和尝试记录。

网页采集采用逐级升级策略：优先静态 HTTP，其次解析页面内嵌结构化数据或公开 API，仍无法获得有效正文时才使用可选浏览器渲染。每次有效或失败的采集都形成有界原始快照，解析与入库从快照继续执行，从而支持离线重放、Schema 漂移诊断和抽取规则回归。

行情继续由 Java `MarketDataGateway` 作为唯一控制面。Python 行情进程作为 Provider 能力提供方，不与 Java 重复执行同一级路由、重试、熔断和快照决策。

## 3. User Stories

1. 作为个人投资研究者，我希望行情主源失败时系统自动切换备用源，以便继续获得可信数据。
2. 作为个人投资研究者，我希望行情明确展示采集时间和质量状态，以便知道数据是否新鲜。
3. 作为个人投资研究者，我希望系统在免费端点限流或超时时返回最后一次合格快照，而不是空白页面。
4. 作为个人投资研究者，我希望刷新在总时间预算内结束，以便单个慢 Provider 不拖垮整个页面。
5. 作为个人投资研究者，我希望系统能抓取公开静态文章页面，以便建立稳定的信息输入渠道。
6. 作为个人投资研究者，我希望系统能识别页面中的 JSON-LD、Next.js 数据和其他内嵌 JSON，以便处理正文不直接存在于 DOM 的页面。
7. 作为个人投资研究者，我希望系统优先调用公开数据 API，以便减少对易变 CSS 选择器的依赖。
8. 作为个人投资研究者，我希望必要时使用浏览器渲染公开动态页面，以便获取 JavaScript 加载后的正文。
9. 作为个人投资研究者，我希望列表页发现与详情正文抓取分离，以便某一篇详情失败时不丢失整个列表结果。
10. 作为个人投资研究者，我希望 RSS、Atom 和 XML 的中文内容不会乱码，以便直接阅读和沉淀。
11. 作为个人投资研究者，我希望可以为合法访问的公开页面配置 Cookie，以便读取需要同意状态或已有会话的内容。
12. 作为个人投资研究者，我希望抓取失败显示明确类别，例如超时、限流、响应过大、空壳页或 Schema 漂移，以便判断如何处理。
13. 作为维护者，我希望新增站点 Adapter 时只实现请求差异和解析规则，以便复用统一稳定性能力。
14. 作为维护者，我希望能够用历史原始响应重放解析，以便站点暂时不可用时仍能修复抽取规则。
15. 作为维护者，我希望敏感 Header 和 Cookie 不进入日志或原始快照，以便降低凭据泄露风险。
16. 作为维护者，我希望每次请求都有状态码、耗时、响应大小、内容哈希和错误类型，以便计算成功率和定位故障。
17. 作为维护者，我希望域名级限速和并发隔离，以便一个站点的失败不影响其他来源。
18. 作为维护者，我希望仅对幂等请求和明确可恢复错误进行有限重试，以便避免请求放大。
19. 作为维护者，我希望浏览器渲染是昂贵的末级能力且有独立容量限制，以便普通抓取保持轻量。
20. 作为维护者，我希望所有自动化测试都使用本地固定响应或历史快照，以便测试不依赖真实外网。

## 4. Implementation Decisions

- 新增深 Module `AcquisitionRuntime`，其 Interface 只暴露一次有策略的采集请求和结构化响应；传输、重试、解码、响应上限、Cookie、重定向、节流和尝试信息属于其 Implementation。
- `SourceAdapter` 保持“外部内容转为 `RawItem`”的职责，不承担通用 HTTP 治理。
- 采集请求配置分为全局默认、能力策略和站点覆盖三层；站点覆盖只能收紧安全限制或提供合法请求参数，不能关闭响应上限和审计。
- 支持 GET 和 JSON/表单 POST，但默认仅自动重试 GET；POST 必须显式声明幂等才允许重试。
- 错误使用稳定英文标识，包括 `TIMEOUT`、`HTTP_RATE_LIMITED`、`HTTP_SERVER_ERROR`、`RESPONSE_TOO_LARGE`、`EMPTY_RESPONSE`、`UNSUPPORTED_CONTENT`、`RENDER_REQUIRED`、`SCHEMA_DRIFT` 和 `BLOCKED_BY_POLICY`，面向用户的解释使用中文。
- 原始快照保存请求 URL、最终 URL、状态码、非敏感响应头、内容类型、字符集、字节数、SHA-256、截断标志、采集时间、策略版本和正文文件路径；Cookie、Authorization 和代理凭据永不持久化。
- 大响应正文写入 `data/raw/`，SQLite 只保存元数据和相对路径；正文大小受策略限制。
- 网页策略按 `STATIC_HTML -> EMBEDDED_DATA -> PUBLIC_API -> BROWSER` 升级；成功标准是获得满足最小正文质量的内容，不以 HTTP 200 作为唯一成功条件。
- 列表发现和详情抓取拆为独立步骤；一期使用有界并发，后续可演进为持久化详情任务。
- 浏览器渲染默认关闭，仅在静态结果被判定为 JavaScript 空壳页且站点策略允许时触发；使用独立超时、响应上限和并发配额。
- Java `MarketDataGateway` 保留行情路由与可靠性策略所有权；统一采集运行时为 Provider 提供一次有界传输，不复制 Provider 路由。
- 不照搬 op-jsoup 的 ES 状态队列、MQ 或信任全部 TLS 证书方案；复用其字符集、响应限制、配置快照、规则优先和失败恢复经验。

## 5. Testing Decisions

- 测试只验证 Module Interface 的外部行为，不锁定私有实现。
- 使用 JDK 本地 `HttpServer` 覆盖重试、429/5xx、超时、重定向、GB18030、BOM、响应过大和空响应。
- 使用固定 HTML/JSON/XML Fixture 覆盖静态正文、JSON-LD、Next.js 数据、RSS、列表发现和动态空壳识别。
- 使用临时 SQLite 和临时数据目录验证快照元数据、正文文件、敏感 Header 脱敏和重放。
- 复用现有 `WebSourceAdapterTest`、`WebListSourceAdapterTest`、`RssSourceAdapterTest`、`ProviderRequestGuardTest` 和 `MarketDataGatewayReliabilityTest` 的测试模式。
- 浏览器测试使用本地动态页面并单独标记，不把浏览器下载或真实外网作为默认单元测试前提。
- 每次迁移一个 Adapter 时，先运行其定向测试，再运行 `finscope-rpc` 和 `finscope-service` 模块测试；最终运行完整后端与 Python 测试。

## 6. Out of Scope

- 验证码识别、滑块破解、设备指纹伪造和主动绕过网站风控。
- 自动登录账号、托管用户名密码或刷新第三方登录令牌。
- 付费行情、交易所直连、Level-2 或毫秒级实时数据。
- 用浏览器替代所有 HTTP 请求。
- 将 Elasticsearch 或消息队列引入当前本地优先架构。
- 在本期改变文章去重、Insight Card、Topic 或 Brief 的业务语义。

## 7. Further Notes

- 免费公开数据源没有可承诺的外部 SLA；FinScope 的可靠性来自多源、严格验证、有限重试、快照降级和可计算审计。
- robots、站点条款和访问频率应由使用者遵守；系统提供域名级限速与停用能力，不承诺任何站点都可被抓取。
- 第一阶段先提高所有现有 HTTP/RSS Adapter 的稳定性；浏览器能力在统一运行时和快照建立后接入，避免形成新的旁路。
