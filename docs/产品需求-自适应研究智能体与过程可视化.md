# 自适应研究智能体与过程可视化产品需求

> 文档状态：待实现  
> 版本：V1.0  
> 日期：2026-07-26  
> 适用范围：Research 工作台、Deep Research Runtime、Agent Runs

## 一、背景

FinScope 已经具备研究命题、来源规划、文章抓取、事件归并、证据抽取、研究报告、可恢复 Runtime 和确定性 Eval Harness。现有系统能够可靠执行一条研究流水线，但研究计划主要由服务端预先写死：面对不同命题，系统还不能显式说明“为什么拆成这些子问题、为什么选择这些工具、当前缺少哪类证据、下一步为何改变计划”。

本期把固定研究流水线升级为领域约束下的自适应研究智能体。Agent 负责生成受控研究合同和任务图，服务端负责校验、执行、预算、恢复和证据门禁；前端将整个过程呈现为可理解、可追踪的“研究作战图”。

## 二、产品定位

自适应研究智能体不是开放式聊天机器人，也不是自动交易系统。

- 输入是一个可验证的研究命题。
- 输出是研究合同、任务图、证据缺口变化和带边界的研究报告。
- Agent 只能从注册工具中选择能力，不能自由构造 SQL、网络请求或代码。
- 所有外部动作继续受 Runtime 动作预算、重复动作和无进展门禁控制。
- 模型不可用或计划不合法时，使用确定性计划，不阻断研究流程。
- 页面展示真实持久化状态，不用前端动画伪造进度。

## 三、目标

1. 为每次命题研究建立结构化 Research Contract。
2. 将命题拆解为具备依赖关系、预期证据和工具选择的任务图。
3. 建立类型化 Research Tool Registry，集中描述工具能力和执行约束。
4. 根据真实证据数量、独立来源和正反证覆盖评估 Evidence Gap。
5. 证据不足时执行计划中的补充搜索任务；证据充分时跳过多余动作。
6. 研究运行详情实时展示合同、任务状态、工具选择、证据缺口和重规划原因。
7. 保留确定性降级、断点恢复和离线评测能力。

## 四、核心用户场景

### 4.1 启动一项可解释的研究

用户选择研究命题并启动运行后，页面首先展示：

- 本次要回答的核心问题；
- 研究范围与成功条件；
- Agent 生成还是规则生成的计划；
- 计划使用哪些工具；
- 各子任务之间的依赖关系。

用户无需等待最终报告，就能理解系统正在做什么。

### 4.2 观察研究如何推进

运行中，任务卡按 `PENDING / RUNNING / COMPLETED / SKIPPED / FAILED` 更新。正在执行的任务显示所用工具、查询意图和预期证据；完成后显示新增证据与独立来源数量。

页面每 750ms 读取一次服务端真实状态。切换运行、刷新页面或应用重启后，过程仍可恢复。

### 4.3 理解为什么继续搜索

每次证据评估保存一份 Gap Snapshot：

- 有效证据数；
- 独立来源数；
- 是否包含支持证据；
- 是否包含反方或风险证据；
- 尚未满足的条件；
- 推荐补充的证据意图。

当系统继续搜索时，页面必须展示具体缺口；当系统提前停止搜索时，必须展示“证据门槛已满足”。

### 4.4 识别 Agent 计划与确定性降级

计划来源分为：

- `LLM_VALIDATED`：模型计划通过 Schema、工具白名单和图校验；
- `DETERMINISTIC`：模型未配置、失败或输出被拒绝后使用确定性计划。

两种模式都可以完成研究，但必须在 UI 和 Agent Trace 中明确标识。

## 五、功能需求

### 5.1 Research Contract

每次运行保存：

- 核心目标；
- 研究对象；
- 研究范围；
- 成功条件；
- 最大动作数；
- 计划版本；
- 计划生成模式；
- 当前状态与活动任务。

研究合同创建后不可被模型任意扩展。运行过程中只允许在合同边界内更新任务状态和 Evidence Gap。

### 5.2 类型化工具注册表

V1 注册四类工具：

| 工具编码 | 用途 | 是否消耗外部动作预算 | 是否允许补充查询 |
|---|---|---:|---:|
| `source_scan` | 扫描配置的信息源 | 是 | 否 |
| `public_news_search` | 根据命题和证据缺口搜索公开新闻 | 是 | 是 |
| `evidence_assess` | 评估证据数量、来源和正反覆盖 | 否 | 否 |
| `report_synthesis` | 基于冻结证据生成报告 | 否 | 否 |

每个工具公开：

- 中文名称和用途；
- 输入字段；
- 输出字段；
- 超时；
- 是否只读；
- 是否允许并行；
- 风险等级；
- 预算类型。

Agent 计划引用未注册工具时，整份模型计划被拒绝并降级。

### 5.3 自适应任务图

任务包含：

- 稳定 `taskKey`；
- 标题与研究问题；
- `taskType`；
- `toolCode`；
- 证据意图 `BASELINE / SUPPORT / COUNTER / PRIMARY / ASSESS / SYNTHESIS`；
- 依赖任务；
- 并行组；
- 查询文本；
- 选择理由；
- 预期证据；
- 状态、执行摘要和增量统计。

约束：

- 一次计划最多 8 个任务；
- 补充搜索任务最多 4 个；
- 依赖图必须无环；
- 每个依赖必须指向同一计划中的任务；
- 查询文本最多 180 个字符；
- 只有白名单工具可以进入可执行计划。

### 5.4 Planning Agent

Planning Agent 输入：

- 研究命题；
- 研究对象；
- 主题范围；
- 可用工具摘要；
- 动作预算；
- 当前日期。

模型只返回 JSON。服务端完成以下校验：

- JSON Schema 形状；
- 字段长度和条数；
- 工具白名单；
- 任务键唯一；
- 依赖合法且无环；
- 必须包含 baseline、evidence assess 和 synthesis；
- 必须包含支持与反方两个研究方向。

校验失败时保存降级原因并生成确定性计划。

### 5.5 Evidence Gap Analyzer

每次初始来源扫描完成、每个补充搜索完成后执行评估。

V1 充分条件：

- 至少 6 条有效证据；
- 至少 2 个独立来源；
- 至少 1 条支持证据；
- 至少 1 条反方或风险证据。

Analyzer 返回结构化警告和推荐意图：

- 缺支持证据：`SUPPORT`；
- 缺反方证据：`COUNTER`；
- 来源不足：`PRIMARY`；
- 数量不足但方向齐全：`BREADTH`；
- 全部满足：`NONE`。

### 5.6 计划执行

- `source_scan` 复用已有来源规划和抓取流程。
- `public_news_search` 使用计划任务的查询文本生成临时 RSS Source，并继续通过 `FetchService` 入库。
- 每个任务开始、完成、跳过或失败时立即持久化。
- Evidence Gap 已满足后，尚未开始的补充搜索标记为 `SKIPPED/SUFFICIENT_EVIDENCE`。
- Runtime Guard 触发后，停止新的外部动作，但允许 Evidence Assess 和报告收尾。
- 恢复运行时，已完成任务不重复执行，未完成任务从持久化状态继续。

### 5.7 研究过程可视化

Research 运行详情新增“研究作战图”，布局包含：

1. **合同栏**：目标、范围、成功条件、计划来源和预算。
2. **任务轨道**：基线、取证、判断、合成四个阶段的任务卡。
3. **证据脉冲**：有效证据和独立来源随运行变化的进度线。
4. **缺口账本**：最近三次 Gap Snapshot 及触发的下一步。
5. **工具图例**：展示本次实际使用的工具及风险/预算属性。

视觉要求：

- 运行中的任务只有一个明确的动态焦点；
- 动画反映真实状态变化；
- 支持浅色、深色和 `prefers-reduced-motion`；
- 任务状态不能只依赖颜色表达；
- 移动端退化为纵向时间线；
- 空状态说明下一步，而不是只显示“暂无数据”。

## 六、接口需求

- `GET /api/research/tools`：读取 Research Tool Registry。
- `GET /api/research/runs/{id}/mission`：读取合同、任务、Gap Snapshot 和工具摘要。
- `GET /api/research/runs/{id}`：继续返回完整运行详情，并内嵌可选 `mission`。

现有创建、恢复、评测和报告接口保持兼容。

## 七、数据与安全

- 模型只能看到工具描述，不能获得数据库连接、API Key 或内部配置。
- 查询文本按不可信模型输出处理，禁止协议头、控制字符和超长内容。
- 临时搜索 Source 不写入用户的信息源配置表。
- 任务输出只保存摘要、计数和引用 ID，不复制完整原文。
- Agent Trace 不保存凭证和请求头。
- 新表均以 `research_run_id` 为生命周期边界，删除运行时级联删除。

## 八、非目标

- 不实现开放域 ReAct Agent。
- 不允许模型执行任意 HTTP、SQL、Shell 或文件写入。
- 不在 V1 实现多 Agent 自由辩论。
- 不引入 LangGraph、向量数据库、消息队列或新的 Python Agent 运行时。
- 不生成买卖建议、目标价或仓位。
- 不在 V1 并发执行 SQLite 写入型抓取任务；并行组用于表达依赖和后续调度能力。

## 九、验收标准

1. 命题运行能够生成合法合同和任务图。
2. LLM 未配置或返回非法计划时，确定性计划仍可完成运行。
3. 非白名单工具、循环依赖和重复任务键会被拒绝。
4. 初始扫描和补充搜索后产生 Gap Snapshot。
5. 证据充分后未开始的搜索任务被跳过。
6. 任务状态与 Runtime 事件、研究运行状态一致。
7. 刷新页面后仍能恢复同一张研究作战图。
8. 运行详情 UI 能明确展示活动任务、工具、证据缺口和计划模式。
9. 后端单元/集成测试、前端组件测试和生产构建通过。

## 十、秋招展示价值

本功能应能回答：

- 如何让 LLM 生成的计划安全进入确定性执行系统？
- 如何设计 Tool Registry、Schema 校验、工具权限和预算？
- 如何校验动态 DAG 并实现幂等恢复？
- 如何让证据缺口而不是固定轮次驱动下一步动作？
- 如何证明前端展示的是服务端真实状态，而不是伪进度？
- 为什么选择“受控自适应”而不是开放式 ReAct 或直接引入 LangGraph？
