# 产品需求：行情数据实时性与可靠性改造

## 1. 背景

FinScope 已经具备股票、指数、基金、板块、资金流和龙虎榜等行情获取能力，也已建立多源路由、熔断、本地快照和质量标记。但实际使用中仍然存在三类问题：

- 刷新失败：部分免费公开端点会限流、超时或返回不完整数据。
- 刷新缓慢：一次外部失败可能被多层重试放大，用户需等待 10–20 秒。
- 刷新不及时：页面请求同时承担“读取”与“抓取”职责，缓存策略与交易时段无关，降级结果也可能继续进入短期缓存。

本期只改造行情数据能力，不扩展到文章、研报或财报抓取。

## 2. 产品目标

### 2.1 核心目标

1. 交易时段内，页面展示的股票、指数、基金估值和板块行情的目标新鲜度为 15 秒以内。
2. 通过免费多源、并行对冲、单层可控重试和故障域隔离，显著降低真实在线刷新失败。
3. 准确区分实时数据、备用源数据、两分钟内旧数据和不可用数据，禁止把过期数据标记为实时。
4. 建立可计算的成功率、新鲜度和延迟指标，用运行数据而不是感觉验收。

### 2.2 目标指标

- 在线新鲜行情成功率：滚动 7 个交易日目标不低于 99.5%。
- 包含不超过两分钟的最后成功数据时，页面可用率目标不低于 99.9%。
- 股票、指数在线刷新 P95 不高于 2 秒。
- 基金、板块在线刷新 P95 不高于 5 秒。
- 交易时段页面读取 P95 不高于 300 毫秒。
- 超过两分钟的盘中快照不得作为可用行情返回。

免费公开数据源没有服务级别承诺，上述成功率是 FinScope 的运行目标，必须通过持续审计验证，不对免费源做虚假 SLA 承诺。

## 3. 用户场景

### 3.1 打开自选页

用户打开自选页时，应快速看到最近一次已验证行情。系统在后台维持交易时段的 10 秒刷新节奏，页面不应因单个外部源超时而长时间卡住。

### 3.2 手动刷新

用户点击“刷新行情”时，系统应启动一次受总预算限制的在线刷新。一个能力失败不影响其他能力完成，页面应显示成功、部分成功、旧数据或不可用的真实状态。

### 3.3 外部源故障

主源超时或返回缺失标的时，系统应在对冲延迟到达后启动备用源，并按标的补齐。如果全部在线源失败，只允许使用交易时段内不超过两分钟的最后成功快照，并明确标记。

## 4. 数据源策略

| 能力 | 主源 | 备用源 | 末级事实兜底 | 说明 |
| --- | --- | --- | --- | --- |
| 股票行情 | 腾讯 | 新浪 | 最后成功快照 | 两个独立域名和供应方，按标的补齐 |
| 指数行情 | 腾讯 | 新浪 | 最后成功快照 | 使用相同对冲策略 |
| 基金估值 | 东方财富估值主端点 | 备用估值域名 | 已确认净值 | 估值与确认净值分层展示 |
| 板块行情 | 东方财富目录 | 候选免费板块源 | 最后成功快照 | 候选源先影子观测，达标后才晋升 |
| 资金流 | Python 多源服务 | 东方财富直连 | 最后成功快照 | 不纳入 15 秒页面行情 SLO |
| 龙虎榜 | 东方财富 | 暂无 | 最后成功快照 | 按交易日事实刷新，不冒充实时逐笔数据 |

## 5. 准确性规则

- 校验请求代码与返回代码一致。
- 校验价格为正数，高低价、开盘价、昨收价和涨跌额关系合理。
- 校验数据时间不在未来，交易时段内超过两分钟的在线报价不得被接受为新鲜数据。
- 两个在线源同时返回时，按时间、完整度和路由优先级选择；价格偏差超阈值时不盲目覆盖最后可信数据。
- 基金盘中估值、ETF IOPV 和已确认净值是不同事实，必须保留各自时间和语义。

## 6. 交付范围

1. 单层行情路由、重试与超时预算。
2. 能力级故障域和执行容量隔离。
3. 交易时段感知的新鲜度与两分钟兜底边界。
4. 自选股票、基金、指数和板块的后台批量预热。
5. 刷新运行和 Provider 尝试级审计。
6. 与现有前端质量标记兼容的状态表达。
7. 后端、Python 行情服务和前端回归测试。

## 7. 非目标

- 不接入需付费或单独商业授权的数据源。
- 不把免费端点包装为具有官方 SLA 的服务。
- 不在本期重写全部 Python 行情服务或迁移非行情数据获取链路。
- 不提供 Level-2 逐笔委托或交易所直连行情。

## 8. 验收

- 自动化测试能稳定复现并阻止双层重试、过期数据冒充实时数据、单能力故障打开其他能力熔断和降级结果进入新鲜缓存等问题。
- 使用真实免费源进行有界验收，记录每项能力的结果状态、来源、时间和耗时。
- 完整运行 `mvn test`、`uv run pytest -q`、`npm test -- --run` 和 `npm run build`。
