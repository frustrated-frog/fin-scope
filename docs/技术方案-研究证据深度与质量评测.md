# 研究证据深度与质量评测技术方案

## 1. 架构决策

采用渐进增强现有 Java Research Runtime 的方案。`ResearchAgentLoopService`、SQLite checkpoint、决策与 Observation 事务、动作预算和确定性降级继续作为唯一控制面。LangGraph 只作为未来可能的 `ResearchOrchestrator` Adapter，不进入当前依赖和主链路。

```text
Research decision
  -> Tavily URL discovery
  -> official source policy
  -> ResearchSourceReader (HTML/PDF)
  -> ResearchEvidenceChunker
  -> ResearchEvidenceRanker
  -> run-scoped research_search_evidence
  -> evidence dossier
  -> narrative synthesis
  -> ResearchClaimAuditor
  -> at most one ResearchReportRepairAgent call
  -> quality gate + benchmark metrics
```

## 2. 模块边界

### 2.1 原文读取

在 `finscope-rpc` 增加 `ResearchSourceReader` 与默认实现，所有 HTTP 调用继续停留在 RPC 层。输出使用 domain 层的 `ResearchSourceDocument`，包含最终 URL、标题、正文、内容类型、抽取方式、字符数和读取状态。

- HTML：复用 Acquisition Runtime 的超时、大小限制和重试，使用现有正文抽取器。
- PDF：同样通过 Acquisition Runtime 下载受限字节，在 RPC 层用 PDFBox 提取文本。
- 安全：仅允许公网 HTTP/HTTPS；拒绝 localhost、loopback、link-local、site-local 和无法解析的主机。
- 降级：读取失败由 service 层转换为 `SEARCH_SNIPPET`，保留失败类型，不能写成 `FULL_TEXT`。

### 2.2 分块与召回

`ResearchEvidenceChunker` 负责清洗正文并生成有序块；`ResearchEvidenceRanker` 负责确定性排序。排序信号包括查询词、研究主体、别名、标题命中、数字密度、意图词和块位置。每个来源最多保留四个片段，合计文本受固定字符预算约束。

数据库继续使用 `research_search_evidence` 作为运行内事实源，新增：

- `search_snippet`
- `content_origin`
- `extraction_method`
- `fetch_status`
- `content_char_count`
- `fetched_at`

`content` 保存带块编号的相关原文片段，不保存无限长度全文。迁移使用 `ensureColumn`，兼容已有 SQLite 数据。

### 2.3 Claim 审计与修复

`ResearchClaimExtractor` 从 Markdown 中提取事实句、引用编号、数字、日期和因果标记。`ResearchClaimAuditor` 对照 `ResearchEvidenceDossier` 输出审计结果。

确定性规则优先：

1. 引用编号必须在白名单；
2. 数字、百分比和日期必须出现在至少一个绑定片段；
3. 主张与证据必须达到最低词项覆盖；
4. 多个绑定证据对同一数字给出不同值时标记冲突；
5. 纯观点句不伪装成事实句审计。

若存在 `PARTIAL` 或 `UNSUPPORTED`，且 LLM 已配置，则 `ResearchReportRepairAgent` 只接收问题主张、审计原因和允许引用，最多调用一次。修复结果重新审计；仍失败则由 assembler 删除无支持数字或改写为“待验证”。审计摘要写入报告质量指标。

### 2.4 Benchmark

在 `finscope-service` 增加离线 Benchmark runner，fixture 放在 `src/test/resources/research-benchmark/`。每个 case 包含冻结时间、问题、期望事实、允许来源和最小支持率。runner 不访问实时网络，使用冻结 evidence/report 输入，保证 CI 可重复。

运行期 `ResearchEvaluationScorer` 新增 grounding 指标：claim coverage、claim support、primary source ratio、freshness、counter evidence coverage。原有运行可靠性指标保留。

### 2.5 官方来源通道

`OfficialFinancialSourceRegistry` 是来源域名和查询模板的唯一事实源，初始覆盖：

- 中国证监会、上交所、深交所、北交所、巨潮资讯；
- 公司 IR 域名；
- 国家统计局、中国人民银行；
- SEC、EDGAR 与主要海外交易所。

`PRIMARY` 意图先生成受控 `site:` 查询；若无进展再走普通 Tavily。来源等级由 registry 统一输出，Selector 和 Dossier 不再各自猜测。

### 2.6 模式与编排缝

`ResearchMode` 定义 QUICK/DEEP 预算配置。`ResearchOrchestrator` 只定义“根据当前缺口生成并执行有界分支”的接口，默认 `BoundedResearchOrchestrator` 仍复用现有工具、Turn 事务和 Observation。

| 模式 | 搜索动作 | 全文读取/搜索 | 最大并发 | 最大迭代 | 修复次数 |
|---|---:|---:|---:|---:|---:|
| QUICK | 2 | 2 | 1 | 5 | 1 |
| DEEP | 6 | 3 | 3 | 10 | 1 |

DEEP 一批最多三条互补分支：`SUPPORT`、`COUNTER`、`PRIMARY` 或 `UPDATE`。并发只用于只读搜索/抓取；每个结果仍通过原有 Turn commit 边界顺序持久化，避免并发写 SQLite。

## 3. 错误与可观测性

- 每个来源记录 `FETCHED`、`SNIPPET_FALLBACK`、`UNSUPPORTED` 或 `FAILED`。
- Observation 展示命中数、全文成功数、摘要降级数、低相关数、重复数和新增来源数。
- 单个来源失败不使搜索工具整体失败；Tavily 本身失败仍按现有 retry 语义处理。
- Claim 审计记录总 Claim、已覆盖、支持、部分支持、不支持和冲突数量。
- Benchmark 版本进入 evaluator version，防止不同口径静默混用。

## 4. 测试策略

所有行为按 TDD 实现：

1. RPC 单测覆盖 HTML/PDF、大小限制、私网 URL 和抽取失败。
2. Service 单测覆盖分块、排序、降级、入库字段和不触碰文章库。
3. Claim 审计单测覆盖数字、日期、部分支持、无支持、冲突和合法观点句。
4. Repair 单测覆盖最多一次调用和引用白名单。
5. Benchmark golden cases 验证指标计算稳定。
6. 来源策略单测覆盖 PRIMARY 优先和域名分级。
7. 模式与编排单测覆盖预算、并发上限、分支互补和失败隔离。
8. 最终执行 Maven 全量测试、前端全量测试、Vite build 与真实研究运行。

## 5. 兼容与发布

- 已有运行默认按 `DEEP` 解释，不要求数据回填。
- 旧 `research_search_evidence.content` 继续可读，缺少新字段时视为 `SEARCH_SNIPPET`。
- 每个阶段独立提交并推送；若某阶段失败，可回滚单个提交而不破坏已交付能力。
- 不修改或输出 `application.yml` 中固定的本地密钥。
