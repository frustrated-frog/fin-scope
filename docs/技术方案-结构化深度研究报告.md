# 技术方案：结构化深度研究报告

> 对应 PRD：`docs/产品需求-结构化深度研究报告.md`
> 日期：2026-07-29
> 状态：已实现（2026-08-03 完成跨模型可靠性改造）

## 一、现状与根因

当前报告链路为：

```text
ResearchEvidenceSelector
  -> ResearchReportGenerator 生成规则 Markdown
  -> ResearchReportSynthesisAgent 单次模型重写
  -> 标题、长度和 URL 校验
  -> ResearchReportService 落库与写入 Vault
```

真实数据表明，最新报告长度为 6,878 字符，但 `generation_mode=DETERMINISTIC`。当前质量问题由以下技术原因共同造成：

1. `ResearchReportSynthesisAgent` 的超时固定为 20 秒，要求模型同时输出 4,000–8,000 字，长响应很容易超时。
2. 模型调用没有显式 `maxOutputTokens`，不同兼容服务的默认输出预算不可控。
3. 输入只包含标题、短 claim、立场、来源和 URL，没有发布时间、正文摘录、子问题归属、来源等级和证据关系。
4. 单次直接输出 Markdown，任何标题偏差、摘要长度偏差或 URL 尾部标点都可能导致整份结果被丢弃。
5. `catch (Exception ignored)` 静默吞掉失败，报告实体没有记录具体降级原因。
6. 规则生成器使用固定行业话术扩充篇幅，缺少按问题类型变化的事实组织和分析框架。
7. 前端把 Markdown 当作单列长文展示，没有章节导航和证据跳转。

当前采用“服务端完整论证基线 → 模型命名槽位增强 → 程序化组装和校验”的混合生成方式。章节、数组、证据编号和引用关系始终归 Java 所有，模型只增强对象特定文本。

## 二、方案选择

### 方案 A：单次大提示词生成 Markdown

优点是改动小。缺点是长输出超时、结构漂移和整份回退问题仍然存在，不采用。

### 方案 B：结构化蓝图 + 深度正文 + 程序化组装（采用）

先生成小而严格的论证蓝图，再基于已经校验的蓝图生成正文。程序负责标题、目录、引用附录和长度控制。该方案兼顾质量、稳定性、成本和可测试性。

### 方案 C：每章节独立 Agent

深度上限高，但调用次数多、失败面大、整体一致性差，暂不采用。后续若报告长度继续增长，可以在方案 B 内部按章节批次扩展。

## 三、总体架构

```text
RunScopedResearchContext
  -> ResearchEvidenceDossierBuilder
       -> 证据正文摘录、日期、来源等级、稳定 E 编号
  -> ResearchReportBlueprintAgent
       -> Java 完整蓝图 + 模型命名文本槽位增强
  -> ResearchReportBlueprintValidator
       -> 引用白名单、覆盖率、反方、对象相关性
  -> ResearchReportNarrativeAgent
       -> Java 完整正文 + 模型命名文本槽位增强
  -> StructuredResearchReportAssembler
       -> 程序化 Markdown、目录元数据、来源附录
  -> ResearchReportQualityValidator
       -> 结构、长度、引用、数字、重复度、信息密度
       -> 通过：MODEL_STRUCTURED
       -> 一次修复：MODEL_REPAIRED
       -> 失败：EVIDENCE_STRUCTURED_FALLBACK + 具体警告
  -> ResearchReportRepository + VaultWriter
  -> ResearchReportReader
```

## 四、内部数据契约

### 4.1 ResearchEvidenceDossier

不新增数据库表，先在报告生成阶段构建运行内对象：

```java
final class ResearchEvidenceDossier {
    String evidenceRef;       // E1、E2
    Long articleId;
    Long evidenceId;
    String sourceIdentity;
    String sourceName;
    String sourceTier;        // PRIMARY、AUTHORITATIVE、MEDIA、AGGREGATOR
    String title;
    String publishedAt;
    String url;
    String factExcerpt;       // 从 evidence claim、summary、body 依次提取
    String stance;
    int relevanceScore;
    List<String> subquestionKeys;
}
```

构建规则：

- 最多使用 12 条证据，优先高相关、一手、独立来源和立场平衡。
- 每条 `factExcerpt` 目标 500–900 字符，整个证据上下文不超过 14,000 字符。
- 清除导航、版权声明和重复文本，不把完整网页直接送模。
- 同源转载共享 `sourceIdentity`，但保留各自文章 ID 用于审计。
- `E` 编号在一次报告生成过程中稳定，蓝图、正文和附录共用。

### 4.2 ResearchReportBlueprint

`DeterministicReportBlueprintBuilder` 先创建合法且完整的蓝图，包括方向、置信度、研究范围、关键认识、子问题、论证链、最强反方、三种情景、未知项和监测项。证据引用与数组形状由服务端固定。

模型只能增强 `DIRECT_ANSWER`、`KEY_INSIGHT_n_MEANING`、`SUBQUESTION_n_ANSWER`、`ARGUMENT_n_INFERENCE` 等白名单槽位。每个槽位使用 `<<<SLOT_NAME>>>...<<<END>>>`；未知槽位、重复槽位、模型自造证据编号都会被忽略。

### 4.3 ResearchReportNarrative

第二阶段同样先创建完整正文基线，再允许模型增强以下命名槽位：

- `executiveSummary`
- `whatHappened`
- `subQuestionAnalysis[]`
- `argumentAnalysis[]`
- `counterAnalysis`
- `scenarioAnalysis[]`
- `knowledgeSynthesis`
- `monitoringPlan`

槽位内部允许普通 Markdown 段落，但不允许二级标题、来源列表、URL 或证据编号。最终标题、表格、顺序、引用和证据附录由组装器生成，避免因为截断、字段类型或标题偏差丢弃整份报告。

## 五、生成流程

### 5.1 证据档案构建

新增 `ResearchEvidenceDossierBuilder`：

1. 从 `ResearchEvidenceCard` 获取 evidence、article 和来源身份。
2. 按 evidence claim、article summary、article body 的顺序组合事实摘录。
3. 使用段落去重和字符预算裁剪，而不是简单截取文章开头。
4. 推断来源等级和发布时间。
5. 为证据分配稳定编号。
6. 形成模型提示词和确定性降级报告共用的证据档案。

### 5.2 论证蓝图生成

新增 `ResearchReportBlueprintAgent`：

- 超时 90 秒；真实全流程验证表明 45 秒会在当前模型服务上触发读超时。
- `maxOutputTokens=3000`。
- 温度沿用全局配置。
- 输入包含研究问题、对象类型、计划子问题、证据档案和证据充分性结果。
- 提示词要求根据问题类型动态拆解，不允许默认套用收入、利润、订单框架。
- 提示词只声明服务端允许增强的文本槽位，不要求模型复制任何嵌套对象、数组或证据引用。
- 首次槽位覆盖不足时只请求关键缺失槽位；模型不可用或输出无效时保留 `DeterministicReportBlueprintBuilder` 生成的完整蓝图。

### 5.3 蓝图校验

`ResearchReportBlueprintValidator` 检查：

- 只引用允许的 `E` 编号。
- `directAnswer` 非空且包含研究对象或原问题核心词。
- 关键认识 3–6 条。
- 子问题 3–6 个，key 合法且不重复。
- 至少两条论证链。
- 正反证据存在时必须进入对应论证。
- 最强反方观点有证据或明确标记为待验证假设。
- 场景和监测项包含具体变量，不能只有“关注风险”等空泛表达。

### 5.4 深度正文生成

新增 `ResearchReportNarrativeAgent`：

- 超时 120 秒。
- `maxOutputTokens=7000`。
- 输入为已校验蓝图和证据档案，不再输入旧规则 Markdown。
- 目标正文 8,000–16,000 中文字符，由完整基线与模型增强段落共同构成。
- 要求围绕对象特定事实展开，但模型不能新增 URL、证据编号、关键数字或日期；引用由 Java 组装时绑定。
- 首次输出被截断时保留已经解析的段落，只请求尚缺失的槽位；修复沿用 120 秒和 `maxOutputTokens=7000`。

### 5.5 程序化组装

`StructuredResearchReportAssembler` 固定生成：

1. 标题与研究元信息。
2. 核心结论。
3. 关键认识。
4. 执行摘要。
5. 研究范围与口径。
6. 关键事实与数字表。
7. 发生了什么。
8. 命题拆解与逐题判断。
9. 核心证据链。
10. 反方解释与争议。
11. 机制与情景推演。
12. 最终认识与未知项。
13. 跟踪清单与失效条件。
14. 证据附录。

组装器负责证据锚点、目录锚点、来源链接和 Markdown 转义。模型不直接控制文档骨架。

### 5.6 质量校验和修复

新增 `ResearchReportQualityValidator`，返回结构化问题列表：

- `MISSING_SECTION`
- `ANSWER_NOT_DIRECT`
- `INSUFFICIENT_KEY_INSIGHTS`
- `INSUFFICIENT_OBJECT_FACTS`
- `INVALID_EVIDENCE_REF`
- `UNCITED_NUMERIC_FACT`
- `WEAK_COUNTERARGUMENT`
- `GENERIC_CONTENT_DOMINANT`
- `DUPLICATED_CONTENT`
- `REPORT_TOO_SHORT`
- `REPORT_TOO_LONG`
- `OUTPUT_TRUNCATED`

修复提示只携带失败字段、原蓝图和必要证据，不整份重新生成。仍失败时进入证据驱动降级。

## 六、证据驱动降级报告

重构 `ResearchReportGenerator`：

- 不再用固定的行业机制、情景和指标段落填充篇幅。
- 从证据档案提取关键事实表、时间线和支持/反方矩阵。
- 每个子问题按实际命中证据生成简短回答；无证据时明确缺口。
- 固定文字只用于标签和边界说明，主体内容必须来自研究对象和证据。
- 生成模式改为 `EVIDENCE_STRUCTURED_FALLBACK`。
- `warning_message` 写入模型失败阶段、异常类型或质量问题编码。

降级报告不强求达到 8,000 字，但必须满足结构、引用和对象相关性要求。

## 七、服务与持久化改造

### 7.1 ResearchReportService

生成顺序调整为：

```text
dossier -> blueprint -> narrative -> assemble -> validate -> persist
```

保存时：

- `generation_mode` 使用 `MODEL_STRUCTURED`、`MODEL_REPAIRED` 或 `EVIDENCE_STRUCTURED_FALLBACK`。
- `warning_message` 保存可读的降级原因，不保存 API Key、完整模型响应或堆栈。
- `executive_summary` 从结构化 narrative 直接取得。
- `character_count` 使用最终 Markdown 长度。
- 继续保持按 `runId` 幂等 upsert 和 Vault 文件路径兼容。

本期不修改数据库结构，避免为了展示结构新增迁移；结构化对象作为生成中间态，正式产物仍为 Markdown。旧报告完全兼容。

### 7.2 可观测性

- 模型阶段记录 `report-blueprint`、`report-narrative`、`report-repair` Agent Run 或结构化日志。
- 日志记录耗时、输出字符数、验证问题编码和降级阶段。
- 禁止 `catch (Exception ignored)`。
- API 继续通过现有 `generationMode` 和 `warningMessage` 向前端暴露结果。

## 八、前端阅读器

### 8.1 Markdown 解析

新增轻量 `researchReportPresentation`：

- 从二级标题提取目录和稳定锚点。
- 为 `[E1]` 引用生成指向证据附录的链接。
- 旧报告缺少证据锚点时保持普通 Markdown 展示。
- 不在前端重新推断研究结论。

### 8.2 页面布局

桌面端：

```text
┌──────────────────────────────────────────────┐
│ 返回 / 标题 / 生成状态 / 质量指标           │
├──────────────┬───────────────────────────────┤
│ 章节目录     │ 结论仪表盘                    │
│ 当前章节高亮 │ 关键认识                      │
│              │ 正文、表格、证据链            │
│              │ 来源附录                      │
└──────────────┴───────────────────────────────┘
```

- 目录使用 `position: sticky`，正文最大宽度约 840–920px。
- 第一屏结论与关键认识使用清晰卡片，正文不重复一级标题。
- 二级标题具有编号和明显留白，三级标题保持较弱层级。
- 表格允许横向滚动，证据引用使用统一强调色。
- 打印时隐藏工具栏和目录，保留标题、指标、正文和来源。

移动端目录折叠为顶部 `<details>`，正文单列展示。

## 九、兼容性与错误处理

- 旧 `DETERMINISTIC`、`LLM_VALIDATED` 报告继续展示，生成方式文案保持兼容。
- 新生成模式增加中文展示映射。
- 模型未配置：直接生成证据驱动降级报告，警告为“模型未配置”。
- 蓝图模型失败：立即恢复完整确定性蓝图，仍继续调用 narrative 增强器，不跳过后续模型阶段。
- narrative 模型失败：保留完整确定性正文；部分槽位成功时合并已完成内容，只修复缺失槽位。
- Vault 写入失败：不把报告标记为完成，保持现有事务与错误语义。
- 证据不足：允许生成较短报告，但必须明确未知项，不能制造数字补长度。

## 十、测试策略

### 10.1 后端单元测试

- 证据档案包含稳定 `E` 编号、正文摘录、日期和来源等级。
- 上下文预算不会截断到半个证据项。
- 槽位解析忽略未知或重复槽位，并限制单槽长度；非法引用、数组形状和反方结构由 Java 基线与校验器控制。
- blueprint Agent 使用 90 秒超时和 3,000 输出 token；narrative Agent 使用 120 秒超时和 7,000 输出 token。
- 组装器生成全部章节、证据锚点和关键事实表。
- 质量校验识别无引用数字、无效证据、重复段落和通用内容占比过高。
- 修复只针对缺失槽位，最多执行一次，且不会丢弃第一次已完成的槽位。
- 任一异常都会形成具体 warning，不再静默吞掉。
- 降级报告不包含与研究对象无关的固定行业模板。

### 10.2 服务测试

- 模型蓝图和正文均通过时保存 `MODEL_STRUCTURED`。
- 修复后通过时保存 `MODEL_REPAIRED`。
- 事实审计局部修复后通过时保存 `MODEL_CLAIM_REPAIRED`。
- 模型超时或质量失败时保存 `EVIDENCE_STRUCTURED_FALLBACK` 和原因。
- 同一 runId 重建报告保持幂等。
- 报告仍只使用运行内证据。

### 10.3 前端测试

- 新旧报告都能打开。
- 目录包含全部二级章节并能跳转。
- `[E1]` 能定位证据附录。
- 生成模式和降级原因正确展示。
- 移动端目录可展开，表格不撑破页面。

### 10.4 真实全流程

先使用不连接数据库的 `ResearchReportModelSmokeTest` 验证当前模型协议，再使用隔离数据库执行真实命题研究：

1. 启动隔离后端与前端。
2. 发起“长鑫科技上市两日的市值和交易表现说明什么”。
3. 等待规划、搜索、证据评估和报告生成完成。
4. 验证报告不是静默 `DETERMINISTIC`。
5. 验证关键认识、事实表、动态子问题、证据链、反方观点、最终认识和来源附录。
6. 验证正文引用全部有效，报告长度和质量门槛达标。
7. 用浏览器检查目录、层级、表格和移动端展示。

## 十一、实施顺序

1. 用失败测试锁定当前短输入、静默降级和固定模板问题。
2. 实现证据档案与预算控制。
3. 实现蓝图契约、Agent 和校验器。
4. 实现 narrative 契约、Agent、组装器和质量校验器。
5. 重构证据驱动降级报告和 `ResearchReportService`。
6. 实现目录、证据跳转和新生成模式展示。
7. 运行定向测试、完整测试、构建和隔离真实全流程。
8. 根据真实报告继续调整提示词、预算和校验规则，直到验收通过。
