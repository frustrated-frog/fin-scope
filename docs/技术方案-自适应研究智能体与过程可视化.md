# 自适应研究智能体与过程可视化技术方案

> 对应 PRD：`docs/产品需求-自适应研究智能体与过程可视化.md`  
> 日期：2026-07-26

## 1. 设计结论

V1 继续采用 Java 原生模块化单体，不引入新的 Agent 框架。动态规划是现有 Deep Research Runtime 之上的受控决策层：

```text
ResearchThesis
  -> ResearchPlanningAgent
  -> ResearchPlanValidator
  -> ResearchMissionService
       -> research_mission
       -> research_mission_task
  -> ResearchService executor
       -> ResearchToolRegistry
       -> source_scan / public_news_search
       -> ResearchEvidenceGapAnalyzer
       -> research_mission_gap
  -> ResearchRuntimeService
       -> checkpoint / events / guard / resume
  -> ResearchReportService
  -> ResearchEvaluationService
```

LLM 只提出候选计划。服务端的 Validator、Tool Registry、Runtime 和 Evidence Gate 才拥有执行决定权。

## 2. 模块边界

### 2.1 Domain

新增 `com.finscope.domain.research.mission`：

- `ResearchMission`：研究合同和计划状态。
- `ResearchMissionTask`：可执行任务节点。
- `ResearchMissionGap`：一次证据缺口评估。
- `ResearchMissionView`：API 聚合视图。
- `ResearchToolDescriptor`：对前端和 Planner 暴露的工具契约。

Domain 不依赖 Spring、DAO 或 RPC。

### 2.2 DAO

新增 `ResearchMissionRepository`，负责：

- 初始化 pending mission；
- 原子替换候选计划；
- 更新任务生命周期；
- 保存 Gap Snapshot；
- 查询聚合数据；
- 启动恢复时中断活动任务。

DAO 不负责计划生成、图校验和证据判断。

### 2.3 Service

新增 `com.finscope.service.research.mission`：

- `ResearchToolRegistry`：工具白名单和描述。
- `ResearchPlanningAgent`：模型调用、严格解析和确定性降级。
- `ResearchPlanValidator`：字段、工具、依赖和 DAG 校验。
- `ResearchMissionService`：任务状态编排与持久化。
- `ResearchEvidenceGapAnalyzer`：从 run-scoped evidence 生成缺口快照。
- `ResearchSearchSourceFactory`：把已校验查询转换为临时 RSS Source。

`ResearchService` 只增加调用这些边界的编排代码，不吸收 JSON 解析、SQL 或展示逻辑。

### 2.4 Web

- `ResearchController` 增加 Tool Registry 和 Mission 查询接口。
- `ResearchRunDetailResponse` 增加可空 `mission`。
- 旧运行没有 mission 时保持正常返回，不做数据回填。

### 2.5 Frontend

新增独立 `ResearchMissionMap.tsx`，避免继续扩大 `ResearchView.tsx`。

组件只消费 `ResearchMissionView`：

- 不在前端推断任务完成；
- 不用本地计时器模拟进度；
- 不直接依赖 Agent Run 原始字段；
- 状态翻译、阶段分组和进度计算使用纯函数，便于测试。

## 3. 数据模型

### 3.1 research_mission

```sql
CREATE TABLE research_mission (
  research_run_id INTEGER PRIMARY KEY,
  goal TEXT NOT NULL,
  subject TEXT,
  scope_summary TEXT NOT NULL,
  success_criteria TEXT NOT NULL,
  status TEXT NOT NULL,
  planning_mode TEXT NOT NULL,
  plan_version INTEGER NOT NULL DEFAULT 1,
  max_actions INTEGER NOT NULL,
  active_task_key TEXT,
  fallback_reason TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY(research_run_id) REFERENCES research_run(id) ON DELETE CASCADE
);
```

状态：

```text
PENDING -> PLANNING -> RUNNING -> COMPLETED
                            ├──> PARTIAL_SUCCESS
                            └──> FAILED
```

### 3.2 research_mission_task

```sql
CREATE TABLE research_mission_task (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  research_run_id INTEGER NOT NULL,
  task_key TEXT NOT NULL,
  title TEXT NOT NULL,
  question TEXT NOT NULL,
  task_type TEXT NOT NULL,
  tool_code TEXT NOT NULL,
  intent TEXT NOT NULL,
  status TEXT NOT NULL,
  dependencies TEXT,
  parallel_group TEXT,
  query_text TEXT,
  rationale TEXT,
  expected_evidence TEXT,
  output_summary TEXT,
  evidence_delta INTEGER NOT NULL DEFAULT 0,
  source_delta INTEGER NOT NULL DEFAULT 0,
  skip_reason TEXT,
  started_at TEXT,
  ended_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(research_run_id, task_key),
  FOREIGN KEY(research_run_id) REFERENCES research_run(id) ON DELETE CASCADE
);
```

### 3.3 research_mission_gap

```sql
CREATE TABLE research_mission_gap (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  research_run_id INTEGER NOT NULL,
  assessment_index INTEGER NOT NULL,
  after_task_key TEXT,
  sufficient INTEGER NOT NULL,
  evidence_count INTEGER NOT NULL,
  source_count INTEGER NOT NULL,
  support_count INTEGER NOT NULL,
  counter_count INTEGER NOT NULL,
  warnings TEXT,
  recommended_intent TEXT NOT NULL,
  state_hash TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE(research_run_id, assessment_index),
  FOREIGN KEY(research_run_id) REFERENCES research_run(id) ON DELETE CASCADE
);
```

列表字段继续使用项目现有的稳定分隔编码，避免为 SQLite 引入 JSON 查询依赖。

## 4. Tool Registry

Registry 是代码级白名单，不从模型或数据库动态加载。

```java
public interface ResearchToolRegistry {
    List<ResearchToolDescriptor> list();
    ResearchToolDescriptor required(String code);
    boolean contains(String code);
}
```

Descriptor 包含：

```text
code / name / description
inputSchema / outputSchema
timeoutMs / readOnly / parallelizable
riskLevel / budgetType
```

V1 的工具执行仍由 `ResearchService` 调用已有领域服务。Registry 不持有反射方法，也不允许模型传入类名。

## 5. Planning Agent

### 5.1 输入

Planner Prompt 只包含：

- 命题字段；
- 主题代码；
- 当日日期；
- 最大动作预算；
- Registry 生成的精简工具契约。

文章正文、API Key、数据库结构和运行时内部对象不会进入 Prompt。

### 5.2 输出

```json
{
  "scopeSummary": "聚焦需求、供给、公司兑现与反方风险",
  "successCriteria": [
    "至少两个独立来源",
    "同时包含支持与反方证据"
  ],
  "tasks": [
    {
      "taskKey": "search_support",
      "title": "验证支持证据",
      "question": "哪些最新事实支持该命题？",
      "taskType": "SEARCH",
      "toolCode": "public_news_search",
      "intent": "SUPPORT",
      "dependencies": ["baseline_scan"],
      "parallelGroup": "evidence_search",
      "queryText": "研究对象 订单 资本开支 最新公告",
      "rationale": "验证核心驱动是否继续成立",
      "expectedEvidence": "公司公告或一手数据"
    }
  ]
}
```

### 5.3 校验顺序

1. JSON 可解析；
2. 顶层字段完整；
3. 任务数量和文本长度；
4. taskKey 格式与唯一性；
5. 工具白名单；
6. 意图白名单；
7. 依赖存在；
8. Kahn 拓扑排序确认无环；
9. 必备任务和正反方向完整。

任一步失败时不做局部修补，整份计划降级。这样避免混合模型计划和服务端猜测后形成不可解释图。

## 6. 确定性计划

确定性计划固定包含：

```text
baseline_scan
  ├── search_support
  ├── search_counter
  └── search_primary
        ↓
assess_evidence
        ↓
synthesize_report
```

查询词根据 `subjectName + question` 和意图模板生成。它保证：

- 计划在没有 LLM 时仍可运行；
- 测试拥有稳定基线；
- 模型计划可以与基线做离线对比。

## 7. 执行与恢复

### 7.1 正常执行

1. `createRun` 保存运行、Runtime checkpoint 和 pending mission。
2. 异步执行器将 mission 标记为 `PLANNING`。
3. Planning Agent 返回候选计划；Validator 通过后原子写入任务。
4. baseline task 包裹现有配置来源抓取。
5. 保存第一次 Gap Snapshot。
6. 按拓扑顺序选择已就绪的 search task。
7. 每次 search 后保存任务增量和新 Gap Snapshot。
8. 证据充分时跳过剩余 search task。
9. assess 和 synthesis 任务包裹现有证据评估与报告生成。
10. mission 与 research run 一起进入终态。

### 7.2 恢复

- `COMPLETED/SKIPPED` 任务不重复执行。
- `RUNNING` 任务在进程重启时改为 `INTERRUPTED`。
- resume 将 `INTERRUPTED/FAILED` 任务恢复为 `PENDING`，但不删除历史 Gap。
- Runtime checkpoint 继续拥有唯一执行权；Mission 状态不单独抢占执行器。

### 7.3 一致性

- 任务开始和结束分别提交，保证 UI 能看到真实活动节点。
- Mission 的 `active_task_key` 与任务 `RUNNING` 状态同时更新。
- 任务写入失败时不执行外部动作。
- 外部动作完成但任务完成写入失败时，Runtime action fingerprint 防止重复副作用。

## 8. Evidence Gap

Analyzer 复用 `RunScopedResearchContextService` 和 `ResearchEvidenceSelector`。为保持封装，`ResearchReportService` 暴露结构化 assessment，而不是让 Mission Service 读取 Repository。

```text
sufficient
evidenceCount
sourceCount
supportCount
counterCount
warnings[]
recommendedIntent
stateHash
```

`stateHash` 由上述计数和排序后的警告计算，用于识别重复评估与无进展。

## 9. API 契约

### GET /api/research/tools

返回全部工具描述。该接口不返回实现类、凭证或外部地址。

### GET /api/research/runs/{id}/mission

```json
{
  "mission": {},
  "tasks": [],
  "gaps": [],
  "tools": []
}
```

运行不存在返回 404；运行存在但属于旧版本且没有 mission 时返回 404。运行详情接口对旧运行则返回 `mission: null`。

## 10. UI 设计

### 10.1 视觉方向

主题：研究指挥室，而不是通用流程看板。

Token：

- `Obsidian Navy #101722`：主背景；
- `Graphite #202B38`：任务轨道；
- `Signal Cyan #52C7D9`：真实运行焦点；
- `Evidence Lime #A8CC6B`：证据满足；
- `Counter Amber #E1A85B`：缺口和反证；
- `Paper Mist #E8EEF2`：主要文本。

字体沿用项目系统字体，数据标签使用等宽字体栈，避免引入网络字体。

### 10.2 Signature

“证据脉冲轨道”是唯一强调元素：一条贯穿任务图的细线，只有当前任务对应区段缓慢移动。它表达证据正在从工具流向判断，不使用无意义发光背景。

### 10.3 布局

```text
┌──────────────── Contract ────────────────┐
│ 目标 / 范围 / 成功条件 / 计划模式 / 预算 │
└──────────────────────────────────────────┘
┌──────────── Mission graph ───────────────┬──── Gap ledger ────┐
│ 基线 → 支持搜索 ┐                         │ Evidence  4 / 6     │
│       反方搜索 ├→ 证据评估 → 报告         │ Sources   2 / 2     │
│       一手搜索 ┘                         │ Counter   missing   │
└──────────────────────────────────────────┴────────────────────┘
┌──────────────── Tools used ───────────────────────────────────┐
```

桌面端图与账本左右布局；窄屏将任务按依赖顺序转为纵向时间线。

## 11. 测试策略

- Validator：非法工具、重复键、悬空依赖、环、缺必备任务。
- Planner：LLM 合法、LLM 非法降级、未配置降级。
- Repository：计划原子替换、任务生命周期、Gap 单调序号。
- Mission Service：证据充分跳过任务、恢复只重置活动任务。
- ResearchService：计划任务驱动搜索、已完成任务不重复。
- API：旧运行兼容、mission 聚合响应。
- Frontend：合同、活动任务、缺口、降级模式、空状态、终态。
- 全量：Java 8 Maven、Vitest、TypeScript、Vite build。

## 12. 设计取舍

- V1 不并发写 SQLite：保证研究任务状态和文章入库的一致性；并行组先作为 DAG 语义保留。
- V1 不做开放式工具循环：计划先校验再执行，Runtime 继续控制动态性。
- V1 不做多 Agent 辩论：先把单 Agent 规划和证据闭环做实。
- V1 不引入向量检索：现阶段任务规划不依赖语义记忆，避免为了技术名词增加基础设施。
