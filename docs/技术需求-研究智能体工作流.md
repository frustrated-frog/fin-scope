## 2. 执行摘要

研究页需要从一个手动“运行研究”的页面，演进为一个受治理的 Agent 工作流控制台。

目标不是自由聊天机器人。FinScope 的优势是本地优先、有证据支撑、确定性可审计的投研工作台。Agent 层应该让工作流更强，但不能获得不受约束的写入权限，也不能把决策隐藏在自然语言后面。

推荐架构是混合式 Agent 工作流：

```text
Natural-language mission
  -> Query rewrite and slot extraction
  -> Clarification if required
  -> Structured research plan
  -> Deterministic execution steps
  -> Controlled LLM nodes
  -> Evidence, event, learning, content artifacts
  -> Trace, budget, warnings, fallback, resumability
```

研究页应把这个生命周期呈现为运维型工作台：

1. 任务入口：保留结构化控件，新增自然语言请求。
2. 计划状态：每次研究运行都有显式步骤，包含状态、依赖、尝试次数、耗时和结果。
3. 执行 Trace：Agent 节点展示 fingerprint、降级、错误类型、终止原因、预算快照和进展增量。
4. 恢复控制：失败或跳过的步骤后续可以从最后一个有意义的检查点重试、跳过或恢复。
5. 澄清路径：目标含糊时先暂停执行并提出聚焦问题，而不是猜测。

第一阶段必须先建立计划状态主干和研究详情 UI。自然语言任务与恢复能力依赖这条主干，应该后续叠加。

## 3. 产品定位

FinScope 是服务学习、研究、内容准备和面试/项目展示的个人投研情报系统。研究页应传达三种产品能力：

1. 它能运行完整研究工作流，而不只是抓取信息流。
2. 它能解释一次运行中发生了什么，包括局部失败。
3. 它能逐步变得更 Agent 化，同时不牺牲可审计性。

最高级的版本不是“自治模型决定一切”。更强的设计是：

> 模型理解模糊研究目标；系统掌控计划、执行资格、预算、证据约束、持久化和恢复。

这个定位与本地面试材料高度一致。生产级 Agent 系统看的不是模型调用次数，而是计划 schema、循环控制、工具治理、可追踪性、fallback 和状态恢复。

## 4. 目标

### 4.1 用户目标

1. 按主题、日期和来源策略运行每日或临时投研。
2. 明确理解一次运行做了什么、失败在哪里。
3. 看到与运行关联的研究产物：事件、证据、学习任务、内容选题和简报。
4. 当结构化控件太慢时，可以用自然语言研究目标启动。
5. 当目标信息不足或与可用来源冲突时，收到澄清问题。
6. 局部失败后能恢复有价值的工作，不丢失已完成步骤。

### 4.2 工程目标

1. 保持模块化单体架构。
2. 保持确定性服务作为执行主干。
3. 为每个研究运行增加显式计划状态。
4. 让 Agent Trace 既可机器读取，也可 UI 阅读。
5. 增加循环护栏：最大节点数、最大 LLM 调用数、重复动作检测、进展增量、终止原因。
6. 把查询改写和澄清 做成受控节点，而不是聊天子系统。
7. 每个新行为都能通过服务测试或 API 测试验证。

### 4.3 展示目标

该功能应帮助在面试中解释 Agent 工程：

1. 带 `plan + past_steps + response` 的计划执行工作流。
2. 状态机驱动的恢复能力。
3. 稳定动作 fingerprint 和 warning/hard 阈值。
4. LLM 输出 schema 校验和确定性 fallback。
5. 作为可中断工作流状态的澄清机制。
6. Trace 优先的可观测性。

## 5. 非目标

1. 不构建通用聊天助手。
2. 不允许模型直接写数据库行。
3. 不引入 LangGraph、CrewAI、AutoGen、MQ、Redis、vector DB 或工作流引擎。
4. 第一阶段不实现自治多 Agent 委派。
5. 默认 UI 不暴露原始提示词。
6. 不提供投资推荐或交易建议。
7. 不抓取私有或需要凭证的数据。
8. 不把运行时行为耦合到 Codex 或任何开发工具。

## 7. 设计原则

### 7.1 确定性主线，Agent 化边缘

数据抓取、文章持久化、去重、事件归并、证据存储和简报写入仍由确定性服务负责。LLM 节点可以辅助：

1. 任务改写和 slot 提取。
2. 证据候选抽取。
3. 文章/事件解读。
4. 学习问题生成。
5. 内容角度生成。
6. 基于已有证据的人类可读综合。

### 7.2 Plan 是运行时对象

Plan 不是散文。它必须可持久化、可查询、可恢复。每个计划步骤 必须包含：

1. 稳定的 `step_id`。
2. 人类可读标题。
3. 类型与执行器。
4. 状态。
5. 依赖关系。
6. 输入摘要和输出摘要。
7. 尝试次数和最大尝试次数。
8. 时间信息。
9. 错误类型和错误消息。
10. fallback 和终止原因。

### 7.3 Trace 是产品界面

Trace 不只是调试信息，它是研究页的价值组成部分。用户应该看到为什么一次运行是 partial、为什么节点 fallback、是否触发预算，以及产生了哪些证据。

### 7.4 澄清 是状态，不是聊天

当任务含糊时，run 应进入 `NEEDS_CLARIFICATION`，并带有结构化问题和选项。用户回答后更新 任务 或 plan，然后继续。第一版可以只返回澄清结果，不做多轮聊天。

### 7.5 运行时护栏优先于 提示词 规则

提示词 可以约束模型，但运行时代码必须强制执行：

1. 最大节点数。
2. 最大 LLM 调用数。
3. 最大重试次数。
4. 相同动作 warning 和 hard 阈值。
5. 无进展限制。
6. 错误分类。
7. 输出 schema 校验。

### 7.6 高级但本地优先

系统应该通过清晰工程体现 Agent 能力，而不是堆外部依赖。SQLite、Java 服务、React UI 和本地 Markdown 仍是中心。

## 8. 目标用户体验

### 8.1 研究页布局

研究页演进为三个区域：

1. 任务/运行启动器
   - 结构化字段：date、themes、max sources、include disabled。
   - 自然语言 任务 输入。
   - 后续阶段提供 “Preview plan” 和 “Run research” 操作。

2. 运行与计划
   - 运行列表保持密集、运维型。
   - 选择一次 run 后打开 详情面板，展示计划步骤。
   - 每个 step 显示状态、耗时、尝试次数、进展、错误/降级 徽标。

3. Trace 与产物
   - 计划来源。
   - Agent trace 时间线。
   - 警告/降级 面板。
   - 到生成简报、事件、证据、学习任务和内容选题的链接。

### 8.2 状态模型

运行状态：

```text
RUNNING
COMPLETED
PARTIAL_SUCCESS
FAILED
NEEDS_CLARIFICATION
CANCELLED
```

计划步骤 状态：

```text
PENDING
RUNNING
COMPLETED
FAILED
SKIPPED
BLOCKED
```

步骤状态解释：

1. `PENDING`：依赖未完成或尚未开始。
2. `RUNNING`：正在执行。
3. `COMPLETED`：满足成功条件。
4. `FAILED`：没有成功 fallback，且该步骤不能安全跳过。
5. `SKIPPED`：降级 或 护栏 判定无需执行或执行不安全，因此有意跳过。
6. `BLOCKED`：等待用户澄清或外部配置。

## 9. 工作流架构

### 9.1 高层流程

```text
ResearchController
  -> ResearchMissionService
       -> QueryRewriteAgent or deterministic parser
       -> ClarificationPolicy
  -> ResearchService
       -> ThemeProfileService
       -> SourcePlanner
       -> ResearchRunRepository
       -> ResearchRunPlanService
       -> ResearchExecutionService
            -> AgentHarness
            -> FetchService
            -> Event/Evidence/Learning/Content services
            -> BriefService
       -> AgentTraceService
```

第一阶段可以继续把执行逻辑放在 `ResearchService` 内，但必须引入 `ResearchRunPlanService` 并持久化 计划步骤。后续阶段可以抽出 `ResearchExecutionService`，让 `ResearchService` 保持小而清晰。

### 9.2 Plan 模板

默认研究计划是：

```text
plan_sources
  -> fetch_sources
  -> classify_events
  -> extract_evidence
  -> compose_brief
  -> summarize_run
```

第一阶段可以把来源抓取建模为一个聚合 step，并保留单个来源级 trace 行。后续如有需要，再为每个来源增加子步骤。

### 9.3 任务 流程

结构化请求：

```json
{
  "runDate": "2026-07-09",
  "themeCodes": ["china_macro", "ai_startup"],
  "maxSourcesPerTheme": 3,
  "includeDisabled": false
}
```

自然语言请求：

```json
{
  "missionText": "今天跟一下 AI 创业融资、中国宏观和公司 IPO，有禁用来源就先不跑"

```

改写输出：

```json

  "themeCodes": ["ai_startup", "china_macro", "company_ipo"],

  "includeDisabled": false,

  "missingSlots": [],
```

```json
{
  "status": "NEEDS_CLARIFICATION",

  "options": [
    {"label": "包含停用来源", "value": "include_disabled"},
```

## 12. 服务设计

### 12.1 ResearchRunPlanService

职责：

1. 为运行创建默认计划步骤。
2. 将步骤标记为 running。
3. 带输出摘要和进展增量完成步骤。
4. 带错误类型和错误消息将步骤标记为失败。
5. 带终止原因跳过或阻塞步骤。
6. 为 运行详情 列出 计划步骤。
7. 保持 repository 层操作小而不承载业务。

必要公开方法：

```java
List<ResearchRunPlanStep> initializeDefaultPlan(Long researchRunId, int sourceCount);
ResearchRunPlanStep start(Long researchRunId, String stepId);
ResearchRunPlanStep complete(Long researchRunId, String stepId, String outputSummary, int progressDelta);
ResearchRunPlanStep fail(Long researchRunId, String stepId, String errorType, String errorMessage);
ResearchRunPlanStep skip(Long researchRunId, String stepId, String reason);
List<ResearchRunPlanStep> findByRunId(Long researchRunId);
```

### 12.2 ResearchService 集成

创建运行时：

1. 解析 themes。
2. 规划 sources。
3. 保存 `research_run`。
4. 保存 planned sources。
5. 初始化默认 plan。
6. 执行 plan。

执行期间：

1. `plan_sources` 在 sources 持久化后完成。
2. `fetch_sources` 包裹逐来源循环。
3. `compose_brief` 包裹 `briefService.generate(...)`。
4. `summarize_run` 在计数和状态更新后完成。
5. 出现异常时，当前步骤失败，运行变为 `FAILED`。

第一阶段可以在 fetch 后把 `classify_events` 与 `extract_evidence` 标记为带聚合计数的 completed，因为现有 ingestion side effects 已在 fetch/article pipeline 内执行。后续阶段如果需要，可以拆成显式 service 调用。

### 12.3 AgentHarness 演进

现有 `AgentHarness.runNode(...)` 应保持小。后续阶段可以增加：

1. Node 预算 前置检查。
2. LLM 预算 前置检查。
3. 无进展跟踪。
4. Retry 辅助器。
5. Error 分类器。
6. 直接或通过事件 callback hook 更新计划步骤。

第一阶段不应过度拟合。它应该从 `ResearchService` 串起计划状态，而不是重建 harness。

## 15. 错误处理

### 15.1 错误类型

使用稳定字符串：

```text
UNKNOWN
VALIDATION_FAILED
NO_SOURCES
SOURCE_FETCH_FAILED
LLM_UNCONFIGURED
LLM_TIMEOUT
LLM_INVALID_JSON
UNGROUNDED_OUTPUT
BUDGET_EXCEEDED
REPEATED_ACTION
NO_PROGRESS
NEEDS_CLARIFICATION
```

### 15.2 运行结果规则

1. 所有必要步骤完成：`COMPLETED`。
2. 非关键来源失败但 brief 已生成：`PARTIAL_SUCCESS`。
3. 关键持久化或 plan 初始化失败：`FAILED`。
4. 执行前缺少用户决策：`NEEDS_CLARIFICATION`。
5. 重复动作硬停止且无 fallback：按已完成产物决定 `FAILED` 或 `PARTIAL_SUCCESS`。

## 21. 阶段 B/C 实现契约：异步 Agent 工作流

本节记录 2026-07-09 手动 QA 后新增的实现契约：点击“运行研究”可能阻塞数分钟，并让 Research tab 缺少有用反馈。

### 21.1 问题陈述

同步 `POST /api/research/runs` 契约会让 UI 等待 来源抓取、文章入库、LLM-backed interpretation、evidence extraction、学习任务生成、内容选题生成 和 简报组合 全部结束后，才能显示 运行详情。本地运行时这意味着：

1. 按钮看起来卡住。
2. 可能展示 `sources=0` 或空计划状态，却没有可操作解释。
3. 被终止的后端可能在 `research_run`、`research_run_plan` 和 `fetch_run` 中留下 `RUNNING` 行。
4. 前端无法在 Agent 工作流实际运行时展示它。

### 21.2 后端契约

`POST /api/research/runs` 现在表示“创建并启动 研究运行”，而不是“同步完成 研究运行”。

必要行为：

1. 解析 themes 和 planned sources。
2. 持久化 `research_run`，状态为 `status=RUNNING`。
3. 持久化 planned source snapshot。
4. 持久化默认 `research_run_plan` steps。
5. 返回前完成 `plan_sources`。
6. 立即返回 run、planned sources 和 `status=RUNNING`。
7. 在 `researchTaskExecutor` 上执行剩余工作流。
8. 如果没有匹配 source，立即失败，并展示可见的 `NO_PLANNED_SOURCES`计划状态，跳过下游 steps。

专用 executor 名为 `researchTaskExecutor`。第一版故意使用单线程，以避免并发 研究运行 导致 SQLite 写入和昂贵 LLM 工作重叠。

### 21.3 终态顺序

Run 不得在可见工作流状态完整之前进入终态。

成功或 partial run 的最终顺序必须是：

1. 完成 `fetch_sources`。
2. 完成 event、evidence、brief 和 summary steps。
3. 记录 `research-orchestrate` 的 `agent_run`。
4. 持久化终态 `research_run.status` 和聚合计数。

这可以避免 UI 看到 `run.status=COMPLETED`，但 `summarize_run` 仍是 `RUNNING` 或 orchestrator trace 缺失。

### 21.4 启动恢复

应用启动时，对中断工作做防御性恢复：

1. `research_run.status=RUNNING` 变为 `FAILED`。
2. `fetch_run.status=RUNNING` 变为 `FAILED`。
3. `research_run_plan.status=RUNNING` 变为 `FAILED`。
4. 中断 run 的 `research_run_plan.status=PENDING` 变为 `SKIPPED`。
5. 恢复终止原因为 `PROCESS_RESTART`。

这还不是 resumability。它是诚实恢复，确保 UI 不会把陈旧运行状态当作仍在执行。

### 21.5 Source Planning 鲁棒性

`SourceProfile.from(Source)` 必须根据本地 source 名称、tags、types 和 URLs 推断可用的 source tiers 与 theme codes。第一版同时识别英文和中文来源线索：

1. 市场和宏观线索，如 `市场`、`宏观`、`政策`、`财经`、`金融`、`market`、`markets`、`economy` 和 `fed`，映射到 `china_macro`。
2. AI 和创业线索，如 `ai`、`arxiv`、`cs.AI`、`人工智能`、`大模型`、`机器学习` 和 `创业`，映射到 `ai_startup`。
3. 公司和 IPO 线索，如 `company`、`ipo`、`公司`、`上市`、`融资`、`财报` 和 `产业`，映射到 `company_ipo`。
4. RSS、MarketWatch、DJ 和 Zhihu sources 映射到 `MEDIA`。
5. arXiv 和 `cs.AI` sources 映射到 `CURATED_AI`。

### 21.6 前端契约

Research tab 必须把 run creation 和 run completion 视为两个独立状态。

必要行为：

1. POST 请求执行期间，按钮文案为 `启动中`。
2. POST 返回 `RUNNING` 后，应用立即打开 运行详情，并展示计划步骤和 planned sources。
3. 全局状态消息为 `研究运行已启动，正在同步进度`。
4. 当选中的 run 处于 active 状态时，前端轮询：
   - `GET /api/research/runs/{id}`
   - `GET /api/research/runs`
5. 当选中 run 的状态离开 活跃状态集合 时停止轮询。
6. 进入终态后刷新 工作区，使 事件、证据、简报、学习、内容工作室和智能体运行 反映后端产物。

初始 活跃状态集合 是 `RUNNING`。后续阶段可以加入 `QUEUED`、`PAUSING` 或 `RESUMING`。
