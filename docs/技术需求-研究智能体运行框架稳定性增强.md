# TRD：FinScope Research Agent Harness 稳定性增强

## 1. 文档信息

- 项目名称：FinScope
- 文档类型：技术需求文档
- 目标版本：V5 Agent Harness 前置版本
- 文档状态：草稿
- 创建日期：2026-07-03
- 目标用户：个人金融学习者、投研信息整理者、自媒体内容创作者、求职项目展示者
- 主要目标：在不破坏现有模块化单体和确定性流水线的前提下，把已有 Agent 节点升级为可计划、可预算、可降级、可观测、可恢复的研究运行时。

## 2. 背景与问题

FinScope 当前已经具备信息源、Inbox、去重、新意判断、事件簇、证据项、每日简报、主题沉淀、学习任务、内容选题和 Agent Trace 等能力。现有 Agent 能力主要体现在：

1. `ArticleInterpretationAgent` 对文章进行结构化解读。
2. `EvidenceService` 可以调用 LLM 抽取证据项，并做 grounding 校验。
3. `ResearchService` 可以创建研究运行，规划来源，执行抓取，生成 brief，并写入 `agent_run`。
4. LLM 不可用或输出不可信时，系统会回到确定性兜底。

这些设计方向正确，但仍偏“节点能力”，还没有形成正式 harness。主要问题是:

1. `ResearchRunContext` 当前只传递 `runId`，不能承载预算、步骤、错误计数、动作指纹、终止原因等运行状态。
2. `agent_run` 目前更像节点日志，缺少 attempt、fingerprint、termination reason、fallback reason、budget snapshot 等排障字段。
3. LLM 节点各自处理 prompt、parse、fallback、trace，缺少统一执行边界。
4. 研究运行没有显式 plan/task state，失败后只能看摘要，不容易知道停在哪一步。
5. 缺少 loop controller 层的稳定性护栏，例如最大 LLM 调用次数、重复动作检测、连续无进展检测、错误分类与有限重试。
6. 前端 Agent Trace 只展示节点、状态、耗时和错误，不足以呈现研究链路的工程深度。

本 TRD 目标是补齐一个 FinScope 专用 Research Agent Harness，而不是引入通用多 Agent 框架。

## 3. 产品定位

Research Agent Harness 是 FinScope 的研究运行时控制层。它的职责不是替代现有服务，也不是让模型自主决定抓取、入库和事件归并,而是把已经存在的研究流水线组织成可治理的节点序列：

```text
ResearchRun
  -> plan sources
  -> fetch sources
  -> ingest articles
  -> attach event clusters
  -> extract evidence
  -> interpret article/event
  -> generate brief
  -> generate learning tasks
  -> generate content ideas
  -> trace / budget / fallback
```

一句话定位：

> Harness 管模型节点的边界、预算、错误、证据和可观测性；业务服务仍然管业务主流程。

## 4. 目标与非目标

### 4.1 目标

1. 建立统一的 Agent 节点执行入口，集中处理 trace、fallback、错误分类、预算和耗时。
2. 建立研究运行级运行上下文,支持 runId、nodeId、stepIndex、limits、counters、recentActions、warnings。
3. 建立动作指纹和重复动作检测，避免同一来源、同一文章、同一事件在一次 run 中被无意义反复处理。
4. 建立研究运行 plan/task state，让 run 的当前阶段、已完成阶段、失败阶段可展示、可恢复、可排障。
5. 扩展 Agent Trace 的数据库和前端展示，让用户能看到节点时间线、fallback 原因、终止原因和预算消耗。
6. 保持 LLM 只做受控认知任务,所有输出必须结构化、可校验、可降级。
7. 保持代码高级简约，不引入重型工作流引擎、向量数据库、MQ 或通用 Agent 编排框架。
8. 把代码规范和模块边界写成硬约束，防止后续为了 Agent 化破坏项目结构。

### 4.2 非目标

1. 不做通用聊天 Agent。
2. 不做开放工具调用系统。
3. 不允许模型决定是否写库、是否删除数据、如何选择数据库主键。
4. 不做多 Agent 自主委派和子 Agent 调度。
5. 不引入 LangGraph、CrewAI、AutoGen 等通用运行时依赖。
6. 不把 Codex、Claude Code 或其他开发工具作为运行时能力。
7. 不做公共热点榜单、运营后台、发布链路或投资建议。
8. 不把公司内部数据、接口、提示词、凭证或专有资料放入项目。

## 5. 设计原则

### 5.1 确定性流水线是主干

抓取、标准化、去重、新意判断、事件归并、数据库写入、Markdown 写入和导出仍然由确定性 Java 服务控制。LLM 只能参与：

1. 文章结构化解读。
2. 证据候选抽取。
3. 学习问题生成。
4. 内容选题角度生成。
5. 对已有证据的可读组织。

### 5.2 Harness 不越过业务边界

Harness 只负责编排和治理 Agent 节点，不直接访问 Repository，不直接拼 SQL，不直接调用外部 HTTP，不直接写 Vault。

正确方向：

```text
Controller
  -> ResearchService
  -> AgentHarness
  -> AgentNode
  -> domain service / rpc client
  -> repository
```

禁止方向：

```text
AgentHarness -> JdbcTemplate
AgentHarness -> Controller
AgentHarness -> SourceAdapter
AgentNode -> Controller
Controller -> Repository
Repository -> LlmChatClient
```

### 5.3 LLM 输出必须先验后用

所有 LLM 输出必须满足：

1. 合法 JSON。
2. 字段在白名单内。
3. 枚举值可识别。
4. confidence 在合法范围内。
5. source、url、数字、事实必须来自输入证据。
6. 缺字段时走确定性 fallback。
7. 无法 grounding 时记录 `REJECTED` 并走 fallback。
8. fallback 不影响抓取、Inbox、事件归并和简报主流程。

### 5.4 运行时护栏必须在代码里

预算、重复检测、retry 上限、硬停止不能只写在 prompt 里。Prompt 可以提示模型，但真正的限制必须由 Java runtime 执行。

### 5.5 可观测性是产品能力

Agent Trace 不是调试日志的附属品。FinScope 的求职展示价值很大一部分来自：

1. 能看到每次研究运行做了什么。
2. 能看到模型何时被调用。
3. 能看到为什么 fallback。
4. 能看到为什么停止。
5. 能看到哪些结论有证据支持。

## 6. 代码规范与工程边界

本节是实现时的硬准则。后续如果参考 `dd-expense` 或 `whole-hotspot`，只能吸收不违反 FinScope 架构边界的代码风格。

### 6.1 模块边界

继续遵守现有 Maven 分层：

```text
finscope-web
  -> finscope-service
      -> finscope-dao
      -> finscope-rpc
  -> finscope-domain

finscope-dao -> finscope-domain + finscope-common
finscope-rpc -> finscope-domain
```

约束：

1. `finscope-web`: 只做 REST contract、request/response DTO、Bean 装配和异常映射。
2. `finscope-service`: 只做用例编排、状态机、算法小组件和 Agent Harness。
3. `finscope-dao`: 只做 SQL、RowMapper、schema 初始化和 repository 查询。
4. `finscope-rpc`: 只做外部信息源、LLM 客户端和外部协议适配。
5. `finscope-domain`: 只放领域对象、枚举常量、DTO 风格对象，不依赖 Spring。
6. `finscope-common`: 只放通用异常、常量和工具，不承载业务编排。

### 6.2 Spring 代码规范

新增或触达的 Spring Bean 必须遵守：

1. 使用构造注入，不新增字段 `@Resource` 或字段 `@Autowired`。
2. 依赖字段使用 `private final`。
3. Controller 只依赖 Service。
4. Service 可以依赖 Repository、RPC client、小算法组件和其他 Service，但不能依赖 Controller。
5. Repository 只能依赖 `JdbcTemplate` 和通用工具。
6. `@Bean` 装配逻辑留在 `finscope-web/config`，业务规则不得写入配置类。
7. 修改旧类时，如果该类属于本次核心路径，同步迁移为构造注入。

### 6.3 DTO 与领域对象规范

1. Web 入参必须使用显式 request DTO，不使用裸 `Map<String, String>`。
2. Web 出参必须使用领域对象或 response DTO，避免把内部执行上下文直接暴露给前端。
3. 状态值使用 `ResearchEnums` 或专门 enum/常量集中定义。
4. request DTO 只表达请求形状，状态校验放在 Service。
5. domain 对象不引入 Jackson、Spring MVC、JdbcTemplate 等框架依赖。

### 6.4 Repository 规范

1. Repository 不做业务判断。
2. Repository 不调用 LLM。
3. Repository 不做 fallback。
4. Repository 方法名表达数据动作，例如 `save`, `findById`, `updateStatus`, `findByResearchRunId`。
5. schema 增量使用 `CREATE TABLE IF NOT EXISTS` 和 `ensureColumn`，保持本地数据可平滑升级。
6. 大字段如 Prompt input/output 默认做长度控制或摘要化，避免 SQLite 无限膨胀。

### 6.5 Agent/LLM 代码规范

1. LLM 调用只允许出现在 `service/agent` 或明确的 interpreter/extractor 类中。
2. LLM client 只通过 `LlmChatClient` 调用，不得在 Service 中直接拼 HTTP。
3. Prompt 构建、JSON 解析、字段校验、evidence grounding 应拆成小方法或小类。
4. 每个 Agent 节点必须有确定性 fallback。
5. 每个 Agent 节点必须记录 trace。
6. 每个 Agent 节点必须声明输入摘要、输出摘要、状态和耗时。
7. 不允许模型输出直接穿透写库。

### 6.6 安全规范

1. API Key 只能从本地环境变量或本地配置注入，不得提交真实凭证。
2. 默认配置不得内置真实 token。
3. Trace 中不得保存 API Key、Authorization header、cookie 或用户私密数据。
4. Prompt input/output 入库前做长度限制和敏感字段过滤。
5. `data/finance.db`、raw content、export、`.env` 和本地凭证必须保持 Git 忽略。

## 7. 核心领域模型

### 7.1 AgentRunContext

描述一次研究运行中 Agent 节点共享的运行状态。

关键字段：

```text
researchRunId
currentNodeName
stepIndex
startedAt
limits
counters
recentActions
warnings
metadata
```

说明：

1. 替代当前只保存 runId 的 `ResearchRunContext`。
2. 第一版可以仍用 `ThreadLocal`，但 ThreadLocal 内部对象必须从 `Long` 升级为上下文对象。
3. 后续如引入异步执行,必须改为显式参数传递，不能依赖 ThreadLocal 跨线程。

### 7.2 AgentBudgetPolicy

描述一次运行的预算。

关键字段：

```text
maxNodes
maxLlmCalls
maxRetriesPerNode
maxRunSeconds
maxPromptChars
maxOutputChars
sameActionWarnThreshold
sameActionHardThreshold
noProgressLimit
```

默认建议：

```text
maxNodes = 80
maxLlmCalls = 30
maxRetriesPerNode = 1
maxRunSeconds = 300
maxPromptChars = 9000
maxOutputChars = 12000
sameActionWarnThreshold = 2
sameActionHardThreshold = 3
noProgressLimit = 3
```

### 7.3 AgentNode

统一 Agent 节点接口。

概念接口：

```java
public interface AgentNode<I, O> {
    String name();
    AgentNodeResult<O> execute(I input, AgentRunContext context);
}
```

第一版不强制所有现有节点一次性改成泛型接口。可以先由 `AgentHarness` 提供函数式包装,逐步迁移。

### 7.4 AgentNodeResult

描述节点执行结果。

关键字段：

```text
status
value
inputSummary
outputSummary
errorType
errorMessage
fallbackUsed
fallbackReason
progressDelta
metadata
```

状态枚举：

```text
SUCCESS
FALLBACK
REJECTED
FAILED
SKIPPED
BLOCKED
```

### 7.5 AgentActionFingerprint

描述一次动作的稳定指纹。

关键字段：

```text
nodeName
targetType
targetId
normalizedIntent
inputHash
fingerprint
```

示例：

```text
source-fetch:source:12
article-interpret:article:345
evidence-extract:event:20:article:345
brief-generate:date:2026-07-03
```

### 7.6 ResearchRunPlanState

描述一次研究运行的任务状态。

关键字段：

```text
researchRunId
version
status
steps
createdAt
updatedAt
```

步骤字段：

```text
stepId
title
status
nodeName
dependsOn
startedAt
endedAt
summary
errorMessage
evidenceRefs
```

步骤状态：

```text
PENDING
RUNNING
COMPLETED
FAILED
SKIPPED
BLOCKED
```

## 8. Harness 运行流程

### 8.1研究运行创建

```text
POST /api/research/runs
  -> ResearchController
  -> ResearchService.createRun()
  -> ThemeProfileService
  -> SourcePlanner
  -> ResearchRunRepository.save()
  -> AgentHarness.createContext()
  -> ResearchRunPlanState 初始化
  -> ResearchService.execute()
```

### 8.2 节点执行

```text
ResearchService
  -> AgentHarness.runNode("source-fetch", input, callback)
  -> beforeNode:
       budget check
       fingerprint check
       plan step running
       trace start
  -> callback:
       execute deterministic service or LLM node
  -> afterNode:
       classify result
       compute progressDelta
       record agent_run
       update plan step
       update budget counters
       decide continue / fallback / stop
```

### 8.3 终止条件

正常终止：

1. 所有必要 计划步骤完成。
2. 研究运行生成 summary。
3. brief 已生成或明确跳过。
4. trace 已完整写入。

fallback 终止:

1. LLM 未配置,全部 LLM 节点走 fallback。
2. 某个非关键来源抓取失败，run 标记为 `PARTIAL_SUCCESS`。
3. 个别证据抽取失败，保留文章和事件，证据使用确定性 fallback。

失败终止：

1.研究运行初始化失败。
2. 数据库写入失败。
3. 关键服务异常导致无法生成 run 结果。
4. hard budget 触发且没有可用 fallback。

需要澄清：

1. 用户输入自然语言目标但无法映射到主题。
2. 请求主题没有可用来源。
3. `includeDisabled=false` 且有效来源数量为 0。

第一版可以不做交互式恢复，只把 run 状态设为 `NEEDS_CLARIFICATION`，前端展示可选动作。

## 9. 稳定性护栏

### 9.1 预算控制

`AgentHarness` 在每次节点执行前检查：

1. 当前节点数是否超过 `maxNodes`。
2. 当前 LLM 调用次数是否超过 `maxLlmCalls`。
3. 当前耗时是否超过 `maxRunSeconds`。
4. 当前 提示词 长度是否超过 `maxPromptChars`。
5. 当前节点 retry 次数是否超过 `maxRetriesPerNode`。

触发预算后：

1. 可 fallback 的节点返回 `FALLBACK`。
2. 非关键节点返回 `SKIPPED`。
3. 关键节点返回 `FAILED` 并写入 termination reason。

### 9.2 重复动作检测

每个节点执行前生成 fingerprint，放入 context 的 sliding window。

规则：

1. 同 fingerprint 出现次数达到 警告阈值，记录 警告，但允许继续一次。
2. 同 fingerprint 出现次数达到 硬阈值，不再执行节点，直接返回 `SKIPPED` 或 `FALLBACK`。
3. fingerprint 必须按节点语义生成，不能简单 hash 完整 JSON。

节点指纹策略：

| 节点 | 指纹关键字段 |
| --- | --- |
| `source-fetch` | sourceId |
| `article-interpret` | articleId + article body hash |
| `evidence-extract` | eventId + articleId + body hash |
| `brief-generate` | briefDate |
| `learning-task-generate` | eventId + themeCode |
| `content-idea-generate` | eventId + themeCode |

### 9.3 错误分类与有限重试

错误类型：

```text
LLM_UNCONFIGURED
LLM_TIMEOUT
LLM_HTTP_ERROR
INVALID_JSON
SCHEMA_INVALID
UNGROUNDED_OUTPUT
EMPTY_RESULT
FETCH_FAILED
DATABASE_ERROR
BUDGET_EXCEEDED
REPEATED_ACTION
UNKNOWN
```

处理策略：

| 错误类型 | 处理 |
| --- | --- |
| `LLM_UNCONFIGURED` | 不 retry，直接 fallback |
| `LLM_TIMEOUT` | 最多 retry 1 次，仍失败 fallback |
| `LLM_HTTP_ERROR` | 不立即重复请求同一输入，记录 failed 或 fallback |
| `INVALID_JSON` | 最多 retry 1 次，提示 JSON 格式错误 |
| `SCHEMA_INVALID` | 降级 |
| `UNGROUNDED_OUTPUT` | rejected + fallback |
| `EMPTY_RESULT` | fallback 或 skipped |
| `FETCH_FAILED` | 非关键来源 局部成功 |
| `DATABASE_ERROR` | run failed |
| `BUDGET_EXCEEDED` | fallback/skipped/failed |
| `REPEATED_ACTION` | skipped 或 fallback |

### 9.4 进展检测

每个节点返回 `progressDelta`。

示例：

```text
source-fetch: 新增文章数 + 成功抓取数
event-attach: 新增事件数 + follow_up 数
evidence-extract: 新增证据数
article-interpret: 成功解读数
brief-generate: brief 是否生成
learning-task-generate: 新增学习任务数
content-idea-generate: 新增选题数
```

如果连续 `noProgressLimit` 个节点没有进展，run 不继续扩展非关键节点，进入 summary 或 partial success。

```sql
CREATE INDEX IF NOT EXISTS idx_agent_run_fingerprint ON agent_run(action_fingerprint);
```

## 16. 风险与应对

### 16.1 过度工程化

风险： 为了展示 Agent Harness 引入复杂框架,破坏当前项目简洁性。

应对：

1. 第一版只做 FinScope 专用 harness。
2. 不引入外部工作流引擎。
3. 节点接口可轻量包装，不强制全量重构。

### 16.2 代码边界被打穿

风险： Harness 变成超级 Service，直接访问 DAO、RPC、LLM、Controller。

应对：

1. Harness 只做治理。
2. 业务动作仍由现有 Service 执行。
3. 新增代码 review checklist 检查层级依赖。

### 16.3 Trace 数据膨胀

风险： prompt 和 output 大量入库导致 SQLite 膨胀。

应对：

1. input/output 做长度限制。
2. 额外保存 hash 和 summary。
3. UI 默认展示摘要。

### 16.4 LLM 幻觉污染结果

风险： 模型输出未被证据支持的结论。

应对：

1. grounding 校验。
2. rejected + fallback。
3. 证据不足时明确“不足以判断”。
4. 不允许 LLM 直接写库。

### 16.5 ThreadLocal 与异步执行冲突

风险： 后续并行化后 ThreadLocal 上下文丢失。

应对：

1. 第一版保持同步执行。
2. 文档明确异步化前必须改为显式 context 参数。
3. 不在 `CompletableFuture` 中读取 ThreadLocal。

## 17. 验收标准

第一版完整验收：

1. 创建研究运行后，系统生成计划状态。
2. 每个核心节点通过 harness 记录 trace。
3. LLM 未配置时研究运行仍能完成或 局部成功。
4. LLM 输出非法 JSON 时节点 fallback,主流程不中断。
5. LLM 输出未 grounding 的证据时记录 `REJECTED`。
6. 同一动作重复达到 硬阈值 时不再执行。
7. 预算触发时 run 有明确 termination reason。
8. Research detail 页面可以看到 plan、trace、fallback 和 警告。
9. 代码保持现有模块边界。
10. 后端 `mvn test`、前端 `npm test`、前端 `npm run build` 均通过。

## 18. 实现前检查清单

每次实现本 TRD 中任务前必须检查：

1. 是否需要新增 domain 对象，而不是把 JSON 字符串散落在 Service 中。
2. 是否需要显式 request/response DTO。
3. 是否保持 Controller 只依赖 Service。
4. 是否保持 Repository 只做 SQL。
5. 是否使用构造注入。
6. 是否为每个新增状态增加测试。
7. 是否为每个 LLM 节点提供 降级。
8. 是否为每个新增 trace 字段设置长度控制。
9. 是否避免把真实 API Key 或私有数据写入配置和测试。
10. 是否避免把 Agent Harness 写成通用大框架。

## 19. 最终结论

FinScope 的 Agent 增强方向不是“让模型拥有更多权力”,而是“让模型节点进入一个更可靠的研究运行时”。Research Agent Harness 应该把已有的 article interpretation、evidence extraction、研究运行 trace 串成一套可治理系统:

```text
deterministic pipeline
  + controlled LLM nodes
  + explicit run context
  + plan state
  + budget guardrails
  + action fingerprint
  + structured fallback
  + trace UI
```

这样既能保持 FinScope 本地优先、个人投研、非热点榜单的产品边界,又能体现 Agent 工程化能力: 状态外部化、上下文控制、循环防护、证据约束、fallback 运行和可观测性。
