# 文章事件证据链路走查与整改方案

## 背景与目标

当前系统已形成“文章抓取 → 情报卡片 → 事件聚类 → 证据抽取 → 学习任务/内容选题”的研究链路。本次整改的目标不是增加更多页面，而是保证四个事实：

1. 一次成功入库必须形成完整、可查询的研究对象；失败不能留下无法恢复的半成品。
2. 一篇文章同一时刻只能归属一个事件；并发与重试不得制造重复事件或重复证据。
3. 证据必须能回溯到原始文章，并正确表达来源、置信度和抽取边界。
4. 前端展示必须与后端事实一致，不因超时、慢响应或筛选状态产生错误成功、混合详情或无反馈操作。

## 走查结论

### P1：会导致错误成功、数据分裂或治理失败

| 编号 | 问题 | 触发与影响 | 整改方向 |
|---|---|---|---|
| P1-1 | URL 抓取超时回退到当前页第一篇文章 | 新文章尚未出现时显示旧文章已生成 | 仅接受任务返回的 articleId 或精确 URL 命中，不再使用位置回退 |
| P1-2 | 移动文章默认值与处理值不一致 | 默认“拆成新事件”请求变为 null 目标，后端 400 | 统一使用 `NEW_EVENT` 常量并增加默认路径测试 |
| P1-3 | 快速切换事件发生响应乱序 | B 的标题搭配 A 的文章和证据 | 请求序号与 AbortController，切换时清空旧详情 |
| P1-4 | 文章、卡片、事件、证据不是同一原子单元 | 失败会留下文章、链接或事件半成品 | 将入库协调器和事件挂接纳入事务；对外部 LLM 失败保留降级策略 |
| P1-5 | 事件挂接为 check-then-act 且缺少唯一约束 | 并发时同文多事件、同事件重复创建 | 为文章归属建立唯一约束，冲突后读取既有结果；事件创建加唯一事件键约束与冲突恢复 |

### P2：会持续降低研究质量或造成错误理解

| 编号 | 问题 | 整改方向 |
|---|---|---|
| P2-1 | 删除/移动最后一篇文章后残留 ACTIVE 空事件 | 归档空事件并禁止自动聚类进入空事件 |
| P2-2 | 合并事件时证据不去重 | 以 `(eventId, articleId, normalizedClaim)` 去重，保留更高置信度记录 |
| P2-3 | 关联表无外键 | 开启 SQLite foreign_keys；新库表加外键，运行时增加孤儿扫描/修复 |
| P2-4 | 全局 refresh 使用单个 Promise.all | 核心页面资源独立刷新，局部失败不清空事件/证据状态 |
| P2-5 | 事件治理操作无忙碌、错误反馈和重复提交保护 | 统一 mutation 状态与 toast，失败后保留编辑值 |
| P2-6 | 证据账本不可追溯 | 返回文章标题、URL、发布时间；页面增加跳转原文与事件详情 |
| P2-7 | 来源名包含字母 x 即判为社交媒体 | 使用标准化来源类型或严格 X/Twitter 匹配 |
| P2-8 | 列表无分页与参数边界校验 | 事件、证据分页；校验日期区间和置信度 0–100 |

### P3：体验与可维护性

- 文章分页缺少响应序号，删除最后一页后不会回退。
- 筛选后详情可能仍指向被隐藏的事件。
- 事件合并为逐文章 N+1 SQL。
- 文章卡片展开无键盘语义。
- `EventsView` 同时承担查询、治理、详情与展示，后续拆为数据协调和详情组件。

## 目标架构

```text
ArticleIngestCoordinator (@Transactional)
  ├─ ArticleRepository.save
  ├─ InsightCardService.createForArticle
  └─ EventClusterService.attachArticle (@Transactional)
       ├─ 原子领取 articleId 的事件归属
       ├─ 创建/更新 EventCluster
       ├─ EvidenceService.capture（去重）
       ├─ LearningTask / ContentIdea
       └─ 计数与空事件状态收敛

前端
  ├─ ArticleView：精确任务结果、分页请求序号、页码回退
  ├─ EventsView：请求序号、治理忙碌/错误、筛选选择收敛
  └─ EvidenceView：证据 → 文章 → 事件双向可追溯
```

## 数据规则

- `event_article_link.article_id` 唯一，一篇文章只能属于一个事件。
- `event_cluster.canonical_event_key` 唯一。同一事件键并发创建时恢复既有事件。
- `evidence_item` 保存 `claim_key`，同事件、同文章、同 claim 只有一条有效证据。
- 事件无关联文章时状态必须为 `ARCHIVED`，不会进入自动候选池。
- 证据来源层级优先使用标准化 source 类型；名称匹配只作为兼容回退。

## 验收标准

1. 任一入库阶段失败后，数据库不存在本次新增的孤儿文章、卡片、事件、链接或证据。
2. 并发执行同一文章 attach 时，最终只有一个事件链接；同一事件键最终只有一个事件。
3. 合并后，同文同 claim 的证据只有一条，且保留最高置信度。
4. 默认“拆成新事件”操作成功；快速切换事件不会混合详情。
5. 超时恢复只会确认精确 URL/任务 articleId，不会提示旧文章成功。
6. 证据账本可打开事件、原文文章和来源 URL。
7. 事件、证据查询分页，非法日期范围/置信度返回 400。
