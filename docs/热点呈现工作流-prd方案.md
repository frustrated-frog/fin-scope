真正接近“完美”的热点发现系统，不应该是“抓三家新闻 → 丢给大模型总结 → 按时间倒序展示”。那样本质上只是一个资讯搬运器。

完整方案应该围绕一个核心转变来设计：

> 系统采集的是文章，识别的是事件，计算的是热点，呈现的是经过证据约束的判断。

也就是说，东方财富、同花顺、财联社返回的每一条内容只是原始材料，最终用户看到的主体不应当是文章，而应该是一个持续演进的“热点事件”。

整体链路可以设计成：

```text
东方财富 / 同花顺 / 财联社
          ↓
多源采集与原始数据存档
          ↓
统一标准化与实体识别
          ↓
文章级去重与转载链识别
          ↓
事件聚类与增量归并
          ↓
热点发现与事件生命周期判断
          ↓
证据抽取、冲突检测、可信度计算
          ↓
AI结构化解读
          ↓
质量校验与风险控制
          ↓
热点榜单、事件详情、时间线、订阅推送
          ↓
用户反馈与离线评测反哺
```

下面从头到尾拆开。

---

**一、先确定整个系统的核心数据对象**

这是系统设计中最重要的一步。很多热点系统做不好，不是因为模型能力不够，而是数据模型从一开始就是错的，只设计了 `news_article` 一张表。

至少应该存在五种核心对象：

```text
Article：某个平台发布的一篇文章或快讯
Event：现实世界中发生的一件事情
Topic：长期存在的研究主题，例如“机器人”“低空经济”
Evidence：支撑某个事实判断的原文证据
Insight：系统基于证据生成的解读
```

例如财联社发布“某公司宣布建设AI数据中心”，东方财富五分钟后发布类似内容，同花顺十分钟后转述。这是三条 `Article`，但对应的是一个 `Event`。

如果随后又出现“公司回应项目投资金额”“交易所发出问询函”，这两条新闻既与原事件相关，又属于新的事件进展。它们可以挂在同一个长期 `Topic` 下，同时成为原事件时间线的新节点。

因此推荐采用三层结构：

```text
Topic：某公司AI数据中心建设
 ├── Event 1：公司首次宣布建设计划
 │    ├── Article A：财联社报道
 │    ├── Article B：东方财富报道
 │    └── Article C：同花顺报道
 │
 ├── Event 2：公司披露投资金额
 │
 └── Event 3：交易所发出问询函
```

用户首页主要看到 `Event`，详情页可以进入 `Topic` 查看完整演化过程，原始文章只作为证据来源存在。

---

**二、采集层必须做到可追溯、可重放、可补偿**

东方财富、同花顺、财联社应该分别实现独立的数据源适配器，而不是把三个源的抓取逻辑混在一起。

```java
public interface NewsSourceAdapter {

    String sourceCode();

    FetchResult fetchIncremental(FetchCursor cursor);

    ArticleDetail fetchDetail(String sourceArticleId);
}
```

采集层必须记录三个时间：

```text
publishTime：平台标注的新闻发布时间
eventTime：新闻中描述的实际事件发生时间
ingestTime：你的系统抓取到这条数据的时间
```

这三个时间不能混用。比如一份公告晚上发布，新闻第二天早上被媒体报道。如果只根据新闻发布时间判断，热点发现可能晚了十几个小时。

每一条抓取结果都应该首先保存到不可变的原始表或对象存储中：

```text
raw_news
- source
- source_article_id
- request_url
- raw_payload
- payload_hash
- publish_time
- ingest_time
- fetch_batch_id
- fetch_status
```

保存原始数据非常重要。后续解析规则、实体识别模型或者聚类算法升级后，可以直接重放历史数据，不需要重新请求外部平台。

采集需要保证幂等。建议使用：

```text
idempotencyKey = source + sourceArticleId
```

如果某些平台没有稳定文章 ID，则使用：

```text
source + canonicalUrl + publishTime
```

作为第二级幂等键，再通过正文哈希做兜底。

采集任务不要直接调用后续业务逻辑，而应该把原始数据发送到消息队列：

```text
news.raw
news.normalized
news.deduplicated
event.updated
event.hotness.changed
insight.generated
```

你可以用 Kafka，也可以在早期使用 RocketMQ。关键不是选哪一个，而是让采集、聚类、热度计算和大模型分析彻底解耦。

当大模型调用失败时，不能阻塞新闻采集；当东方财富暂时不可用时，也不能影响财联社的数据处理。

当前雷达预解读链路已选用 Kafka：Top 20 榜单快照写入并预热成功后，生产者发送 `finscope.radar.interpretation.requested.v1` 批次消息；消费者逐个事件发起幂等解读，单条失败不会中断同批其他事件。榜单始终先对用户可见，解读完成后只刷新雷达视图版本，因此用户打开热点时可以直接复用已经生成的结果。

当前排序还明确区分事件时间：优先使用新闻发布时间，缺失时回退到首次发现时间，不使用持续抓取时不断变化的最后发现时间。综合热点分中时效权重为 24%，超过 24 小时快速接近零、超过 48 小时归零；优先级评分中的时效项同步提高到 25 分，避免旧闻因重复采集长期占据榜单。

---

**三、标准化不是简单地统一字段名**

不同数据源对标题、快讯、正文、股票代码、行业和发布时间的表达都不同。需要先把原始数据转化为统一的标准对象：

```json
{
  "articleId": "internal-id",
  "source": "CLS",
  "sourceArticleId": "123456",
  "title": "某公司拟建设人工智能数据中心",
  "content": "...",
  "summary": "...",
  "publishTime": "2026-08-05T14:03:00+08:00",
  "ingestTime": "2026-08-05T14:03:18+08:00",
  "articleType": "FLASH",
  "categories": ["AI", "算力"],
  "entities": [],
  "numbers": [],
  "contentHash": "...",
  "qualityScore": 0.92
}
```

标准化阶段至少要完成正文清洗、时间解析、股票代码统一、公司别名归一、行业分类、关键数字提取和文章类型判断。

其中，公司实体归一非常关键。以下表达可能指向同一个主体：

```text
宁德时代
宁德时代新能源科技股份有限公司
CATL
300750
```

因此需要维护自己的证券主数据和实体词典：

```text
security_entity
- entity_id
- stock_code
- exchange
- standard_name
- short_name
- aliases
- industry
- concept_tags
```

文章中的公司名、股票代码、产品名、人物和政策机构，都要映射为内部统一实体 ID。后续聚类、热点计算和影响分析都依赖这一层。

如果实体识别不准，两个完全不同公司的新闻可能被错误合并；同一个公司的不同别名又可能被拆成多个热点。

---

**四、文章去重和事件聚类必须分成两层**

文章去重解决的是：

> 这两篇文章是不是同一篇内容的转载或改写？

事件聚类解决的是：

> 这两篇不同的文章是不是在描述同一件现实事件？

这两者不能混为一谈。

文章去重可以分四级完成。

第一级是 URL 规范化，去掉追踪参数、分享参数和无意义查询参数。

第二级是精确哈希。对清洗后的正文计算 SHA-256，相同哈希直接判定为完全重复。

第三级是近似文本去重。可以使用 SimHash、MinHash 或正文分段指纹，识别轻微改写、调整段落顺序和替换标题的转载内容。

第四级是语义重复判断。对标题和摘要生成向量，再结合发布时间、公司实体和关键数字判断。

最终不要直接删除重复文章，而应该建立转载组：

```text
duplicate_group
- group_id
- canonical_article_id
- first_source
- first_publish_time
- member_count
```

因为“多少平台转发”本身就是热点传播速度的重要信号。但是计算热度时不能把同一篇稿件被十个平台转载，当成十个独立信源。

这就需要进一步识别“信源家族”。如果同花顺和东方财富都转载了同一份公告，它们虽然是两个平台，但真正的信息源只有一个：上市公司公告。

---

**五、事件聚类是整个系统最核心的算法**

事件聚类建议采用“候选召回 + 多特征打分 + 灰区判定”的增量模式。

当一篇新文章进入系统时，不要和所有历史事件比较，而是先召回一批候选事件。召回条件可以包括：

```text
过去24小时或72小时内
相同核心公司或人物
相同一级行业或主题
向量相似度 TopK
关键词或关键数字重叠
```

然后计算文章与候选事件之间的综合匹配分数：

```text
EventMatchScore =
0.30 × 标题语义相似度
+ 0.20 × 核心实体重合度
+ 0.15 × 事件动作相似度
+ 0.10 × 关键数字重合度
+ 0.10 × 时间接近度
+ 0.10 × 正文语义相似度
+ 0.05 × 来源上下文一致性
```

这里最容易被忽视的是“事件动作”。

例如下面三条新闻虽然实体相同，但并不是同一事件：

```text
某公司拟收购A公司
某公司终止收购A公司
监管部门调查某公司收购A公司
```

如果只比较公司名和向量，很容易全部合并。你应该抽取事件结构：

```text
主体：某公司
动作：收购
客体：A公司
状态：拟进行 / 已终止 / 被调查
时间：
金额：
地点：
```

推荐使用类似事件五元组的数据结构：

```text
subject
predicate
object
status
event_time
```

然后设置三段阈值：

```text
score >= 0.82：自动合并至已有事件
score <= 0.62：新建事件
0.62 < score < 0.82：进入灰区判定
```

灰区可以交给一个成本较低的模型进行二分类：

```text
这两组材料是否描述同一现实事件？
只允许输出 SAME_EVENT 或 DIFFERENT_EVENT。
```

但模型只能处理少量灰区，不能让所有新闻都依赖大模型聚类，否则成本、延迟和稳定性都会出问题。

事件需要维护动态中心：

```text
event_centroid = 所有核心文章向量的加权平均
```

权威来源、首发来源和高质量文章权重更高，转载文章权重更低。这样可以降低大量转载内容对事件中心的污染。

---

**六、要防止事件簇不断漂移**

增量聚类常见的问题是“链式错误”。

文章 A 与事件相似，合并进去；文章 B 与 A 相似，也被合并；文章 C 与 B 相似，继续合并。最后 C 和最初的事件已经不是同一件事，但整个簇被不断拉宽。

因此不能只判断新文章和事件中心的相似度，还要判断它与事件核心事实是否一致。

可以维护两种事件描述：

```text
Event Core：事件不可变的核心事实
Event Latest State：事件当前最新进展
```

例如：

```text
Event Core：
某公司计划收购A公司

Event Latest State：
公司已终止收购，监管问询仍在继续
```

新文章加入前，需要同时判断：

```text
是否属于同一核心事件
是否是该事件的新进展
是否实际上构成一个新的子事件
```

如果是同一主题下的新动作，应新建子事件并挂到原 Topic，而不是无限往同一个 Event 里塞。

---

**七、热点发现不能只看新闻数量**

真正的热点至少包含四个维度：

```text
Attention：有多少人在讨论
Velocity：热度增长有多快
Importance：事情本身有多重要
Credibility：信息是否可信
```

推荐将热点分数拆成多个可解释子分：

```text
HotScore =
0.22 × SourceBreadth
+ 0.20 × PublishVelocity
+ 0.15 × SourceAuthority
+ 0.12 × Novelty
+ 0.10 × CrossPlatformSpread
+ 0.08 × Persistence
+ 0.08 × MarketReaction
+ 0.05 × UserEngagement
```

其中 `SourceBreadth` 不是文章数量，而是独立原始信源数量。十篇转载同一公告的文章不能算十个独立信源。

`PublishVelocity` 衡量短时间内的新增速度，例如过去10分钟、30分钟和1小时的文章增长量。可以做环比：

```text
velocity =
当前30分钟新增量
÷
过去6小时每30分钟平均新增量
```

`Novelty` 衡量事件与过去历史新闻的差异。某家公司每天重复发布相似宣传稿，即使文章数量多，也不应该长期占据榜单。

`Persistence` 用于区分一闪而过的新闻和持续发酵事件。一个事件连续几个小时都有新进展，其热度应该比单点爆发更稳定。

`MarketReaction` 可以接入行情数据，例如相关股票的价格、成交量、换手率、板块联动和资金变化。但必须注意：

> 市场异动只能说明事件与市场反应在时间上相关，不能直接证明新闻导致了价格变化。

因此展示时应写成“事件发布后，相关板块出现明显异动”，而不是武断地说“该新闻导致股票上涨”。

热度还必须加入时间衰减：

```text
FinalHotScore =
RawHotScore × e^(-λ × hoursSinceLastUpdate)
```

不同事件类型可以使用不同衰减速度。快讯衰减很快，政策和重大产业事件可以衰减得更慢。

---

**八、热点不是一个分数，而应该有生命周期**

每个事件应该有明确状态：

```text
DISCOVERED：刚被发现
EMERGING：开始增长
RISING：快速升温
PEAK：达到峰值
COOLING：热度下降
REACTIVATED：出现新进展后重新升温
CLOSED：长期无更新
```

状态转换不能只依赖绝对热度，还要看一阶变化和二阶变化：

```text
当前热度
热度增长速度
增长速度是否继续加快
```

例如：

```text
热度低，但增长非常快：潜在热点
热度高，但已经快速下降：过气热点
热度高且仍在上涨：核心热点
热度下降后再次突增：事件复燃
```

因此用户首页最好至少提供三类榜单：

```text
实时热点：当前综合热度最高
正在升温：增长速度最快
重大事件：重要性高但不一定文章最多
```

否则娱乐性高、传播量大的新闻很容易淹没真正重要的产业和金融事件。

---

**九、构建“证据包”，再让大模型生成解读**

绝对不要把十篇文章全文直接拼起来交给模型：“请分析这个热点”。

正确做法是先构建结构化证据包：

```json
{
  "eventId": "E123",
  "coreEntities": ["某上市公司", "某产品"],
  "timeline": [],
  "facts": [
    {
      "factId": "F1",
      "claim": "公司计划投资50亿元建设项目",
      "evidenceArticleIds": ["A1", "A3"],
      "sourceCount": 2,
      "confidence": 0.94
    }
  ],
  "conflicts": [],
  "marketSignals": [],
  "unknowns": []
}
```

证据包的生成分为几个阶段。

首先从每篇文章中抽取原子事实。原子事实必须尽可能小，例如：

```text
错误：
公司发布重大利好并将推动行业快速增长。

正确：
公司宣布投资50亿元。
项目计划于2028年投产。
公司预计项目达产后年产能为X。
```

每个事实都要绑定原文片段、文章 ID、来源和发布时间。

然后把不同文章中的事实进行对齐。相同事实合并，冲突事实并列保留。

例如：

```text
来源A：投资金额为50亿元
来源B：投资金额约为60亿元
```

系统不能自行挑一个数字，而应该生成冲突记录：

```json
{
  "field": "investmentAmount",
  "values": [
    {"value": "50亿元", "sources": ["A"]},
    {"value": "60亿元", "sources": ["B"]}
  ],
  "status": "UNRESOLVED"
}
```

这样最终解读中可以明确写：

> 关于投资金额，不同来源存在差异，目前尚未完全确认。

这才是可信热点系统和普通新闻摘要系统的分界线。

---

**十、AI 解读应该拆成多个受约束步骤**

我建议不要让一个模型一次完成全部分析，而是采用多阶段流水线。

第一阶段是事实抽取，只负责输出结构化 JSON：

```text
主体
动作
客体
时间
地点
金额
事件状态
引用证据
```

第二阶段是事件摘要，只根据已确认事实生成一句话概述和三条核心信息。

第三阶段是影响分析，结合公司、产业链、板块和历史背景，分析可能影响。

第四阶段是风险和不确定性分析，明确哪些信息未确认，哪些判断只是推测。

第五阶段是后续观察点生成，告诉用户接下来应关注什么。

最终可以形成如下结构：

```json
{
  "headline": "某公司宣布建设人工智能数据中心",
  "oneSentenceSummary": "...",
  "whyHot": "...",
  "confirmedFacts": [],
  "timeline": [],
  "possibleImpacts": [],
  "affectedEntities": [],
  "uncertainties": [],
  "nextCheckpoints": [],
  "sourceReferences": []
}
```

模型必须遵循一个硬约束：

> 事实部分只能引用证据包中存在的内容；背景知识和推理必须明确标识为分析，不得与事实混写。

所以详情页最好明确区分：

```text
已确认事实
AI分析
市场表现
风险与争议
后续观察
```

而不是把所有内容混成一篇看起来很流畅、但事实和推测边界模糊的文章。

---

**十一、解读最好采用“事实—原因—影响—后续”框架**

最终面向用户的解读可以稳定使用四层结构。

第一层回答“发生了什么”，只能陈述已确认事实。

第二层回答“为什么现在成为热点”，解释首发、传播速度、平台覆盖、市场反应或者新增进展。

第三层回答“可能影响谁”，识别直接主体、上下游、竞争公司、相关行业和板块，但必须给出推理链。

第四层回答“接下来关注什么”，例如公告、业绩说明会、监管问询、项目审批、订单落地和产品发布。

示例：

```text
发生了什么：
公司宣布计划投资建设新项目，目前投资规模和投产时间已经披露。

为什么成为热点：
消息发布后30分钟内被三家财经平台集中报道，同时相关板块成交量明显增加。

可能影响：
直接受益方向主要是设备供应商和项目承建方。但目前尚未披露具体供应商名单，因此只能视为潜在关联。

接下来关注：
项目是否获得审批、资金来源、实际开工时间，以及后续订单和供应商名单。
```

这种表达比单纯输出“利好某板块，建议关注某股票”专业得多，也更可控。

---

**十二、模型生成后必须经过质量闸门**

模型输出不能直接发布，至少要经过以下校验：

```text
JSON Schema 校验
引用证据覆盖率校验
数字一致性校验
实体一致性校验
时间线顺序校验
事实与推测边界校验
冲突信息遗漏校验
敏感内容与合规校验
```

可以计算一个解读质量分：

```text
InsightQuality =
0.30 × CitationCoverage
+ 0.20 × FactConsistency
+ 0.15 × SourceDiversity
+ 0.15 × Completeness
+ 0.10 × Timeliness
+ 0.10 × RiskCompliance
```

如果质量分低于阈值，则只展示原始事件摘要，不发布深度解读。

比如事件只有一个来源、关键数字存在冲突，系统就应该显示：

```text
该事件目前仅有单一来源，信息仍待进一步确认。
```

而不是为了页面完整性强行生成一篇“深度分析”。

---

**十三、最终呈现不应该是新闻流，而应该是事件流**

首页热点卡片推荐展示：

```text
事件标题
一句话概述
当前状态：正在升温 / 持续发酵 / 热度下降
热度分数及变化
首次发现时间
最近更新时间
独立信源数量
关联公司与板块
可信度
```

例如：

```text
某公司宣布建设AI数据中心

正在升温 ↑ 36%
首次发现：14:03
最近更新：14:28
3个独立信源 · 8篇相关报道
可信度：高

热点原因：
30分钟内跨平台集中传播，相关算力板块同步出现异动。
```

详情页建议按照下面顺序：

```text
一句话结论
事件当前状态
为什么成为热点
已确认事实
事件时间线
不同来源报道
市场反应
产业链影响
观点与争议
风险与不确定性
下一观察节点
```

用户每次重新进入事件时，最好优先展示：

> 与上次相比发生了什么变化。

例如：

```text
新增进展：
公司已正式回复交易所问询。

判断变化：
此前投资金额存在争议，最新公告已确认金额为50亿元。
```

这比每次让用户重新阅读整篇解读有价值很多。

---

**十四、推荐的存储架构**

关系型数据库保存核心业务状态：

```text
MySQL / PostgreSQL
- article
- article_duplicate_group
- event
- event_article_relation
- event_fact
- event_conflict
- event_timeline
- event_snapshot
- topic
- insight
- insight_version
```

OpenSearch 或 Elasticsearch 用于新闻全文搜索、关键词检索和筛选。

Qdrant、Milvus 或 pgvector 用于文章和事件向量召回。你目前规模不大时，使用 PostgreSQL + pgvector 完全够用。

Redis 用于：

```text
实时热点榜单
频道榜单
事件详情缓存
文章去重短期缓存
分布式锁
限流
热点分数时间序列的短期窗口
```

对象存储保存原始响应、长正文、抓取快照和模型输入输出归档。

热点变化需要单独建立快照表：

```text
event_snapshot
- event_id
- snapshot_time
- article_count
- independent_source_count
- velocity
- hot_score
- credibility_score
- lifecycle_state
```

没有快照，就无法判断热点是升温还是降温，也无法进行历史回放和算法评测。

---

**十五、关键链路和非关键链路要分开**

从新闻出现到热点上线的关键链路应该足够短：

```text
抓取
→ 标准化
→ 去重
→ 事件归并
→ 初始热度计算
→ 上线事件卡片
```

大模型深度解读不要阻塞事件上线。事件可以先以“基础摘要”状态出现，后续异步补齐分析。

```text
事件先上线：
发现某公司发布重大公告

30秒后：
补充核心事实与多源摘要

进一步处理后：
补充产业链影响、争议与后续观察
```

这样即使大模型超时，热点发现仍然可以正常运行。

可以把解读状态设计成：

```text
PENDING
FACT_EXTRACTED
SUMMARY_READY
FULL_ANALYSIS_READY
QUALITY_REJECTED
```

前端根据状态渐进式展示。

---

**十六、容错和数据一致性必须提前设计**

每一个处理节点都需要幂等。例如事件归并重复消费时，不能重复增加文章数量。可以在关系表上建立唯一索引：

```text
UNIQUE(event_id, article_id)
```

消息消费采用“至少一次投递 + 业务幂等”，通常比追求绝对的 Exactly Once 更现实。

失败消息进入死信队列：

```text
news.parse.dlq
event.cluster.dlq
insight.generate.dlq
```

每条任务都保存：

```text
task_id
input_version
processor_version
retry_count
last_error
next_retry_time
```

所有模型结果必须保存模型名称、Prompt 版本、证据包版本和生成时间：

```text
model_name
prompt_version
evidence_version
generated_at
```

这样出现错误时，才能知道是数据问题、聚类问题、Prompt 问题还是模型版本变化。

---

**十七、必须建立来源可信度体系**

不能简单认为财联社、东方财富、同花顺权重固定。不同内容类型下，来源优先级不同。

例如上市公司自身公告是事实确认的一级来源，交易所公告和监管文件通常比媒体转述更强；媒体首发可能在时效性上更强，但确认度可能较低。

推荐将来源评分拆开：

```text
Authority：来源权威性
Originality：是否为首发或原始材料
AccuracyHistory：历史准确率
Timeliness：时效性
Independence：是否独立信源
```

同一家媒体也不能只有一个全局分数。它在快讯上的时效性可能很高，但某些转载内容仍然只是二手信源。

更精细的评分单位应该是：

```text
来源 × 内容类型 × 领域
```

---

**十八、系统评测决定它能不能长期进化**

热点系统不能只看“用户觉得不错”，需要建立离线数据集。

事件聚类至少评估：

```text
Pairwise Precision：
被系统合并的文章中，有多少确实属于同一事件

Pairwise Recall：
属于同一事件的文章中，有多少被正确合并

Cluster Purity：
每个事件簇内部是否足够纯净
```

热点发现要评估：

```text
热点召回率
误报率
首次发现延迟
相对主流平台的提前量
热点排序相关性
热点生命周期判断准确率
```

AI 解读要评估：

```text
事实准确率
引用覆盖率
无依据陈述比例
关键事实遗漏率
冲突发现率
数字错误率
时间线错误率
```

最重要的业务指标不是文章点击率，而是：

```text
用户是否打开事件详情
用户是否持续关注同一事件
用户是否认为“这次更新提供了新信息”
热点提醒是否被用户保留
用户是否收藏或订阅某个主题
```

还应该建立 Bad Case 分类：

```text
错误合并
错误拆分
热点发现过晚
旧闻翻炒
单一转载源被误判为多源
谣言被误判为事实
数字抽取错误
因果关系过度推断
行业关联过度扩散
```

每一个 Bad Case 都要能回溯到具体处理环节。

**十九、这个系统最容易踩的坑**

第一个坑是把“文章多”直接等同于热点。很多平台会转载同一个稿源，必须识别传播链和独立信源。

第二个坑是让大模型直接做聚类。模型适合处理模糊边界，不适合承担所有高频聚类任务。

第三个坑是事件粒度失控。粒度太粗，几天内某家公司所有新闻都被合成一个事件；粒度太细，同一事件每篇文章都单独成簇。

第四个坑是旧新闻重新传播。系统必须根据核心事实指纹和历史事件库判断这是新进展，还是旧闻被重新炒作。

第五个坑是把时间相关性写成因果关系。新闻发布后股价上涨，不代表新闻必然导致上涨。

第六个坑是解读没有证据引用。没有证据绑定，再流畅的分析也只是模型作文。

第七个坑是只保存最终结果，不保存中间过程。没有原始数据、事件快照和模型版本，就无法复现错误。

**二十、我认为最理想的最终架构**

可以将整个系统划分为六个相对独立的引擎：

```text
1. Ingestion Engine
负责多源采集、增量游标、重试、原始数据存档

2. Content Intelligence Engine
负责清洗、实体识别、分类、数字和事件要素抽取

3. Event Resolution Engine
负责文章去重、事件聚类、事件拆分合并、时间线维护

4. Hotness Engine
负责传播速度、信源广度、重要性、市场反应和生命周期

5. Evidence & Insight Engine
负责事实对齐、冲突检测、证据包、AI解读和质量校验

6. Distribution Engine
负责榜单、搜索、个性化、订阅提醒、API和多端分发
```

其中事件对象是整个系统的核心状态：

```text
Article 进入系统
    ↓
Article 被挂载到 Event
    ↓
Event 更新事实、时间线和热点分数
    ↓
Event 触发新的 Insight 版本
    ↓
用户看到 Event 的最新状态和变化
```

真正接近完美的热点系统，不是“模型写得像分析师”，而是同时做到：

> 发现得足够早，合并得足够准，来源能够追溯，事实与分析严格分开，事件可以持续更新，错误能够复现和评测。

你的东方财富、同花顺、财联社接入只是数据入口。项目真正有技术含量的部分，是后面的**事件解析、增量聚类、传播链识别、生命周期建模、证据约束生成和持续状态更新**。
